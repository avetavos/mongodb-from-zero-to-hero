มีสองวิธีแสดงความสัมพันธ์ระหว่าง document และแทบทุกการตัดสินใจออกแบบคือการเลือกระหว่างสองวิธีนี้ คุณ **embed** ได้: วางข้อมูลที่เกี่ยวข้องไว้ใน document แม่ ซ้อนเป็น sub-object หรือ array หรือ **reference**: เก็บข้อมูลที่เกี่ยวข้องใน collection ของมันเองและเก็บ identifier - มักเป็น `_id` - ไว้ในตัวแม่ แล้วค้นเมื่อต้องการ การ embed เอื้อต่อการอ่าน; การ reference เอื้อต่อ single source of truth

บทนี้ใช้ข้อมูล order ของโมดูล: `products` 500 รายการ และ order 10 000 รายการสองเวอร์ชัน (`ordersEmb` ที่แต่ละรายการมีสำเนา title และราคา, `ordersRef` ที่มีแค่ `productId`) กับ helper `revenue()` ที่รวม qty x ราคา จับจาก mongo 8.3.11, mongosh 2.11.1 และ Node driver 7.7.0 บน Mac เครื่องเดียว; แท็บ Python, Go และ Rust ถูกรันอย่างละครั้งในโปรแกรม scratch

```js
// mongosh/evr-seed.js
const rnd = (() => { let x = 7; return () => (x = (Math.imul(x, 1103515245) + 12345) >>> 0) / 4294967296; })();   // repeatable pseudo-random numbers
db.products.insertMany(Array.from({ length: 500 }, (_, i) => ({ _id: "BK-" + i, title: "Book " + i, price: 10 + (i % 40) })));
const specs = Array.from({ length: 10000 }, (_, i) => ({
  _id: "order_" + i, customerId: "cust_" + (i % 500), status: i % 3 ? "shipped" : "new",
  lines: Array.from({ length: 2 + Math.floor(rnd() * 4) }, () => { const p = Math.floor(rnd() * 500); return { p, qty: 1 + Math.floor(rnd() * 3) }; }),
}));
db.ordersEmb.insertMany(specs.map(({ lines, ...o }) => ({ ...o, items: lines.map((l) => ({ sku: "BK-" + l.p, title: "Book " + l.p, qty: l.qty, price: 10 + (l.p % 40) })) })));   // embedded copies
db.ordersRef.insertMany(specs.map(({ lines, ...o }) => ({ ...o, items: lines.map((l) => ({ productId: "BK-" + l.p, qty: l.qty })) })));                                 // references only
console.log("products:", db.products.countDocuments(), "| orders:", db.ordersEmb.countDocuments(), "embedded /", db.ordersRef.countDocuments(), "referenced");

globalThis.revenue = (coll) => coll.aggregate([{ $unwind: "$items" }, { $group: { _id: null, total: { $sum: { $multiply: ["$items.qty", "$items.price"] } } } }]).toArray()[0].total;
```

```text
products: 500 | orders: 10000 embedded / 10000 referenced
```

## Embed: เก็บไว้ด้วยกัน

order แบบ embed มีรายการของมันอยู่ในตัว document จึงเป็นคำตอบครบของ "แสดง order นี้" (ดูตัวอย่าง `ordersEmb` ในบทก่อน) ข้อดีคือ **read locality**: อ่านครั้งเดียว ไม่ต้อง join ข้อมูลที่ embed ยังเปลี่ยนแบบ atomic ไปกับตัวแม่: คู่มือระบุว่า "write operations are atomic on the single-document level, even if modifying multiple values" ([atomicity](https://www.mongodb.com/docs/manual/core/write-operations-atomicity/), ตรวจ 2026-09-30) `updateOne` เดียวที่เปลี่ยนจำนวนของรายการและสถานะ:

```js
// mongosh/evr-atomic.js
db.scratch.insertOne(db.ordersEmb.findOne({ _id: "order_1" }));                                   // work on a copy so later totals stay untouched
const before = db.scratch.findOne({ _id: "order_1" });
const r = db.scratch.updateOne({ _id: "order_1" }, { $set: { status: "returned" }, $inc: { "items.0.qty": 1 } });   // two changes, one document: one atomic write
const after = db.scratch.findOne({ _id: "order_1" });
console.log({ matched: r.matchedCount, modified: r.modifiedCount }, "| items.0.qty", before.items[0].qty, "->", after.items[0].qty, "| status", before.status, "->", after.status);
assert.strictEqual(r.modifiedCount, 1);
```

```text
{ matched: 1, modified: 1 } | items.0.qty 3 -> 4 | status shipped -> returned
```

ต้นทุนคือ **ข้อมูลซ้ำ** (title และราคาเป็นสำเนา) และ **การโตของ document** (ทุกรายการที่ embed ทำให้ order ใหญ่ขึ้น และ array ที่โตไม่หยุดจะชนเพดาน 16 MiB - ดูบทถัดไป)

## Reference: แยกไว้

เมื่อ reference ตัวแม่เก็บแค่ identifier และข้อมูลจริงอยู่ครั้งเดียวใน collection ของมันเอง ไม่มีข้อมูลซ้ำและ order เล็ก ต้นทุนเป็นภาพสะท้อนของ embed - การ resolve id ต้อง **ค้นครั้งที่สอง** ไม่ว่าในโค้ดแอปหรือด้วย `$lookup` คำถามรายได้รวมเดียวกัน ตอบจากแต่ละรูปแบบ (แท็บ Node.js resolve สินค้าของหนึ่ง order ด้วย `$lookup`):

## สำเนาเลื่อนไหล - และบางครั้งควรเป็นเช่นนั้น

ทีนี้ราคาแคตตาล็อกของ `BK-7` เปลี่ยนจาก 17 เป็น 99:

```js
// mongosh/evr-drift.js
const line = (c, p) => db[c].aggregate([{ $match: { "items.sku": p } }, { $count: "orders" }]).toArray()[0]?.orders;
console.log("orders containing BK-7 (embedded):", db.ordersEmb.countDocuments({ "items.sku": "BK-7" }), "| (referenced):", db.ordersRef.countDocuments({ "items.productId": "BK-7" }));
console.log("catalogue price before:", db.products.findOne({ _id: "BK-7" }).price);
db.products.updateOne({ _id: "BK-7" }, { $set: { price: 99 } });                               // the catalogue price changes
console.log("catalogue price after :", db.products.findOne({ _id: "BK-7" }).price);
console.log("an embedded order still shows :", db.ordersEmb.findOne({ "items.sku": "BK-7" }).items.find((i) => i.sku === "BK-7").price, "(its copy did not change)");
console.log("a referenced order resolves to :", db.products.findOne({ _id: "BK-7" }).price, "(one place to update)");
```

```text
orders containing BK-7 (embedded): 69 | (referenced): 69
catalogue price before: 17
catalogue price after : 99
an embedded order still shows : 17 (its copy did not change)
a referenced order resolves to : 99 (one place to update)
```

รูปแบบ reference ตามแคตตาล็อกทันที - เปลี่ยนแค่ document เดียว สำเนาที่ embed ยังเป็น 17 นั่นเป็นบั๊กหรือไม่ขึ้นกับข้อมูล: ราคา *ปัจจุบัน* ของสินค้าควร reference แต่ราคา *ที่จ่ายใน order* เป็นข้อเท็จจริงในอดีต และสำเนาที่ embed คือ snapshot ที่คุณต้องการพอดี การเขียนทับคือบั๊ก:

กฎเบื้องต้นที่ใช้ได้: embed ข้อมูลที่ **อ่านด้วยกัน เขียนด้วยกัน และมีขนาดจำกัด**; reference ข้อมูลที่ **ใหญ่ ใช้ร่วมกันหลายแม่ อัปเดตบ่อยด้วยตัวเอง หรือจำนวนไม่จำกัด**

**In Compass:** เปิดแท็บ **Schema** ของ collection: Compass สุ่มตัวอย่าง document เพื่อแสดง field ที่มี ชนิด และความถี่ของ array และ object ซ้อน - วิธีเร็วที่จะดูว่าจริง ๆ คุณ embed หรือ reference

## เคล็ดลับและข้อควรระวัง

- การ embed ให้การเขียนแบบ atomic ฟรี: แม่และลูกที่ embed เปลี่ยนในการดำเนินการเดียว
- การ reference เก็บข้อมูลที่ใช้ร่วมกันไว้ที่เดียว - อัปเดตแล้วเห็นทุกที่ - แต่ทุกการอ่านที่ต้องใช้มันต้องจ่ายค่าค้น (324 ms เทียบ 26 ms ข้างบน)
- ผสมทั้งสอง: embed snapshot เล็ก ๆ ที่แสดงเสมอ และเก็บ reference ไปยังเรคคอร์ดเต็ม
- ถามทุกสำเนาที่ embed: เป็น snapshot (เก็บไว้) หรือกระจกเงา (ต้องซิงก์)
- array ที่มีแต่โตคือวิธีที่พบบ่อยที่สุดที่การตัดสินใจ embed กลายเป็นปัญหา

<Callout title="embed สิ่งที่อ่านด้วยกัน">
สัญญาณชัดที่สุดของการ embed คือการเข้าถึงร่วมกัน: ถ้าแอปแทบทุกครั้งอ่านข้อมูลสองส่วนด้วยกัน และลูกมีขอบเขตและเป็นของแม่เพียงตัวเดียว ให้ embed ถ้าข้อมูลใช้ร่วมกัน ใหญ่ หรือโตไม่จำกัด ให้ reference แทน

```js
// mongosh/evr-bug.js
const total = () => +revenue(db.ordersEmb).toFixed(2);
const revenueBefore = total();
const order = db.ordersEmb.findOne({ "items.sku": "BK-7" });
const oldTotal = order.items.reduce((n, i) => n + i.qty * i.price, 0);
// AI: "keep embedded prices consistent with the catalogue" (the catalogue price of BK-7 is now 99)
const r = db.ordersEmb.updateMany({ "items.sku": "BK-7" }, { $set: { "items.$[i].price": 99 } }, { arrayFilters: [{ "i.sku": "BK-7" }] });
const newTotal = db.ordersEmb.findOne({ _id: order._id }).items.reduce((n, i) => n + i.qty * i.price, 0);
console.log({ ordersRewritten: r.modifiedCount, revenueBefore, revenueAfter: total() });
console.log("one past order:", order._id, "was worth", oldTotal, "and is now", newTotal);
assert.notStrictEqual(revenueBefore, total());
```

## Mental Model

ถามว่าแต่ละ field *มีความหมายว่าอะไร* ถ้าหมายถึง "ค่าปัจจุบันของสิ่งที่อยู่ที่อื่น" ให้ reference ถ้าหมายถึง "ค่า ณ ขณะที่ document นี้ถูกสร้าง" ให้ embed - มันเป็นข้อเท็จจริงของ document นี้ และสำเนาคือประเด็น จากนั้นตรวจขอบเขต: embed เฉพาะสิ่งที่ไม่โตไม่จำกัด

## ข้อแลกเปลี่ยน

| กรณี | ข้อดีของตัวเลือกที่แนะนำ | ต้นทุน |
|---------|---------|------|
| 1:1 (ผู้ใช้ + โปรไฟล์) - embed | อ่านครั้งเดียว เขียนแบบ atomic | document ใหญ่ขึ้น; แยกทีหลังยากขึ้น |
| 1:many จำกัด (โพสต์ + tag) - embed | เร็ว ง่าย ไม่มี join | ต้องมั่นใจว่าขอบเขตจริง |
| 1:many ไม่จำกัด (ผู้ใช้ + โพสต์) - reference จากฝั่งลูก | ตัวแม่เล็กเสมอ; ลูกแบ่งหน้าได้อิสระ | query ที่สอง; ไม่มีการเขียน atomic ข้ามแม่และลูก |
| ราคาที่จ่ายใน order - embed snapshot | ประวัติยังจริง; สแกน 26 ms | ไม่ตามแคตตาล็อก (โดยออกแบบ) |
| many:many - array ของ id ทั้งสองฝั่ง | อ่านเร็วทั้งสองทิศทาง | เขียนสองเท่า; ต้องรักษาสองฝั่งให้ตรงกัน |

## Common Misconceptions

- **"embed เร็วกว่าเสมอ"** - เฉพาะเมื่อ array มีขอบเขต; array ที่ไม่จำกัดทำให้ทุกการอ่านและเขียนช้าลง (ดูบทถัดไป มีตัวเลข)
- **"`$lookup` ไม่มีกลยุทธ์ join"** - explain รายงาน IndexedLoopJoin
- **"สำเนา embed ที่ล้าสมัยเป็นบั๊กเสมอ"** - ราคาที่จ่ายใน order คือประวัติ; การซิงก์เขียนทับ 69 order
- **"กฎเดียวใช้ได้ทุกความสัมพันธ์"** - ตัดสินแต่ละอันจากรูปแบบการเข้าถึงและการเติบโต

> ตัวอย่างจากของจริง
>
> แนวทางการออกแบบข้อมูลในคู่มือ MongoDB วางกรอบการตัดสินใจเดียวกัน: embed เมื่อ "Your application queries pieces of information together" และ reference เมื่อ "Your embedded data grows without bounds" หรือ "Data duplication is too complicated to manage and not preferred" ([Embedded Data Versus References](https://www.mongodb.com/docs/manual/data-modeling/concepts/embedding-vs-references/), ตรวจ 2026-09-30)

ทุกความสัมพันธ์เข้ากับหนึ่งในสามรูปแบบตาม **cardinality** - จำนวนของสิ่งหนึ่งที่สัมพันธ์กับจำนวนของอีกสิ่ง ผู้ใช้มีโปรไฟล์หนึ่งอัน (one-to-one) ผู้ใช้เขียนหลายโพสต์ (one-to-many) นักเรียนลงหลายคอร์สและคอร์สมีหลายนักเรียน (many-to-many) ใน relational database รูปแบบกำหนดกลไก: foreign key และ join table ใน MongoDB รูปแบบเพียงจำกัดตัวเลือก คุณยังเลือก embed หรือ reference สำหรับแต่ละอันโดยใช้ข้อแลกเปลี่ยนจากบทก่อน

บทนี้เตรียมข้อมูลของตัวเอง: `users` 1 000 รายการที่มี `profile` แบบ embed, `posts` 20 000 รายการที่อ้าง author และ collection เล็ก ๆ `students` / `courses` จับจาก mongo 8.3.11, mongosh 2.11.1 และ Node driver 7.7.0 บน Mac เครื่องเดียว (ตัวอย่าง transaction ต้องใช้ container replica set จากบท setup); แท็บ Python, Go และ Rust ถูกรันอย่างละครั้งในโปรแกรม scratch

## One-to-one

เมื่อ document หนึ่งสัมพันธ์กับอีกอันเพียงอันเดียว การ embed มักเป็นทางที่เป็นธรรมชาติ - ข้อมูลที่เกี่ยวข้องมีขอบเขต เป็นของแม่ตัวเดียว และอ่านไปพร้อมกัน ผู้ใช้และโปรไฟล์กลายเป็น document เดียว:

export const oneToOneDiagram = `flowchart LR
  U["User document"] --> P["profile sub-object embedded inside"]`

แยก one-to-one ก็ต่อเมื่อส่วนที่เกี่ยวข้องใหญ่ ไม่ค่อยถูกอ่าน หรือเข้าถึงแยกต่างหาก - เช่นไบนารีขนาดใหญ่หรือบล็อก audit ใน collection ของมัน เพื่อให้ document ที่ใช้บ่อยเล็ก

## One-to-many

กับแม่หนึ่งและลูกจำนวนมาก มีสองรูปแบบที่ดี ถ้าลูกมีน้อยและจำกัด **embed เป็น array**: tag สามอันของโพสต์คือ embed ที่สะอาด เมื่อฝั่ง "many" โตได้หรือถูก query แยก **reference จากฝั่งลูก**: โพสต์แต่ละอันเก็บ `authorId` reference นั้นต้องมี index ไม่เช่นนั้นการแสดงโพสต์ของผู้ใช้จะสแกนทุกโพสต์:

## Many-to-many

แต่ละฝั่งสัมพันธ์กับหลายรายการของอีกฝั่ง - นักเรียนและคอร์ส แนวทางที่สะอาดคือ **reference ด้วย array ของ id** ฝั่งเดียวหรือสองฝั่ง array บนฝั่งที่อ่านคือหนึ่งการเขียนต่อการลงทะเบียน array ทั้ง **สองฝั่ง** ทำให้อ่านเร็วทั้งสองทิศทางแต่ทุกการลงทะเบียนเป็นสองการเขียนที่ต้องสำเร็จด้วยกัน - ไม่เช่นนั้น crash ระหว่างทางทิ้งข้อมูลที่ไม่สอดคล้องดังที่ครึ่งแรกของการรันนี้แสดง multi-document transaction (ครึ่งหลัง และแท็บ Node.js) แก้ได้:

## ขีดจำกัด 16 MiB และ array ที่ไม่จำกัด

ทุก document มีเพดานตายตัว 16 mebibyte ([limits](https://www.mongodb.com/docs/manual/reference/limits/), ตรวจ 2026-09-30) เพียงพอสำหรับข้อมูลปกติ แต่ทำให้ embed กลายเป็นกับดักเมื่อ array ไม่มีขอบเขตตามธรรมชาติ ที่นี่ห้องแชต `$push` ข้อความขนาด 8 KB ลง document เดียว ที่แต่ละจุดตรวจเราวัดเวลาของ `$set` *เล็ก ๆ* ของ field ที่ไม่เกี่ยวข้อง:

```js
// mongosh/rel-16mb.js
db.rooms.insertOne({ _id: "room1", messages: [] });
const pad = "x".repeat(8000), size = () => db.rooms.aggregate([{ $match: { _id: "room1" } }, { $project: { b: { $bsonSize: "$$ROOT" } } }]).toArray()[0].b;
const marks = [1, 100, 500, 1000, 1500, 2000], rows = [];
let n = 0, err = null;
for (;;) {
  try { db.rooms.updateOne({ _id: "room1" }, { $push: { messages: { n, text: pad } } }); } catch (e) { err = "code " + e.code + ": " + e.message.slice(e.message.indexOf("Resulting")); break; }
  n++;
  if (marks.includes(n)) {                                   // time a tiny update ($set one field) on the document as it is now
    const t = Date.now(); for (let i = 0; i < 5; i++) db.rooms.updateOne({ _id: "room1" }, { $set: { lastActive: i } });
    rows.push({ pushes: n, docMB: +(size() / 1048576).toFixed(2), msPerTinyUpdate: (Date.now() - t) / 5 });
  }
}
console.log(rows);
console.log("first failure after", n, "pushes ->", err);
assert.ok(err.includes("16777216"));
```

```text
[
  { pushes: 1, docMB: 0.01, msPerTinyUpdate: 1.4 },
  { pushes: 100, docMB: 0.77, msPerTinyUpdate: 1 },
  { pushes: 500, docMB: 3.83, msPerTinyUpdate: 3.2 },
  { pushes: 1000, docMB: 7.66, msPerTinyUpdate: 5.8 },
  { pushes: 1500, docMB: 11.48, msPerTinyUpdate: 6.4 },
  { pushes: 2000, docMB: 15.31, msPerTinyUpdate: 7.6 }
]
first failure after 2089 pushes -> code 10334: Resulting document after update is larger than 16777216
```

ก่อนจะเกิด error ใด ๆ update เล็กตัวเดิมช้าลงราว **ราวห้าเท่า** (1.4 ms ที่ 0.01 MB เป็น 7.6 ms ที่ 15.3 MB) เพราะ server เขียน document ที่ใหญ่ขึ้นเรื่อย ๆ ใหม่ทุกครั้งที่เปลี่ยน - document ไม่ได้ "ย้าย" จริง ๆ (นั่นคือ storage engine MMAPv1 รุ่นเก่า); WiredTiger เขียนเวอร์ชันใหม่ของมัน push ครั้งที่ 2 090 ชนกำแพงด้วย `Resulting document after update is larger than 16777216` ทางแก้คือ reference ข้อความจากฝั่งลูก เหมือนในหัวข้อ one-to-many:

```js
// mongosh/rel-16mb-fix.js
db.roomMessages.createIndex({ roomId: 1, n: -1 });
const pad = "x".repeat(8000);
db.roomMessages.insertMany(Array.from({ length: 2100 }, (_, n) => ({ roomId: "room2", n, text: pad })));       // more than the array version could hold
const t = Date.now(); for (let i = 0; i < 5; i++) db.rooms.updateOne({ _id: "room2" }, { $set: { lastActive: i } }, { upsert: true });
console.log("room document stays tiny; tiny update:", (Date.now() - t) / 5, "ms");
console.log("last 20 messages:", plan(db.roomMessages.find({ roomId: "room2" }).sort({ n: -1 }).limit(20)));
console.log("messages stored:", db.roomMessages.countDocuments({ roomId: "room2" }), "(no per-document ceiling)");
```

```text
room document stays tiny; tiny update: 1.4 ms
last 20 messages: LIMIT > FETCH > IXSCAN(roomId_1_n_-1)  returned=20 keys=20 docs=20
messages stored: 2100 (no per-document ceiling)
```

document ของห้องเล็กเสมอ การอัปเดตเสียเท่ากับวันแรก และ 20 ข้อความล่าสุดคือการอ่าน index 20 key ก่อนถึง 16 MiB นานแล้ว การโตคือศัตรู ไม่ใช่แค่เพดาน; รูปแบบ Bucket (บทถัดไป) คือทางสายกลางเมื่อต้องการหลายรายการต่อ document แต่จำกัดขนาดแต่ละอัน

## เคล็ดลับและข้อควรระวัง

- cardinality จำกัดตัวเลือก; การเข้าถึงและการเติบโตเป็นตัวตัดสิน
- one-to-one เกือบทั้งหมด embed; ส่วนย่อยที่ใหญ่หรือไม่ค่อยอ่านอาจมี collection ของตัวเอง
- สำหรับ one-to-many ถามว่า "ฝั่ง many โตไม่จำกัดได้ไหม" ถ้าได้ ให้ reference จากฝั่งลูกและทำ index ให้ reference
- many-to-many แบบ reference สองฝั่งเสียสองการเขียนต่อการเปลี่ยน; ใช้ transaction และเฉพาะเมื่อสองทิศทางร้อนทั้งคู่
- ประสิทธิภาพเสื่อมก่อนถึง 16 MiB นานแล้ว (update เล็กช้าลงราว 5 เท่าที่ 15 MB ที่นี่)

<Callout title="cardinality จำกัด; การเข้าถึงตัดสิน">
ให้รูปทรงของความสัมพันธ์ตัดตัวเลือกที่ผิดชัดเจนออก แล้วให้รูปแบบการเข้าถึงและคำถามเรื่องการเติบโตเลือกจากที่เหลือ อย่า embed array ที่ไม่มีขีดจำกัดตามธรรมชาติ - นั่นคือวิธีที่การตัดสินใจ embed กลายเป็นหน้าผา 16 MiB
</Callout>

## Mental Model

ถามทุกฝั่ง "many": มีค่าสูงสุดตามธรรมชาติที่ระบุชื่อได้ไหม tag ต่อโพสต์: มี, embed ข้อความต่อห้อง: ไม่มี, reference การลงทะเบียน: ไม่จำกัดทั้งสองฝั่ง จึง reference และตัดสินว่าอ่านทิศทางไหน ขอบเขตที่คุณระบุไม่ได้คือขอบเขตที่คุณไม่มี

## ข้อแลกเปลี่ยน

| รูปแบบ | ข้อดี | ต้นทุน |
|---------|---------|------|
| embed แบบ one-to-few | อ่านครั้งเดียว; เขียนแบบ atomic | ปลอดภัยเฉพาะเมื่อจำนวนลูกมีขอบเขตจริง |
| one-to-many, reference จากฝั่งลูก | ตัวแม่เล็กเสมอ; อ่านหน้า 10 key ด้วย index | ต้อง query ที่สอง; ต้องมี index บน reference |
| many-to-many, array ทั้งสองฝั่ง | อ่านเร็วทั้งสองทาง ไม่ต้อง `$lookup` | สองการเขียนต่อการเปลี่ยน; ต้องใช้ transaction เพื่อความสอดคล้อง |
| array ที่ embed แบบไม่จำกัด | ง่ายตอนแรก | update ช้าลง 5 เท่าที่ 15 MB แล้วล้มเหลวถาวร |

## Common Misconceptions

- **"cardinality ตัดสิน embed หรือ reference"** - มันแค่จำกัด; การเข้าถึงและการเติบโตตัดสิน
- **"รายการที่เล็กวันนี้คือมีขอบเขต"** - ถามว่าโตได้ไหม ไม่ใช่ตอนนี้ใหญ่แค่ไหน
- **"server ย้ายทั้ง document ทุกครั้งที่ update"** - นั่นคือ MMAPv1; WiredTiger เขียนใหม่ และต้นทุนยังโตตามขนาด
- **"array ของ reference ทั้งสองฝั่งฟรี"** - crash ระหว่างสองการเขียนทำให้ไม่ตรงกัน
- **"16 MiB คือปัญหาเดียว"** - update ช้าลง 5 เท่าแล้วที่ 15 MB

> ตัวอย่างจากของจริง
>
> คู่มือ MongoDB ระบุกรณีเดียวกับที่ใช้ที่นี่: reference เมื่อ "Your embedded data grows without bounds" และระบุขีดจำกัดขนาด BSON document 16 mebibyte ที่ตายตัว ([Embedded Data Versus References](https://www.mongodb.com/docs/manual/data-modeling/concepts/embedding-vs-references/); [limits](https://www.mongodb.com/docs/manual/reference/limits/), ตรวจ 2026-09-30)

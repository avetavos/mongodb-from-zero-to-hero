การเรียก `find` ตอบคำถามได้แบบเดียว: "คืน document ที่ตรงกับฟิลเตอร์นี้กลับมาให้ฉัน" ซึ่งเพียงพอสำหรับการอ่านข้อมูล แต่มันไม่สามารถ *สรุป* ข้อมูลเหล่านั้นได้ มันบอกคุณไม่ได้ว่าค่าเฉลี่ย rating ต่อ genre เป็นเท่าไร ลูกค้าแต่ละคนสั่งซื้อกี่ครั้ง หรือหนังสือสามอันดับขายดีที่สุดเมื่อเดือนที่แล้วคืออะไร สำหรับคำถามที่ต้องยุบ document จำนวนมากให้กลายเป็นคำตอบที่เล็กลงและถูกจัดรูปใหม่ MongoDB มอบ **aggregation pipeline** ให้คุณ

pipeline เป็นแนวคิดที่ทรงพลังที่สุดใน MongoDB รองจากตัว document เอง ลองนึกภาพสายพานลำเลียง: document ของคุณเข้ามาทางปลายด้านหนึ่ง ไหลผ่านชุดของ **stage** แล้วสตรีมที่ถูกแปลงแล้วออกมาทางปลายอีกด้าน แต่ละ stage รับ document ที่ส่งมาให้ ทำงานหนึ่งอย่างที่นิยามไว้ชัดเจน แล้วส่งผลลัพธ์ต่อไปยัง stage ถัดไป ลำดับเป็นสิ่งที่คุณเลือกได้ และลำดับนั้นสำคัญ — stage หนึ่งจะเห็นเฉพาะสิ่งที่ stage ก่อนหน้ามันผลิตออกมาเท่านั้น

เราจะทำงานกับชุดข้อมูลเล็ก ๆ ที่สมมติขึ้นตลอดทั้งโมดูลนี้: collection `sales` ของออเดอร์หนังสือในร้านในจินตนาการ การทำให้ข้อมูลมีขนาดเล็กช่วยให้ *รูปร่าง* ของการแปลงแต่ละครั้งโดดเด่นชัดเจน

## pipeline คือลิสต์ของ stage

คุณส่ง **array** ของออบเจกต์ stage ให้กับ aggregation แต่ละ stage ถูกตั้งชื่อด้วยคีย์ที่นำหน้าด้วย `$` — `$match`, `$group`, `$sort` เป็นต้น นี่คือรูปแบบมาตรฐาน: ฟิลเตอร์สตรีม ยุบมันเข้ากลุ่ม แล้วเรียงลำดับผลลัพธ์

array ของ stage ชุดเดียวกันนี้คือสิ่งที่คุณส่งเข้าไปในทุกภาษา สังเกตว่าการเรียกคือ `aggregate` และอาร์กิวเมนต์คือ pipeline:

**ใน Compass:** เปิด collection แล้วคลิกแท็บ **Aggregations** ตัวสร้าง pipeline ให้คุณเพิ่มทีละ stage จาก dropdown แก้ไขเนื้อหาของมัน และดูตัวอย่าง document ที่ไหลออกจากแต่ละ stage แบบสดในตัวอย่างข้อมูล — นี่เป็นวิธีที่ดีที่สุดในการ *เฝ้าดู* สายพานลำเลียงทำงาน

## ต่างจาก find อย่างไร

`find` ฟิลเตอร์และ project แต่มันจะคืนสับเซตของ document *ต้นฉบับ* ของคุณเสมอ aggregation ทำแบบนั้นได้เช่นกัน แต่มันยังสามารถสร้าง document ใหม่ทั้งหมดขึ้นมาได้ด้วย: จำนวนนับ ค่าเฉลี่ย ระเบียนที่ join แล้ว อาร์เรย์ที่แบนราบ อะไรก็ตามที่ `find` ทำได้ aggregation ก็ทำได้ด้วย `$match` และ `$project` แต่ในทางกลับกันไม่จริง

- `find` อ่าน document ออกมา; aggregation **จัดรูปสตรีม** ของ document ใหม่
- `find` คืน document ที่มีอยู่แล้ว; aggregation สามารถ **สังเคราะห์** document ใหม่ขึ้นมาได้
- pipeline เป็นสิ่งที่ **เรียงลำดับและประกอบกันได้** — คุณเรียงซ้อน stage เหมือนต่อ Lego และเพิ่มได้เรื่อย ๆ

## โมดูลนี้ครอบคลุมอะไรบ้าง

บทเรียนข้างหน้าจะแนะนำ stage ที่คุณจะหยิบมาใช้บ่อยที่สุด ทีละแนวคิด:

1. **Pipeline basics** — `$match` เพื่อฟิลเตอร์ตั้งแต่เนิ่น ๆ และ `$project` เพื่อจัดรูปใหม่ และทำไมลำดับของ stage จึงเปลี่ยนทั้งความถูกต้องและความเร็ว
2. **Group and accumulators** — `$group` พร้อม `$sum`, `$avg`, `$min`, `$max`, `$push` และพวกพ้อง บวกกับยอดรวมทั้งหมด
3. **Lookup joins** — `$lookup` เพื่อดึง document ที่เกี่ยวข้องจาก collection อื่น
4. **Unwind arrays** — `$unwind` เพื่อเปลี่ยนหนึ่ง document ที่มีอาร์เรย์ให้กลายเป็นหลาย document
5. **Facets and buckets** — `$facet` สำหรับหลายคำตอบในการประมวลผลครั้งเดียว และ `$bucket` สำหรับการจัดกลุ่มแบบฮิสโทแกรม

<Callout title="แบบจำลองความคิด">
aggregation pipeline คือ array ของ stage document เข้ามา แต่ละ stage แปลงสตรีมและส่งต่อ และผลลัพธ์ของ stage สุดท้ายคือผลลัพธ์ของคุณ ลองคิดถึงมันเหมือนสายพานลำเลียง ไม่ใช่เคียวรีเดี่ยว ๆ
</Callout>

## Trade-offs

| ตัวเลือก | Benefit | Cost |
|---------|---------|------|
| aggregation pipeline | คำนวณและสรุปข้อมูลฝั่ง server ลดข้อมูลที่ต้องส่งผ่านเครือข่าย | pipeline อ่านยากกว่า query ธรรมดา และ debug ทีละ stage ต้องใช้เวลา |
| find + ประมวลผลใน application code | เขียนง่าย เข้าใจง่าย เหมาะกับ logic ที่ซับซ้อนซึ่งยากจะแสดงเป็น stage | ต้องดึง document ทั้งหมดผ่านเครือข่ายก่อนคำนวณ ทำให้ช้าและกิน memory เมื่อข้อมูลใหญ่ |
| pipeline ที่มีหลาย stage | ประกอบ stage ทีละอันได้ยืดหยุ่น ต่อยอดง่าย | ยิ่งมี stage เยอะ ยิ่งต้องระวังลำดับที่ส่งผลต่อ performance และความถูกต้อง |

## Common Mistakes

- **คิดว่า aggregation pipeline แทน find ได้เสมอ** — ถ้าคุณแค่ต้องการ document ที่ตรง filter โดยไม่ต้องแปลงรูป find ธรรมดาอ่านง่ายกว่าและมักเร็วพอ ๆ กัน ใช้ pipeline เมื่อคุณต้องสรุปหรือสร้าง document ใหม่จริง ๆ
- **มองว่า stage แต่ละตัวเห็น collection ต้นฉบับ** — ทุก stage เห็นเฉพาะผลลัพธ์ของ stage ก่อนหน้า ไม่ใช่ collection ทั้งก้อน ถ้า stage ก่อนหน้าทิ้งฟิลด์ไป stage ถัดมาจะอ้างฟิลด์นั้นไม่ได้
- **ลืมว่า pipeline คือ array ที่ลำดับสำคัญ** — สลับตำแหน่ง stage สองตัวอาจให้ผลลัพธ์คนละแบบ หรือช้าลงมาก ไม่ใช่แค่เรื่อง style การจัดเรียง

> 💡 Real World Example
>
> **Analytics dashboard ทั่วไป** — หน้า dashboard ที่ต้องแสดงยอดขายรวม ยอดขายแยกตามหมวด และ top product ในคำขอเดียว มักใช้ aggregation pipeline (`$group`, `$facet`) แทนการดึง document ทั้งหมดมาคำนวณใน backend เพราะลด round-trip และภาระของ application server
>
> **Keller Williams (real estate)** — ระบบรายงานอสังหาริมทรัพย์ที่ต้องสรุปยอดขาย นายหน้า และพื้นที่ ใช้ aggregation pipeline เพื่อคำนวณสรุปจากข้อมูลธุรกรรมจำนวนมากฝั่ง server แทนที่จะย้ายข้อมูลดิบทั้งหมดมาประมวลผลที่ application layer

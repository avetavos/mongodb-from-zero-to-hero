MongoDB เก็บข้อมูลที่เกี่ยวข้องกันไว้ใน collection แยกกันบ่อยพอที่บางครั้งคุณจะต้องเย็บสอง collection กลับเข้าด้วยกัน stage `$lookup` join นั้นภายใน aggregation pipeline: สำหรับแต่ละ document ที่เข้ามา มันค้นหา document ที่ตรงกันในอีก collection หนึ่ง แล้วแนบเข้ามาเป็นฟิลด์ **array** มันคือ left outer join — ทุก document อินพุตจะผ่านมา พร้อม array ว่างเมื่อไม่มีอะไรตรงกัน

เราเพิ่ม collection ที่สองเข้ามาในร้าน นอกจาก `sales` แล้ว ตอนนี้มี collection `books` ที่อธิบายแต่ละชื่อเรื่อง:

```json
{ "_id": "Dune", "author": "Frank Herbert", "pages": 412, "year": 1965 }
```

ออเดอร์ใน sales อ้างถึงหนังสือด้วย `title` ของมัน:

```json
{ "_id": "a1", "title": "Dune", "quantity": 3, "price": 12 }
```

## รูปแบบความเท่ากัน: localField และ foreignField

`$lookup` แบบที่ง่ายที่สุดจับคู่ฟิลด์ในเครื่องหนึ่งฟิลด์กับฟิลด์ต่างถิ่นหนึ่งฟิลด์ คุณระบุชื่อ collection ที่จะ join (`from`) ฟิลด์บน document ที่เข้ามา (`localField`) ฟิลด์บน document ต่างถิ่น (`foreignField`) และชื่อของฟิลด์ array ที่จะเพิ่ม (`as`)

ตอนนี้ document sales แต่ละอันพา array `book` ที่เก็บ document book ที่ตรงกัน:

```json
[
  {
    "_id": "a1",
    "title": "Dune",
    "quantity": 3,
    "price": 12,
    "book": [
      { "_id": "Dune", "author": "Frank Herbert", "pages": 412, "year": 1965 }
    ]
  }
]
```

ผลลัพธ์เป็น **array เสมอ** แม้ว่าจะมี document ตรงกันอย่างมากที่สุดเพียงหนึ่งอัน เพราะโดยทั่วไปการ join อาจตรงกันหลายอัน ขั้นถัดไปที่พบบ่อยคือ `$unwind` (บทเรียนถัดไป) เพื่อแบน array หนึ่งสมาชิกนั้นให้เป็นออบเจกต์ธรรมดา

**ใน Compass:** แท็บ **Aggregations** มี `$lookup` ให้เลือกจาก dropdown และให้คุณเลือก collection ต่างถิ่นและฟิลด์ด้วยช่องกรอกฟอร์ม การดูตัวอย่างแสดงฟิลด์ array ใหม่ที่ถูกต่อท้ายแต่ละ document ซึ่งทำให้พฤติกรรม "join แนบ array" เป็นรูปธรรม

## รูปแบบ pipeline สำหรับ join ที่ซับซ้อนขึ้น

เมื่อคุณต้องการมากกว่าความเท่ากันของฟิลด์เดียว — ฟิลเตอร์ document ต่างถิ่น project พวกมัน หรือจับคู่ตามหลายเงื่อนไข — ให้ใช้ **รูปแบบ pipeline** คุณประกาศตัวแปร `let` จาก document ในเครื่องและรัน sub-pipeline กับ collection ต่างถิ่น โดยเปรียบเทียบด้วย `$expr` ที่นี่เราแนบเฉพาะหนังสือที่ตีพิมพ์หลังปี 1950 โดยเปิดเผยแค่ author และ year:

<Tabs syncKey="lang">
  <TabItem label="mongosh">
    ```js
    db.sales.aggregate([
      { $lookup: {
          from: "books",
          let: { t: "$title" },
          pipeline: [
            { $match: { $expr: { $eq: ["$_id", "$$t"] } } },
            { $match: { year: { $gt: 1950 } } },
            { $project: { _id: 0, author: 1, year: 1 } }
          ],
          as: "book"
      } }
    ])
    ```
  </TabItem>
  <TabItem label="Node.js">
    ```js
    const rows = await db.collection("sales").aggregate([
      { $lookup: {
          from: "books",
          let: { t: "$title" },
          pipeline: [
            { $match: { $expr: { $eq: ["$_id", "$$t"] } } },
            { $match: { year: { $gt: 1950 } } },
            { $project: { _id: 0, author: 1, year: 1 } },
          ],
          as: "book",
      } },
    ]).toArray();
    ```
  </TabItem>
  <TabItem label="Python">
    ```python

                {"$match": {"$expr": {"$eq": ["$_id", "$$t"]}}},

        }},
    ]))
    ```
  </TabItem>

            {"from", "books"},

ตอนนี้ array ที่แนบมาเก็บเฉพาะ document ต่างถิ่นที่ถูกตัดทอนและกรองแล้ว:

```json
[
  {
    "_id": "a1",
    "title": "Dune",
    "quantity": 3,
    "price": 12,
    "book": [ { "author": "Frank Herbert", "year": 1965 } ]
  }
]
```

สังเกตไวยากรณ์ `$$t`: `$` ตัวเดียวอ้างถึงฟิลด์ของ document ต่างถิ่น ส่วน `$$` อ้างถึงตัวแปร `let` ที่พามาจาก document ในเครื่อง

## ทิปและกับดัก

- `$lookup` รันเคียวรีกับ collection ต่างถิ่นสำหรับทุก document อินพุต **สร้าง index บน `foreignField`** (หรืออะไรก็ตามที่ sub-pipeline จับคู่ด้วย) ไม่เช่นนั้นการ join อาจช้าลงเมื่อขนาดข้อมูลในโลกจริง
- มันคือ left outer join: document อินพุตที่ไม่มีคู่ตรงกันก็ยังผ่านมา พร้อม array `as` ว่าง ฟิลเตอร์พวกนั้นทิ้งภายหลังด้วย `$match` ถ้าคุณต้องการเฉพาะแถวที่ join แล้ว
- การ join ทรงพลังแต่ไม่ฟรี ถ้าคุณพบว่าตัวเองกำลัง join สอง collection เดิมในทุกการอ่าน นั่นอาจเป็นสัญญาณว่าข้อมูลอยากถูก **ฝัง** (embedded) มากกว่าถูกอ้างอิง — เป็นคำถามเรื่องการออกแบบข้อมูลที่จะกล่าวถึงในภายหลัง
- ฟิลด์ผลลัพธ์ที่ตั้งชื่อใน `as` เป็น array เสมอ จับคู่ `$lookup` กับ `$unwind` เมื่อคุณคาดว่าจะตรงกันอันเดียวและต้องการออบเจกต์แบนราบ

<Callout title="lookup แนบ array">
$lookup คือ left outer join ที่แขวน document ต่างถิ่นที่ตรงกันไว้บนฟิลด์ array ใหม่ รูปแบบความเท่ากัน join หนึ่งฟิลด์กับหนึ่งฟิลด์ ส่วนรูปแบบ pipeline ให้คุณฟิลเตอร์และจัดรูปฝั่งต่างถิ่นใหม่ได้ สร้าง index บนฟิลด์ต่างถิ่น เพราะการ join เคียวรีมันหนึ่งครั้งต่อ document อินพุต
</Callout>

## Trade-offs

| ตัวเลือก | Benefit | Cost |
|---------|---------|------|
| `$lookup` (อ้างอิงข้ามหลาย collection) | ข้อมูลไม่ซ้ำซ้อน อัปเดตที่เดียว แชร์ข้อมูลระหว่าง document ได้ | ทุกครั้งที่อ่านต้องเสีย cost ของการ join เพิ่มงานให้ query engine ต่อ document อินพุตแต่ละตัว |
| Embedding (ฝังข้อมูลไว้ใน document เดียว) | อ่านครั้งเดียวจบ ไม่ต้อง join เลย เร็วที่สุดสำหรับ read-heavy workload | ข้อมูลซ้ำซ้อนถ้าถูกอ้างจากหลายที่ อัปเดตต้องไล่แก้หลาย document และ document อาจโตจนเกิน limit |
| รูปแบบ pipeline ของ `$lookup` (`let` + sub-pipeline) | ฟิลเตอร์/จัดรูป document ต่างถิ่นได้ก่อน join จับคู่ด้วยเงื่อนไขซับซ้อนหลายฟิลด์ได้ | เขียนซับซ้อนกว่า อ่านยากกว่า และปรับ index ให้ sub-pipeline ใช้ได้เต็มที่ยากกว่า |
| รูปแบบความเท่ากันของ `$lookup` (`localField`/`foreignField`) | เขียนสั้น เข้าใจง่าย ปรับ index ตรงไปตรงมา | จับคู่ได้แค่เงื่อนไขเท่ากันเงื่อนไขเดียว ทำอะไรซับซ้อนกว่านั้นไม่ได้ |

## Common Mistakes

- **ไม่สร้าง index บน `foreignField`** — `$lookup` เคียวรี collection ต่างถิ่นให้ทุก document อินพุตหนึ่งครั้ง ถ้าไม่มี index บนฟิลด์ที่จับคู่ การ join จะช้าลงอย่างมากเมื่อข้อมูลโต
- **ลืมว่า `$lookup` เป็น left outer join เสมอ** — document อินพุตที่ไม่มีคู่ตรงกันยังผ่านมาพร้อม array ว่างใน `as` ไม่ใช่ถูกกรองทิ้ง ถ้าต้องการเฉพาะแถวที่ join สำเร็จ ต้องเติม `$match` กรอง array ว่างเอง
- **สับสนระหว่าง `$` กับ `$$` ใน pipeline-style lookup** — `$` ตัวเดียวอ้างถึงฟิลด์ของ document ต่างถิ่นใน sub-pipeline ส่วน `$$` อ้างถึงตัวแปรที่ประกาศด้วย `let` จาก document ในเครื่อง สลับกันแล้ว query จะพังเงียบ ๆ หรือ error

> 💡 Real World Example
>
> **Analytics dashboard** — รายงานยอดขายที่ต้องโชว์ชื่อสินค้าและหมวดหมู่ควบคู่กับตัวเลขยอดขาย มักเก็บ `sales` กับ `products` แยก collection แล้วใช้ `$lookup` join ตอน query แทนที่จะฝังข้อมูลสินค้าไว้ในทุก order เพราะข้อมูลสินค้าเปลี่ยนบ่อยกว่า order
>
> **Keller Williams** — รายงานอสังหาริมทรัพย์ที่ต้อง join ธุรกรรมกับข้อมูลนายหน้าและข้อมูล listing ใช้ `$lookup` แบบ pipeline-style เพื่อกรองเฉพาะธุรกรรมในช่วงเวลาที่ต้องการก่อน join ลดขนาดข้อมูลที่ engine ต้องประมวลผลข้าม collection

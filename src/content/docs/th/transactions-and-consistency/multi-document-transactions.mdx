บางครั้ง operation เดียวต้องเปลี่ยนหลาย document จริง ๆ และต้องสำเร็จทั้งหมดหรือไม่สำเร็จเลย ตัวอย่างตำราคือการโอนเงิน: หักบัญชีหนึ่งและเพิ่มอีกบัญชีหนึ่ง ถ้าการหักสำเร็จแต่การเพิ่มล้มเหลว เงินก็หายไป เมื่อ document ที่เกี่ยวข้องรวมเป็นอันเดียวไม่ได้ — เพราะเป็นบัญชีคนละบัญชี หรืออยู่คนละ collection — MongoDB มี **multi-document transaction** จริง ๆ ให้ มันรับประกัน ACID เต็มรูปแบบข้ามทุก operation ข้างใน: commit พร้อมกันหมด หรือ roll back พร้อมกันหมด

ราคาที่ต้องจ่ายคือ transaction ต้องมี **session** ต้องมี **replica set** (หรือ sharded cluster) และแพงกว่าการเขียนธรรมดา จึงเป็นเครื่องมือที่ใช้อย่างตั้งใจ ไม่ใช่ค่าเริ่มต้น ทุก output ด้านล่างจับจากเครื่อง Mac นี้ บน mongo 8.3.11, mongosh 2.11.1 และ Node driver 7.7.0 แท็บ Python, Go และ Rust สะท้อนการเรียกที่ตรวจแล้วใน shell/Node แต่ไม่ได้ถูกรันโดยตัวตรวจอัตโนมัติของคอร์ส

## เงื่อนไขก่อน: ต้องมี replica set

container `mongo:8` จากบทเรียน setup ที่สตาร์ท **โดยไม่มี** `--replSet` คือ standalone server และ transaction บนมันล้มตั้งแต่การเขียนครั้งแรก output จริงจาก container `mongo:8.3.11` standalone ชั่วคราว (Node driver; mongosh ให้ข้อความเดียวกัน):

```text
MongoServerError: This MongoDB deployment does not support retryable writes. Please add retryWrites=false to your connection string.
```

change stream บน standalone ตัวเดียวกันก็ล้มเหมือนกัน (`MongoServerError 40573: The $changeStream stage is only supported on replica sets or mongos`) ให้สตาร์ท replica set โหนดเดียวแทน — แค่ `--replSet` กับ `rs.initiate()` หนึ่งครั้ง และเป็นสิ่งที่ harness ของคอร์สนี้รันจริง:

```bash
# scripts/replset-one-node.sh
docker run -d --name mongo-rs --memory 1g -p 27017:27017 mongo:8 \
  mongod --replSet rs0 --bind_ip_all --wiredTigerCacheSizeGB 0.5
docker exec mongo-rs mongosh --quiet --eval 'rs.initiate({ _id: "rs0", members: [{ _id: 0, host: "localhost:27017" }] })'
docker exec mongo-rs mongosh --quiet --eval 'db.hello().isWritablePrimary'   # true
```

เชื่อมต่อด้วย `mongodb://localhost:27017/?replicaSet=rs0` (หรือ `directConnection=true`) จากเครื่อง host

## transaction อยู่ใน session

ลำดับเป็นแบบเดียวกันเสมอ คุณเริ่ม **session** แล้วรัน operation ภายใน transaction ที่ผูกกับ session นั้น helper `withTransaction` ของ driver ห่อทั้งหมด: เริ่ม transaction, รัน callback, **commit** ถ้า return ปกติ และ **abort** (roll back ทุกอย่าง) ถ้า throw มัน retry callback เมื่อเจอ `TransientTransactionError` และ retry commit เมื่อเจอ `UnknownTransactionCommitResult` ด้วย จึงควรใช้แทนการ start และ commit เอง

  C -->|"No"| ABORT["Abort — every change is rolled back"]`

## Abort: throw แล้ว roll back ทุกอย่าง

ถ้า callback throw, `withTransaction` จะ abort และไม่มีอะไรใน transaction เหลือรอด ในตัวอย่างนี้การหักสำเร็จภายใน transaction แล้วการเช็คยอดล้มเหลว:

```js
// app/txn-abort.mjs
const accounts = db.collection("accounts");
await accounts.deleteMany({});   // fresh start
await accounts.insertMany([{ name: "Ada", balance: 10 }, { name: "Linus", balance: 4 }]);

const session = client.startSession();
let message = null;
try {
  await session.withTransaction(async () => {
    await accounts.updateOne({ name: "Ada" }, { $inc: { balance: -30 } }, { session });
    const ada = await accounts.findOne({ name: "Ada" }, { session });
    console.log("inside the transaction, Ada sees:", ada.balance);
    if (ada.balance < 0) throw new Error("insufficient funds");
    await accounts.updateOne({ name: "Linus" }, { $inc: { balance: 30 } }, { session });
  });
} catch (e) { message = e.message; }
finally { await session.endSession(); }

const rows = await accounts.find({}, { projection: { _id: 0 } }).toArray();
console.log("error:", message, "| after:", rows);
if (message !== "insufficient funds") throw new Error("expected the callback error");
if (rows.find((r) => r.name === "Ada").balance !== 10) throw new Error("debit should have been rolled back");
```

```text
inside the transaction, Ada sees: -20
error: insufficient funds | after: [ { name: 'Ada', balance: 10 }, { name: 'Linus', balance: 4 } ]
```

ภายใน transaction Ada เห็น −20 แล้ว (transaction อ่านสิ่งที่ตัวเองเขียนได้); ข้างนอกและหลังจากนั้น ไม่มีอะไรเปลี่ยน

## สอง transaction บน document เดียว: write conflict

transaction ที่สองที่แตะ document ซึ่ง transaction อื่นที่ยังเปิดอยู่เขียนไว้แล้ว จะไม่รอ — มันล้มทันทีด้วย `WriteConflict` (code 112) พร้อม error label `TransientTransactionError` ซึ่งหมายความว่า "retry ทั้ง transaction ได้อย่างปลอดภัย" `withTransaction` retry ให้เอง ส่วนลูป `startTransaction` ที่เขียนเองต้องทำเอง:

```js
// app/txn-conflict.mjs
const accounts = db.collection("accounts");
await accounts.deleteMany({});   // fresh start
await accounts.insertOne({ name: "Ada", balance: 10 });

const s1 = client.startSession(), s2 = client.startSession();
s1.startTransaction(); s2.startTransaction();
await accounts.updateOne({ name: "Ada" }, { $inc: { balance: -1 } }, { session: s1 });
let err = null;
try { await accounts.updateOne({ name: "Ada" }, { $inc: { balance: -2 } }, { session: s2 }); }
catch (e) { err = e; }
console.log(err.codeName, err.code, [...err.errorLabelSet]);
await s1.commitTransaction();
await s2.abortTransaction();
await s1.endSession(); await s2.endSession();
console.log(await accounts.findOne({ name: "Ada" }, { projection: { _id: 0 } }));
if (!err.hasErrorLabel("TransientTransactionError")) throw new Error("expected the retry label");
```

```text
WriteConflict 112 [ 'TransientTransactionError' ]
{ name: 'Ada', balance: 9 }
```

## ขีดจำกัดและต้นทุน

transaction ต้องเสร็จภายใน `transactionLifetimeLimitSeconds` ซึ่งค่าเริ่มต้นคือ 60 วินาที ([Production considerations](https://www.mongodb.com/docs/manual/core/transactions-production-consideration/)) อ่านค่านั้น แล้วดูว่าการหมดอายุหน้าตาเป็นอย่างไร:

```js
// mongosh/txn-limit.js
const p = db.adminCommand({ getParameter: 1, transactionLifetimeLimitSeconds: 1 });
console.log(p.transactionLifetimeLimitSeconds);
assert.strictEqual(p.transactionLifetimeLimitSeconds, 60);
```

```text
60
```

เพื่อดูการหมดอายุโดยไม่ต้องรอหนึ่งนาที เราสตาร์ท replica set โหนดเดียวชั่วคราวด้วย `--setParameter transactionLifetimeLimitSeconds=2` transaction ที่หลับ 3.5 วินาทีระหว่างสองการเขียนได้ผลนี้ (output จริง ไม่ได้รันโดยตัวตรวจ):

```js
// app/txn-expired.mjs @skip-verify needs a mongod started with transactionLifetimeLimitSeconds=2
const s = client.startSession();
s.startTransaction();
await accounts.updateOne({ name: "Ada" }, { $inc: { balance: -3 } }, { session: s });
await new Promise((r) => setTimeout(r, 3500));
await accounts.updateOne({ name: "Linus" }, { $inc: { balance: 3 } }, { session: s });   // throws
```

```text
MongoServerError 251 NoSuchTransaction Transaction with { txnNumber: 2 } has been aborted. [ 'TransientTransactionError' ]
```

การหักของ Ada ถูก roll back ไปด้วย (ยอดยังคงเป็น 10 / 4) ทีนี้ต้นทุนที่วัดจริง: โอน 1 000 ครั้งด้วย (a) สอง update ธรรมดา, (b) `withTransaction` หนึ่งครั้งกับสอง update, (c) หนึ่ง update บน document เดียวที่เก็บทั้งสองยอด:

```js
// app/txn-cost.mjs
const accounts = db.collection("accounts"), pair = db.collection("pair");
await accounts.deleteMany({}); await pair.deleteMany({});   // fresh start
await accounts.insertMany([{ name: "Ada", balance: 1e6 }, { name: "Linus", balance: 0 }]);
await pair.insertOne({ _id: 1, ada: 1e6, linus: 0 });
const N = 1000, time = async (f) => { const t = Date.now(); for (let i = 0; i < N; i++) await f(); return Date.now() - t; };

const plain = await time(async () => {
  await accounts.updateOne({ name: "Ada" }, { $inc: { balance: -1 } });
  await accounts.updateOne({ name: "Linus" }, { $inc: { balance: 1 } });
});
const session = client.startSession();
const txn = await time(() => session.withTransaction(async () => {
  await accounts.updateOne({ name: "Ada" }, { $inc: { balance: -1 } }, { session });
  await accounts.updateOne({ name: "Linus" }, { $inc: { balance: 1 } }, { session });
}));
await session.endSession();
const single = await time(() => pair.updateOne({ _id: 1 }, { $inc: { ada: -1, linus: 1 } }));

console.log({ plainTwoUpdatesMs: plain, transactionMs: txn, singleDocumentMs: single, perTxnMs: txn / N });
if (!(single < plain && single < txn)) throw new Error("expected the single-document write to be cheapest");
```

```text
{
  plainTwoUpdatesMs: 2357,
  transactionMs: 2121,
  singleDocumentMs: 1086,
  perTxnMs: 2.121
}
```

ตัวเลขมาจากการรันหนึ่งครั้งบนเครื่อง Mac นี้: replica set โหนดเดียว ไม่มี network latency ไม่มี contention มีสองข้อที่เด่น การเขียน document เดียวเร็วกว่าทางเลือกอื่นประมาณสองเท่า — เพราะเป็นการเขียนหนึ่งครั้งกับ acknowledgement หนึ่งครั้ง และตรงข้ามกับความเชื่อที่ว่า transaction ช้ากว่าการเขียนแบบเดียวกันเสมอ ที่นี่ transaction *ไม่ได้* ช้ากว่าสอง update ธรรมดา: ด้วย `w: "majority"` ค่าเริ่มต้น update ธรรมดาแต่ละตัวรอ acknowledgement ของตัวเอง ส่วน transaction จ่ายครั้งเดียวตอน commit (ผมไม่ได้แยกพิสูจน์เหตุผลนี้ต่อ) สิ่งที่ transaction เพิ่มเข้ามาคือสิ่งที่ตัวเลขนี้มองไม่เห็น — snapshot ที่ค้างใน cache, การ retry `WriteConflict` ภายใต้ contention, ขีดจำกัด 60 วินาที และ commit ข้ามหลายโหนด — จึงควรวัดบน topology ของคุณเอง อีกหนึ่งจุดข้อมูล: สคริปต์เดียวกันบน replica set สามโหนด (Docker network, Node ในคอนเทนเนอร์) ได้ 1.97 วินาทีสำหรับคู่ update ธรรมดา 1 000 ครั้ง, 1.21 วินาทีสำหรับ transaction และ 0.83 วินาทีสำหรับการเขียน document เดียว — ลำดับเหมือนเดิม โดย transaction ยังนำหน้าสองการเขียน majority ธรรมดา

`withTransaction` รับ transaction options ด้วย คู่ที่เอกสารแนะนำคือ snapshot read กับ majority write ([Production considerations](https://www.mongodb.com/docs/manual/core/transactions-production-consideration/)):

```js
// app/txn-options.mjs
const session = client.startSession();
try {
  await session.withTransaction(async () => {
    await db.collection("accounts").insertOne({ name: "Grace", balance: 1 }, { session });
  }, { readConcern: { level: "snapshot" }, writeConcern: { w: "majority" }, maxCommitTimeMS: 5000 });
} finally { await session.endSession(); }
console.log(await db.collection("accounts").countDocuments({ name: "Grace" }));
```

```text
1
```

## เคล็ดลับและข้อควรระวัง

- **transaction ต้องใช้ replica set** (หรือ sharded cluster) error ของ standalone ด้านบนคือสิ่งที่คุณจะได้ถ้าไม่มี
- **ทำ transaction ให้สั้น** ต่ำกว่า 60 วินาทีเป็นขีดจำกัดตายตัว ยิ่งสั้นก็ยิ่งค้าง snapshot น้อยและเจอ write conflict น้อย งานช้า — เรียก network, คำนวณหนัก — ทำข้างนอก
- **ส่ง session ให้ทุก operation** — ส่วนถัดไปแสดงว่าจะเกิดอะไรเมื่อลืม
- เมื่อ abort หรือเกิด error ให้ retry ทั้ง transaction (เอกสาร: "When you encounter an error during individual operation in the transaction, abort and retry the transaction")

<Callout title="ออกแบบให้เป็น single-document ก่อน">
ต้นทุนที่วัดมาข้างบนคือข้อโต้แย้ง: การเขียน document เดียวเร็วกว่าประมาณสองเท่าและไม่ต้องมี session ไม่ต้องมีลูป retry ก่อนเขียน transaction ให้ถามว่าจัดรูป document ใหม่ให้การเปลี่ยนแปลงอยู่ในอันเดียวได้ไหม
</Callout>

```js
// app/txn-forgot-session.mjs
const accounts = db.collection("accounts");
await accounts.deleteMany({});   // fresh start
await accounts.insertMany([{ name: "Ada", balance: 10 }, { name: "Linus", balance: 4 }]);
const balances = async () => Object.fromEntries((await accounts.find().toArray()).map((r) => [r.name, r.balance]));

const session = client.startSession();
try {
  await session.withTransaction(async () => {
    await accounts.updateOne({ name: "Ada" }, { $inc: { balance: -3 } });                // BUG: no session
    await accounts.updateOne({ name: "Linus" }, { $inc: { balance: 3 } }, { session });
    throw new Error("audit log unavailable");
  });
} catch {}
const buggy = await balances();

await accounts.updateOne({ name: "Ada" }, { $set: { balance: 10 } });
try {
  await session.withTransaction(async () => {
    await accounts.updateOne({ name: "Ada" }, { $inc: { balance: -3 } }, { session });   // FIX
    await accounts.updateOne({ name: "Linus" }, { $inc: { balance: 3 } }, { session });
    throw new Error("audit log unavailable");
  });
} catch {}
const fixed = await balances();
await session.endSession();

console.log({ buggy, fixed });
if (buggy.Ada !== 7 || buggy.Linus !== 4) throw new Error("expected the debit to survive");
if (fixed.Ada !== 10 || fixed.Linus !== 4) throw new Error("expected a full rollback");
```

## Mental Model

transaction คือ **snapshot บวกชุดการเขียนที่ถูก buffer ไว้** ซึ่งเป็นของ session หนึ่ง การอ่านข้างในเห็น ณ เวลาเดียว (บวกสิ่งที่ transaction เขียนเอง); การเขียนมองไม่เห็นจากคนอื่นจนกว่าจะ commit และถูกทิ้งเมื่อ abort operation ใดที่ไม่มี session ก็เป็น operation ธรรมดาที่ทำอยู่ข้างเคียง การชนกันถูกตรวจแบบ optimistic — ฝ่ายแพ้ได้ error label และถูกคาดหวังให้รันใหม่

## Trade-offs

| ตัวเลือก | ประโยชน์ | ต้นทุน |
|---------|---------|------|
| ใช้ multi-document transaction | ACID เต็มข้าม document และ collection รับประกันว่า commit หรือ abort ด้วยกัน | วัดข้างบน: ราว 2.1 ms ต่อการโอน เทียบกับ 1.1 ms สำหรับการเขียน document เดียว (โหนดเดียว); ถือ snapshot ใน WiredTiger cache จนกว่าจะ commit; abort เมื่อ write conflict และหลัง 60 วินาที |
| หลีกเลี่ยง transaction โดยออกแบบ document ใหม่ | เร็วที่สุด (แถว document เดียวข้างบน) ไม่มี session ไม่ต้อง retry | ยอมรับข้อจำกัดของโมเดลข้อมูล เช่นการซ้ำซ้อนหรือ eventual consistency ระหว่าง collection |

## Common Misconceptions

- **"`withTransaction` ทำให้โค้ดข้างในทั้งหมดเป็น transactional"** — เฉพาะ operation ที่ได้รับ session เท่านั้น การหักที่มีบั๊กข้างบนถูก commit ไปแล้ว
- **"transaction ที่ล้มเหลวคือบั๊กที่ต้องโยนออกไป"** — `TransientTransactionError` เป็นผลลัพธ์ปกติภายใต้ contention ควร retry ทั้ง transaction ซึ่ง `withTransaction` ทำให้
- **"transaction ใช้ได้ทุกที่"** — ไม่ใช่บน standalone server (error จริงข้างบน)
- **"transaction ยาว ๆ ไม่เป็นไร แค่ใช้เวลานานขึ้น"** — มันถูก abort ที่ 60 วินาทีโดยค่าเริ่มต้น และค้าง cache ไว้จนถึงตอนนั้น
- **"transaction ช้ากว่าการเขียนแบบเดียวกันมากเสมอ"** — ไม่ใช่บน replica set โหนดเดียวที่ว่าง (พอ ๆ กับสอง update ธรรมดาข้างบน: 2.1 ms เทียบ 2.4 ms ต่อการโอน) ต้นทุนของมันคือการ retry, snapshot ที่ค้าง และขีดจำกัด 60 วินาที; ตัวเลือกที่ถูกที่สุดก็ยังคือการเขียน document เดียว

จนถึงตอนนี้เราเปลี่ยนข้อมูลและอ่านกลับเอง แต่หลายแอปพลิเคชันต้อง **ตอบสนอง** ต่อการเปลี่ยนแปลงที่ส่วนอื่นของระบบทำ — ส่งอีเมลเมื่อมีสมาชิกใหม่ รีเฟรช cache เมื่อ record เปลี่ยน ผลักข้อมูลไปยัง dashboard ทันทีที่มีคนจ่ายค่าปรับ การ poll collection ซ้ำ ๆ สิ้นเปลืองและช้า **change stream** แก้ปัญหานี้ตรง ๆ: คุณเปิด stream ด้วย `watch()` แล้วฐานข้อมูลส่งทุก insert, update และ delete ให้ทีละรายการตามที่เกิดขึ้น ตามลำดับ

Change stream สร้างบน **oplog** ซึ่งเป็น log ภายในตัวเดียวกับที่ replica set ใช้คัดลอกการเขียนจาก primary ไปยัง secondary จึงทำให้ change stream — เช่นเดียวกับ transaction — ต้องใช้ **replica set** (หรือ sharded cluster) บน standalone server `watch()` ล้มด้วย `MongoServerError 40573: The $changeStream stage is only supported on replica sets or mongos` (output จริง) output ด้านล่างมาจาก mongo 8.3.11 (replica set โหนดเดียว), mongosh 2.11.1 และ Node driver 7.7.0 บนเครื่อง Mac นี้ id และ token บนเครื่องคุณจะต่างออกไป แท็บ Python/Go/Rust สะท้อนการเรียกที่ตรวจแล้วใน shell/Node และไม่ได้ถูกรันโดยตัวตรวจอัตโนมัติของคอร์ส ลูปของมันบล็อกโดยออกแบบ จึงต้องรันใน worker ในบริการจริง — ตัวอย่างที่รันได้ในนี้อ่านด้วยการ poll `tryNext()` แบบมีขอบเขตแทน

## เปิด stream บน collection

แต่ละ event คือ document ที่มี `operationType` (`insert`, `update`, `delete`, `replace`, `drop`, `invalidate`, ...), `documentKey`, namespace `ns` และ resume token ใน `_id` ลูป `while (stream.hasNext())` ที่เห็นบ่อยจะบล็อก shell ตลอดไปเพื่อรอ event ถัดไป ตัวอย่างจึง poll ด้วย `tryNext()` (คืน `null` เมื่อไม่มีอะไรรออยู่) แล้วหยุด:

```js
// mongosh/cs-seed.js
db.createCollection("members");
assert.strictEqual(db.members.countDocuments(), 0);
```

## event มีอะไรบ้าง

insert event จริง (Node) update event จริงทั้งแบบไม่มีและมี `fullDocument: "updateLookup"` และ resume token:

```js
// app/cs-events.mjs
const members = db.collection("events_members");
await db.createCollection("events_members");
const next = async (cs, ms = 3000) => { const end = Date.now() + ms; while (Date.now() < end) { const e = await cs.tryNext(); if (e) return e; } return null; };

const plain = members.watch();
await plain.tryNext();
await members.insertOne({ name: "Grace", fines: 4 });
const ins = await next(plain);
console.log("insert keys:", Object.keys(ins));
console.log("resume token: length", ins._id._data.length, "starts", ins._id._data.slice(0, 24) + "...");

await members.updateOne({ name: "Grace" }, { $set: { fines: 3 } });
const upd = await next(plain);
console.log("update:", upd.updateDescription, "| has fullDocument:", "fullDocument" in upd);
await plain.close();

const lookup = members.watch([], { fullDocument: "updateLookup" });
await lookup.tryNext();
await members.updateOne({ name: "Grace" }, { $set: { fines: 2 } });
const upd2 = await next(lookup);
console.log("updateLookup fullDocument:", upd2.fullDocument);
await lookup.close();
if (ins._id._data.length !== 188 || "fullDocument" in upd || upd2.fullDocument.fines !== 2) throw new Error("unexpected event shape");
```

```text
insert keys: [
  '_id',
  'operationType',
  'clusterTime',
  'wallTime',
  'fullDocument',
  'ns',
  'documentKey'
]
resume token: length 188 starts 826ABCCD12000000012B042C...
update: { updatedFields: { fines: 3 }, removedFields: [], truncatedArrays: [] } | has fullDocument: false
updateLookup fullDocument: {
  _id: new ObjectId('6abccd12c596e5cafe63b469'),
  name: 'Grace',
  fines: 2
}
```

สามข้อจากการรันนั้น resume token จริงคือสตริง hex 188 ตัวอักษร (`_data`) ไม่ใช่ค่าสั้น ๆ เล่น ๆ update event ธรรมดามีแค่ delta ใน `updateDescription` — ไม่มี `fullDocument` เว้นแต่คุณขอ `updateLookup` ซึ่งดึง document *ปัจจุบัน* ตอนส่ง (จึงอาจมีการเปลี่ยนแปลงที่ตามมาแล้ว หรือเป็น `null` ถ้า document ถูกลบไปแล้ว ดู [manual](https://www.mongodb.com/docs/manual/changeStreams/) ตรวจเมื่อ 2026-09-30) และแต่ละ stream สดเท่ากับตอนที่มันถูกเปิดเท่านั้น ดังส่วนถัดไปจะแสดง

หากต้องการสถานะก่อน/หลังที่แม่นยำ ให้เปิด pre- และ post-image บน collection แล้วขอมัน หากไม่ได้เปิดแต่ขอ `required` stream จะล้มด้วย `MongoServerError 47: ... the pre-image was not found for event` จริง:

```js
// app/cs-images.mjs
const next = async (cs, ms = 3000) => { const end = Date.now() + ms; while (Date.now() < end) { const e = await cs.tryNext(); if (e) return e; } return null; };
await db.createCollection("images_members", { changeStreamPreAndPostImages: { enabled: true } });
const members = db.collection("images_members");
await members.insertOne({ _id: 1, name: "Ada", fines: 4 });

const stream = members.watch([], { fullDocument: "required", fullDocumentBeforeChange: "required" });
await stream.tryNext();
await members.updateOne({ _id: 1 }, { $inc: { fines: -2 } });
const e = await next(stream);
console.log("before:", e.fullDocumentBeforeChange, "| after:", e.fullDocument);
await stream.close();
if (e.fullDocumentBeforeChange.fines !== 4 || e.fullDocument.fines !== 2) throw new Error("expected the images");
```

```text
before: { _id: 1, name: 'Ada', fines: 4 } | after: { _id: 1, name: 'Ada', fines: 2 }
```

pre-image ถูกเก็บ (ใน `config.system.preimages`) และกินพื้นที่ เปิดต่อ collection เฉพาะเมื่อมี consumer ที่ต้องการ ([manual](https://www.mongodb.com/docs/manual/changeStreams/))

## resume จากจุดที่ค้างไว้

เครือข่ายหลุดและโปรเซสรีสตาร์ท ทุก event มี **resume token** ใน `_id` เก็บ token ของ event สุดท้ายที่จัดการแล้ว แล้วเปิด stream ใหม่จากจุดนั้นเพื่อรับทุกการเปลี่ยนแปลงตั้งแต่นั้น ด้านล่าง stream อ่านหนึ่ง event แล้วปิด มีการเขียนอีกสองครั้งขณะไม่มีใครฟัง แล้ว stream ใหม่ resume จาก token ที่เก็บไว้ ตามด้วยสองกรณีล้มเหลว: token ที่แต่งขึ้น และการ resume หลัง `invalidate` (collection ถูก drop) ซึ่ง `resumeAfter` ถูกปฏิเสธและต้องใช้ `startAfter`:

การ drop collection ที่ watch อยู่ทำให้ stream จบด้วย event `drop` ตามด้วย `invalidate` คุณ `resumeAfter` จาก invalidate ไม่ได้; `startAfter` เริ่ม stream ใหม่จากมัน:

```js
// app/cs-startafter.mjs
const next = async (cs, ms = 3000) => { const end = Date.now() + ms; while (Date.now() < end) { const e = await cs.tryNext(); if (e) return e; } return null; };
await db.createCollection("tmp_members");
const c = db.collection("tmp_members");

const s = c.watch();
await s.tryNext();
await c.drop();
const kinds = [(await next(s)).operationType, null];
const inv = await next(s);
kinds[1] = inv.operationType;
await s.close();
console.log("events after drop:", kinds);

await db.createCollection("tmp_members");
let refused = null;
try { await next(c.watch([], { resumeAfter: inv._id })); } catch (e) { refused = e; }
console.log("resumeAfter invalidate:", refused.code, refused.message);

const again = c.watch([], { startAfter: inv._id });
await again.tryNext();
await c.insertOne({ k: 2 });
const e = await next(again);
console.log("startAfter invalidate ->", e.operationType, e.fullDocument.k);
await again.close();
if (refused.code !== 260 || e.operationType !== "insert") throw new Error("expected resumeAfter refused, startAfter working");
```

```text
events after drop: [ 'drop', 'invalidate' ]
resumeAfter invalidate: 260 Attempting to resume a change stream using 'resumeAfter' is not allowed from an invalidate notification
startAfter invalidate -> insert 2
```

## กรองที่ต้นทาง

ส่ง aggregation pipeline ให้ `watch()` เพื่อให้ server ส่งเฉพาะสิ่งที่คุณสนใจ stream นี้ต้องการเฉพาะ update ที่ทำให้ `fines` ต่ำกว่า 3:

```js
// app/cs-filter.mjs
const next = async (cs, ms = 3000) => { const end = Date.now() + ms; while (Date.now() < end) { const e = await cs.tryNext(); if (e) return e; } return null; };
await db.createCollection("filter_members");
const members = db.collection("filter_members");
await members.insertMany([{ _id: 1, fines: 4 }, { _id: 2, fines: 9 }]);

const stream = members.watch([
  { $match: { operationType: "update", "updateDescription.updatedFields.fines": { $lt: 3 } } },
]);
await stream.tryNext();
await members.updateOne({ _id: 2 }, { $set: { fines: 8 } });   // filtered out
await members.insertOne({ _id: 3, fines: 0 });                  // filtered out
await members.updateOne({ _id: 1 }, { $set: { fines: 1 } });    // delivered
const e = await next(stream);
console.log(e.operationType, e.documentKey, e.updateDescription.updatedFields);
await stream.close();
if (e.documentKey._id !== 1) throw new Error("the filter should deliver only member 1");
```

```text
update { _id: 1 } { fines: 1 }
```

## token ย้อนกลับได้ไกลแค่ไหน?

token resume ได้ตราบที่ oplog ยังเก็บ operation นั้นอยู่ ("The oplog must have enough history to locate the operation associated with the token", [manual](https://www.mongodb.com/docs/manual/changeStreams/)) เมื่อมันหลุดออกจาก oplog แล้ว stream จะล้ม จึงควรกำหนดขนาด oplog ให้รองรับช่วงที่ consumer หยุดทำงานนานที่สุดที่คาด หน้าต่างนี้เช็คได้ในบรรทัดเดียว:

```js
// mongosh/cs-oplog.js
const info = db.getReplicationInfo();
console.log({ configuredLogSizeMB: Math.round(info.logSizeMB), usedMB: Math.round(info.usedMB), windowHours: Number((info.timeDiffHours).toFixed(2)) });
assert.ok(info.logSizeMB > 0);
```

```text
{ configuredLogSizeMB: 1292, usedMB: 1284, windowHours: 0.42 }
```

server ของ harness ตัวนั้นใช้ร่วมกันและยุ่ง หน้าต่างของมันจึงเป็นเศษของชั่วโมง — เตือนใจว่าหน้าต่างจะหดลงเมื่อปริมาณการเขียนเพิ่ม

**ใน Compass:** ไม่มี view สำหรับ change stream โดยเฉพาะ แต่คุณรันโค้ด `watch()` ในแท็บ **mongosh** ที่ฝังอยู่ แล้วแก้ไขในแท็บ Documents ในอีกหน้าต่างหนึ่งได้

## เคล็ดลับและข้อควรระวัง

- **change stream ต้องใช้ replica set หรือ sharded cluster** ด้วยเหตุผลเดียวกับ transaction
- **เก็บ resume token** หลังจัดการแต่ละ event มันคือสิ่งที่ทำให้ consumer ทนการล่ม handler ต้อง idempotent เพราะการล่มระหว่างจัดการกับบันทึกจะทำให้ event ถูกเล่นซ้ำ
- **token หมดอายุพร้อม oplog** ถ้า consumer ออฟไลน์นานกว่าหน้าต่างของ oplog stream จะ resume ไม่ได้ และคุณต้อง reconcile ด้วยวิธีอื่น
- **event จำกัดที่ 16 MiB**; เมื่อขอทั้ง pre- และ post-image บน document ใหญ่จะมีผล ([manual](https://www.mongodb.com/docs/manual/changeStreams/))

<Callout title="Watch อย่า poll">
เมื่อแอปต้องตอบสนองต่อการเปลี่ยนแปลงข้อมูล ให้เปิด change stream แทนการ poll เตรียม (prime) มันด้วยการอ่านครั้งแรกก่อนเขียน เก็บ resume token ของทุก event ที่จัดการแล้ว และกำหนดขนาด oplog ให้รองรับช่วงหยุดที่นานที่สุด
</Callout>

## อ่านโค้ดที่ AI สร้าง

ผู้ช่วย AI เขียนเทสต์สำหรับ "listener ได้รับ insert" — เปิด stream แล้วเขียน:

<SpotTheBug lang="js" code={`// AI comment: "watch() subscribes immediately, so the insert below will be delivered"
const stream = members.watch();
await members.insertOne({ name: "Katherine" });
for await (const event of stream) { console.log(event.operationType); break; }`}>

`watch()` ใน mongosh เปิด server cursor ทันที แต่ **Node driver เปิด change stream แบบ lazy** ตอนอ่านครั้งแรก insert เกิดขึ้น *ก่อน* ที่ stream จะมีอยู่บน server จึงไม่เคยถูกส่ง และ `for await` รอตลอดไป ด้านล่างคือรอบที่พลาด (จำกัด 2 วินาทีแทนที่จะค้าง) และวิธีแก้ — อ่านครั้งแรก (`tryNext()`) เพื่อให้ stream เปิดก่อนเขียน:

```js
// app/cs-lazy-open.mjs
const members = db.collection("lazy_members");
await db.createCollection("lazy_members");
const next = async (cs, ms = 2000) => { const end = Date.now() + ms; while (Date.now() < end) { const e = await cs.tryNext(); if (e) return e; } return null; };

const lazy = members.watch();
await members.insertOne({ name: "Missed" });
const missed = await next(lazy);
await lazy.close();

const primed = members.watch();
await primed.tryNext();                         // FIX: opens the stream on the server
await members.insertOne({ name: "Seen" });
const seen = await next(primed);
await primed.close();

console.log({ lazy: missed?.operationType ?? "MISSED", primed: seen?.fullDocument.name });
if (missed !== null || seen?.fullDocument.name !== "Seen") throw new Error("expected lazy=missed, primed=seen");
```

```text
{ lazy: 'MISSED', primed: 'Seen' }
```

## Mental Model

change stream คือ **หางของ oplog พร้อมที่คั่นหน้า** แต่ละ event คือหนึ่งรายการตามลำดับ commit; resume token คือที่คั่นหน้า stream เห็นเฉพาะรายการตั้งแต่ตอนที่มันถูกเปิด (หรือจากที่คั่นหน้าที่คุณให้) คำถามจึงเป็นสองข้อเสมอ "stream ของฉันเริ่มที่ไหน?" (prime มัน หรือส่ง token) และ "ที่คั่นหน้ายังอยู่ใน log หรือไม่?" (หน้าต่างของ oplog) stream บอก *สิ่งที่เกิดขึ้น* ไม่เคยบอก *สถานะปัจจุบัน*

## ข้อแลกเปลี่ยน

| ตัวเลือก | ประโยชน์ | ต้นทุน |
|---------|---------|------|
| Change stream (`watch()`) | event แบบ real-time ตามลำดับ commit, resume จาก token ได้, กรองที่ต้นทางได้ | ต้องมี replica set; คุณเก็บ token เอง; token หมดอายุพร้อม oplog; Node เปิดแบบ lazy |
| `fullDocument: "updateLookup"` | ได้ document ทั้งก้อนบน update event โดยไม่ต้องรู้ schema | lookup เพิ่มต่อ event; คืน document *ปัจจุบัน* (อาจใหม่กว่า event หรือ `null` ถ้าถูกลบ) |
| Pre/post image (`required`) | สถานะก่อน/หลังที่แม่นยำ | เก็บต่อ collection (พื้นที่) และ stream error ถ้าไม่มี image |
| Polling | ง่าย ไม่พึ่ง oplog | latency เท่ากับ interval, query สิ้นเปลือง, พลาดการอัปเดตได้ง่าย |

## Common Misconceptions

- **"`watch()` subscribe ทันทีที่ return"** — ไม่ใช่ใน Node driver (lazy open); insert ที่ทำทันทีหลัง `watch()` พลาดไป และ `tryNext()` ครั้งแรกแก้ได้
- **"ลูป `while (hasNext())` คือวิธีบริโภค stream"** — มันบล็อกตลอดไปเพื่อรอ event; ใช้ `tryNext()` พร้อม deadline ในสคริปต์ และ async iterator ในบริการ
- **"update event มี document"** — มีแค่ delta เว้นแต่ขอ `updateLookup` หรือ post-image
- **"`resumeAfter` ใช้ได้หลังทุก event"** — ไม่ใช่หลัง `invalidate` (code 260); ใช้ `startAfter`
- **"resume token เป็นสตริงทึบสั้น ๆ"** — ของจริงยาว 188 ตัวอักษร hex และของที่แต่งขึ้นล้มด้วย code 50793
- **"change stream บอกสถานะปัจจุบัน"** — มันบอกสิ่งที่เกิดขึ้น; bootstrap สถานะด้วย query

index แบบ ascending ธรรมดาตอบโจทย์ส่วนใหญ่ แต่ MongoDB มี index เฉพาะทางสำหรับกรณีที่จัดการได้ไม่สวย: field ที่เป็น array, full-text search, document ที่ควรหมดอายุเอง, index เฉพาะส่วนของ collection, ความไม่ซ้ำ, attribute ที่ไม่มี schema, การค้นแบบ hashed และตำแหน่ง แต่ละแบบเป็นเพียงการปรับ `createIndex` เล็กน้อย และแต่ละแบบมีกับดักที่ตัวอย่างในเอกสารทั่วไปไม่แสดง บทนี้พิสูจน์ทุกแบบ

จับจาก mongo 8.3.11, mongosh 2.11.1 และ Node driver 7.7.0 บน Mac เครื่องเดียว บทนี้เตรียม `members` 100 000 รายการ (10 เมือง ยืมหนังสือคนละสามเล่ม 2% มี fines ครึ่งหนึ่งมี `cardNumber` บางรายมี `attrs` แบบอิสระ และแต่ละคนมีพิกัดใกล้ Berlin) และใช้ helper `plan()` บรรทัดเดียวเดิม แท็บ Python, Go และ Rust ถูกรันอย่างละหนึ่งครั้งในโปรแกรม scratch กับ server เดียวกัน

```js
// mongosh/types-seed.js
const cities = ["Berlin", "Paris", "Lima", "Oslo", "Cairo", "Tokyo", "Rome", "Lagos", "Dhaka", "Quito"];
globalThis.plan = (cur) => {                       // stage chain (also through TEXT/GEO stages), then keys and docs read
  const e = cur.explain("executionStats"), s = e.executionStats, stages = [];
  for (let p = e.queryPlanner.winningPlan; p; p = p.inputStage) stages.push(p.stage + (p.indexName ? "(" + p.indexName + ")" : ""));
  return stages.join(" > ") + "  returned=" + s.nReturned + " keys=" + s.totalKeysExamined + " docs=" + s.totalDocsExamined;
};
const colors = ["red", "green", "blue"];
for (let s = 0; s < 100000; s += 50000) {
  db.members.insertMany(Array.from({ length: 50000 }, (_, k) => {
    const i = s + k;
    const d = { name: "m" + i, city: cities[i % 10],
                borrowed: ["book" + (i % 500), "book" + ((i * 7) % 500), "book" + ((i * 13) % 500)],
                fines: i % 50 === 0 ? 1 + (i % 7) : 0,                       // only 2% of members owe anything
                location: { type: "Point", coordinates: [13 + (i % 100) / 100, 52 + (Math.floor(i / 100) % 100) / 100] } };
    if (i % 2 === 0) d.cardNumber = "C" + i;                                    // half the members have no card
    if (i % 3 === 0) d.attrs = { color: colors[i % 3 === 0 ? (i / 3) % 3 : 0] };   // schemaless attributes
    if (i % 5 === 0) d.attrs = Object.assign(d.attrs ?? {}, { size: "L" });
    return d;
  }), { ordered: false });
}
console.log("members:", db.members.countDocuments(), "| with fines:", db.members.countDocuments({ fines: { $gt: 0 } }), "| with cardNumber:", db.members.countDocuments({ cardNumber: { $exists: true } }));
```


## Multikey: ทำ index ให้ array

เมื่อคุณทำ index ให้ field ที่เก็บ array MongoDB ทำให้เป็น index แบบ **multikey** อัตโนมัติ: หนึ่ง entry ต่อหนึ่งสมาชิกของ array query หาหนังสือหนึ่งเล่มจึง seek ตรงถึงเจ้าของ ไม่ต้องตั้งค่าอะไร - ค่าเป็นตัวตัดสิน

## Text: ค้นหาคำ

**text index** แยกคำและทำ stem ให้ field แบบ string เพื่อให้ `$text` จับคู่คำได้ บทเดิมเคยบอกว่าผลลัพธ์เรียงตามความเกี่ยวข้อง แต่ไม่ใช่ เว้นแต่คุณขอ server เก็บคะแนนไว้และคุณต้อง project และ sort ด้วย `{ $meta: "textScore" }`:

<Tabs syncKey="lang">
  <TabItem label="mongosh">
    ```js

    assert.strictEqual(JSON.stringify(ranked.slice(0, 2).map((d) => d.n)), "[5,4]");
    ```

## TTL: document ที่หมดอายุเอง

**TTL** index ลบ document เมื่อ field วันที่เก่ากว่า `expireAfterSeconds` field ต้องเป็น BSON date (หรือ array ที่มี date): คู่มือระบุว่า "specify an index field that is either a date type or an array that contains date type values" และงานเบื้องหลัง "runs every 60 seconds" ([TTL indexes](https://www.mongodb.com/docs/manual/core/index-ttl/), ตรวจ 2026-09-30) การสร้างทำได้ในการเรียกเดียว แท็บแรกด้านล่างยังพิสูจน์กับดักเรื่องชนิดข้อมูลด้วย:

<Tabs syncKey="lang">

เพื่อเห็นเวลาจริง การรันนี้ใช้ `expireAfterSeconds: 1` และ poll ตรวจ มันถูกทำเครื่องหมาย `@skip-verify` เพราะรอตัว monitor ที่ทำงานทุก 60 วินาที และตัวตรวจของคอร์สมีงบ 90 วินาทีต่อบท:

```js
// mongosh/types-ttl.js @skip-verify waits up to ~60 s for the TTL monitor (default sweep interval)
db.sessions.createIndex({ createdAt: 1 }, { expireAfterSeconds: 1 });
const t0 = Date.now();
db.sessions.insertMany([
  { _id: "date", createdAt: new Date() },
  { _id: "array", createdAt: [new Date(), new Date(Date.now() + 3600e3)] },
  { _id: "string", createdAt: new Date().toISOString() },                 // the trap: a string, not a Date
]);
let gone = null;
while (Date.now() - t0 < 125000) {
  if (gone === null && db.sessions.countDocuments({ _id: { $in: ["date", "array"] } }) === 0) gone = Math.round((Date.now() - t0) / 1000);
  sleep(1000);
}
console.log("Date and array-of-Date documents gone after", gone, "s (expireAfterSeconds was 1)");
console.log("after 125 s still stored:", db.sessions.find().toArray().map((d) => d._id));
```

```text
Date and array-of-Date documents gone after 14 s (expireAfterSeconds was 1)
after 125 s still stored: [ 'string' ]
```

document แบบ Date และ array ของ Date หายไปภายในรอบ 60 วินาทีของ monitor (14 วินาทีในการรันนี้ - เฟสขึ้นกับว่ารอบล่าสุดยิงเมื่อไร) ไม่เคยทันที document ที่เก็บ ISO string ยังอยู่หลัง 125 วินาที และจะอยู่ตลอดไป: TTL เมินค่าที่ไม่ใช่วันที่แบบเงียบ ๆ

## Partial: ทำ index บางส่วน

**partial** index ครอบคลุมเฉพาะ document ที่ตรง filter จึงเล็กเมื่อคุณ query แค่ส่วนเดียว มีสมาชิกเพียง 2% ที่ค้างค่าปรับ index ด้านล่างจึงมี 2 000 entry แทน 100 000:

<Tabs syncKey="lang">
  <TabItem label="mongosh">
    ```js
    // mongosh/types-partial.js
    console.log(db.members.createIndex({ fines: 1 }, { partialFilterExpression: { fines: { $gt: 0 } }, name: "fines_owing" }));
    const kb = (n) => Math.round(n / 1024);
    db.members.createIndex({ fines: 1 }, { name: "fines_all" });
    const sz = db.members.stats().indexSizes;
    console.log("index sizes KB:", { fines_owing: kb(sz.fines_owing), fines_all: kb(sz.fines_all) });
    db.members.dropIndex("fines_all");
    console.log("fines > 2   :", plan(db.members.find({ fines: { $gt: 2 } })));
    console.log("fines = 0   :", plan(db.members.find({ fines: 0 })));
    console.log("fines >= 0  :", plan(db.members.find({ fines: { $gte: 0 } })));
    ```
  </TabItem>
  <TabItem label="Node.js">

```text
fines > 2: keys 40 docs 40
```

partial index มีขนาด 28 KB เทียบ 360 KB ของ index เต็มบน field เดียวกัน มันรับ `fines > 2` (1 428 key สำหรับ 1 428 ผลลัพธ์) แต่ไม่รับ `fines = 0` หรือ `fines >= 0`: planner ใช้ partial index ก็ต่อเมื่อรับประกันได้ว่า query อยู่ในช่วงของ filter และสองแบบนั้นอาจ match สมาชิกที่ไม่เคยถูกทำ index

## Unique และทำไม sparse จึงเป็นเครื่องมือที่ผิด

**unique** index ปฏิเสธค่าซ้ำ จุดยากคือ field ที่ไม่บังคับ: field ที่หายถูก index เป็น `null` และ `null` สองตัวนับว่าซ้ำ บทเดิมรัน `unique` แล้ว `unique + sparse` บน key เดียวกัน ซึ่งล้มเหลว (ชื่อ index ซ้ำ) ลำดับทั้งหมดพร้อม error จริง:

```js
// mongosh/types-unique.js
try { db.members.createIndex({ cardNumber: 1 }, { unique: true }); }              // half the members have no cardNumber
catch (e) { console.log("1. unique alone     :", e.codeName, "-", e.message.slice(e.message.indexOf("E11000"))); }
console.log("2. unique + sparse  :", db.members.createIndex({ cardNumber: 1 }, { unique: true, sparse: true }));
try { db.members.createIndex({ cardNumber: 1 }, { unique: true, partialFilterExpression: { cardNumber: { $exists: true } } }); }
catch (e) { console.log("3. switch to partial (same name):", e.codeName); }
db.members.dropIndex("cardNumber_1");
console.log("4. partial + unique :", db.members.createIndex({ cardNumber: 1 }, { unique: true, partialFilterExpression: { cardNumber: { $exists: true } }, name: "card_unique" }));
db.members.insertMany([{ name: "no card 1" }, { name: "no card 2" }]);
try { db.members.insertOne({ name: "dup", cardNumber: "C2" }); } catch (e) { console.log("   duplicate card     : code", e.code, JSON.stringify(e.keyValue)); }
console.log("   members without a card inserted:", db.members.countDocuments({ name: /^no card / }));
```

```text
1. unique alone     : DuplicateKey - E11000 duplicate key error collection: b2_e5a3dc.members index: cardNumber_1 dup key: { cardNumber: null }
2. unique + sparse  : cardNumber_1
3. switch to partial (same name): IndexKeySpecsConflict
4. partial + unique : card_unique
   duplicate card     : code 11000 {"cardNumber":"C2"}
   members without a card inserted: 2
```

ขั้น 1 ล้มเหลวเพราะสมาชิก 50 000 คนไม่มีบัตร (`dup key: { cardNumber: null }`) ขั้น 2 ใช้ได้ แต่เป็นเครื่องมือที่ผิด: index แบบ **sparse** ข้าม document ที่ไม่มี field และ sparse index ที่ planner ถูกบังคับให้ใช้กับ sort คืนผลไม่ครบ:

```js
// mongosh/types-sparse.js
db.cards.insertMany([{ n: 1, card: "b" }, { n: 2 }, { n: 3, card: "a" }]);
db.cards.createIndex({ card: 1 }, { sparse: true, name: "card_sparse" });
console.log("plain sort           :", db.cards.find().sort({ card: 1 }).toArray().map((d) => d.n));
console.log("sort with sparse hint:", db.cards.find().sort({ card: 1 }).hint("card_sparse").toArray().map((d) => d.n), "<- document 2 is missing");
assert.strictEqual(db.cards.find().sort({ card: 1 }).hint("card_sparse").toArray().length, 2);
```

```text
plain sort           : [ 2, 3, 1 ]
sort with sparse hint: [ 3, 1 ] <- document 2 is missing
```

document 2 ไม่มี `card` plan ที่ถูก hint จึงทิ้งมัน (2 จาก 3 document); ถ้าไม่ hint planner ปฏิเสธ sparse index และคืนครบทั้งสาม คู่มือบอกเช่นกัน: "MongoDB does not select the sparse index to fulfill the query in order to return complete results" และ "Partial indexes can function as sparse indexes, but also support filter expressions ... Use a partial index for greater control" ([sparse indexes](https://www.mongodb.com/docs/manual/core/index-sparse/), ตรวจ 2026-09-30) ขั้น 4 ข้างบนคือรูปแบบที่แนะนำ: `unique` บวก `partialFilterExpression: { cardNumber: { $exists: true } }` ยอมให้สมาชิกที่ไม่มีบัตรมีกี่คนก็ได้และปฏิเสธบัตรซ้ำ การเปลี่ยน index ที่มีอยู่ไปใช้ option ต่างต้อง drop ก่อน (ขั้น 3 ได้ `IndexKeySpecsConflict`)

## อีกสามแบบที่คุณจะเจอ

**Wildcard** - index เดียวบน subtree ที่คุณไม่รู้ key ล่วงหน้า (`attrs.$**`) สะดวกกับ attribute ที่ไม่มี schema แต่ทำ index ทุก path จึงใหญ่และช้ากว่า index เฉพาะจุด สังเกตว่า conjunction ด้านล่างยังใช้ path wildcard เดียวแล้วกรองที่เหลือ (11 112 key สำหรับ 2 223 ผลลัพธ์):

```js
// mongosh/types-wildcard.js
console.log(db.members.createIndex({ "attrs.$**": 1 }));
console.log("attrs.color = red :", plan(db.members.find({ "attrs.color": "red" })));
console.log("attrs.size  = L   :", plan(db.members.find({ "attrs.size": "L" })));
console.log("size = L AND color:", plan(db.members.find({ "attrs.size": "L", "attrs.color": "red" })));
```

```text
attrs.$**_1
attrs.color = red : FETCH > IXSCAN(attrs.$**_1)  returned=11112 keys=11112 docs=11112
attrs.size  = L   : FETCH > IXSCAN(attrs.$**_1)  returned=20000 keys=20000 docs=20000
size = L AND color: FETCH > IXSCAN(attrs.$**_1)  returned=2223 keys=11112 docs=11112
```

**Hashed** - เก็บ hash ของค่า: เหมาะกับ equality และ hash-based sharding แต่ไร้ประโยชน์กับช่วงและ sort:

```js
// mongosh/types-hashed.js
console.log(db.members.createIndex({ name: "hashed" }));
console.log("name = m4242 :", plan(db.members.find({ name: "m4242" })));
console.log("name range   :", plan(db.members.find({ name: { $gte: "m4242", $lt: "m4243" } })));
console.log("sort by name :", plan(db.members.find().sort({ name: 1 }).limit(3)));
```

```text
name_hashed
name = m4242 : FETCH > IXSCAN(name_hashed)  returned=1 keys=1 docs=1
name range   : COLLSCAN  returned=11 keys=0 docs=100002
sort by name : SORT > COLLSCAN  returned=3 keys=0 docs=100002
```

**2dsphere** - พิกัด GeoJSON บนทรงกลม สำหรับ `$near`, `$geoWithin` และพวกเดียวกัน stage ใน plan คือ `GEO_NEAR_2DSPHERE`:

```js
// mongosh/types-geo.js
console.log(db.members.createIndex({ location: "2dsphere" }));
const near = { location: { $near: { $geometry: { type: "Point", coordinates: [13.5, 52.5] }, $maxDistance: 2000 } } };
console.log("$near 2 km :", plan(db.members.find(near)));
console.log("nearest 3  :", db.members.find(near, { name: 1, _id: 0 }).limit(3).toArray().map((d) => d.name));
```

```text
location_2dsphere
$near 2 km : GEO_NEAR_2DSPHERE(location_2dsphere)  returned=150 keys=383 docs=250
nearest 3  : [ 'm5050', 'm25050', 'm65050' ]
```

**In Compass:** ไดอะล็อก **Create Index** ในแท็บ **Indexes** มีตัวเลือกเหล่านี้ - ติ๊ก **Unique** ตั้งค่า **TTL** หรือใส่ **Partial Filter Expression** ได้โดยไม่ต้องออกจาก GUI

## เคล็ดลับและข้อควรระวัง

- compound index มี field แบบ array ได้อย่างมากหนึ่งอัน (`cannot index parallel arrays`, code 171) และ error อาจโผล่ทีหลังตอน insert
- `$text` ไม่จัดอันดับเว้นแต่คุณ project และ sort `textScore`; หนึ่ง collection มี text index ได้อันเดียว
- TTL ลบเฉพาะ BSON date ภายในราว 60 วินาที ไม่ใช่ทันที; วันที่แบบ string ไม่เคยถูกลบ
- เลือก partial แทน sparse; partial index รับเฉพาะ query ที่รับประกันว่าอยู่ในช่วง filter
- unique index ถือ field ที่หายเป็น `null`; ถ้าไม่มี partial filter document ที่ไม่มี field นั้นได้เพียงอันเดียว

<Callout title="เลือก index ที่เข้ากับรูปร่างของข้อมูล">
query ส่วนใหญ่ต้องการ index ธรรมดา แต่ array ต้องการ multikey, คำต้องการ text (และ sort ตามคะแนน), ข้อมูลหมดอายุต้องการ TTL บนวันที่จริง, ส่วนย่อยที่ถูก query ต้องการ partial, ค่า unique แบบไม่บังคับต้องการ partial + unique, key ที่ไม่รู้ล่วงหน้าต้องการ wildcard และตำแหน่งต้องการ 2dsphere
</Callout>

## Mental Model

index พิเศษทุกชนิดคือ B-tree เดียวกันที่มีกฎต่างกันว่า **entry ใดถูกใส่เข้าไป** (multikey: ทุกสมาชิกของ array; partial/sparse: เฉพาะบาง document; wildcard: ทุก path; hashed: ค่า hash; TTL: วันที่ที่ server เฝ้าดู) และ **ตอบคำถามแบบไหนได้** (text: จับคู่คำพร้อมคะแนน; 2dsphere: ระยะทาง; hashed: equality เท่านั้น) ถ้า query ต้องการ entry ที่ไม่เคยถูกเขียน index ก็ช่วยไม่ได้

## ข้อแลกเปลี่ยน

| ทางเลือก | ข้อดี | ต้นทุน |
|---------|---------|------|
| Multikey | seek ตามสมาชิก array ใดก็ได้ | ราว 3 entry ต่อ document ที่นี่; หนึ่ง array field ต่อ compound index |
| Text | ค้นหาคำพร้อมคะแนน | อันเดียวต่อ collection; ไม่จัดอันดับเว้นแต่ sort ตาม textScore |
| TTL | ข้อมูลล้างตัวเอง ไม่ต้อง cron | ช้าได้ถึง ~60 วินาที; เฉพาะวันที่จริง |
| Partial | 28 KB แทน 360 KB | เฉพาะ query ที่อยู่ในช่วง filter ใช้ได้ |
| Unique (+ partial) | ความไม่ซ้ำระดับฐานข้อมูลพร้อม field ที่ไม่บังคับ | การเขียนซ้ำถูกปฏิเสธ: ต้องจัดการ E11000 |
| Wildcard | ไม่ต้องรู้ key ล่วงหน้า | ทำ index ทุก path; อ่อนกว่า index เฉพาะจุด |
| Hashed | กระจายสม่ำเสมอ equality ถูก | ไม่มีช่วง ไม่มี sort |

## Common Misconceptions

- **"ผล `$text` มาแบบจัดอันดับ"** - ลำดับที่ไม่ sort คือ 5, 1, 4, 2; sort ตามคะแนนคือ 5, 4, 1, 2
- **"TTL ใช้ได้กับ field ที่หน้าตาเหมือน timestamp ทุกอัน"** - ISO string อยู่รอด 125 วินาที; ลบเฉพาะวันที่จริง
- **"unique + sparse คือวิธีทำให้ field ที่ไม่บังคับไม่ซ้ำ"** - ใช้ partial filter; sparse ทำ document หายเมื่อ sort
- **"partial index เร่งทุก query บน field"** - `fines = 0` และ `fines >= 0` เป็น COLLSCAN
- **"hashed index ช่วยช่วงและ sort ด้วย"** - ทั้งสองเป็น COLLSCAN บน 100 000 document
- **"TTL ลบตรงวินาทีเป๊ะ"** - อยู่ในรอบ monitor 60 วินาที ไม่เคยทันที

> ตัวอย่างจากของจริง
>
> คู่มือ MongoDB เองชี้ให้ห่างจาก sparse: "Partial indexes can function as sparse indexes, but also support filter expressions for conditions beyond whether a field exists" ([sparse indexes](https://www.mongodb.com/docs/manual/core/index-sparse/), ตรวจ 2026-09-30) และเตือนว่า document ที่หมดอายุ "may exist for some time beyond the 60 second period between runs of the background task" บน server ที่ยุ่ง ([TTL indexes](https://www.mongodb.com/docs/manual/core/index-ttl/), ตรวจ 2026-09-30)

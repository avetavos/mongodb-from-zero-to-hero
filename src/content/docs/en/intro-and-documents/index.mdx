Welcome to **MongoDB — From Zero to Hero**. This course takes you from never having touched a database to comfortably modelling data, querying it, indexing it for speed, aggregating it into reports, and running it in production. We will work in concrete examples the whole way: a small, made-up world of library members and the books they borrow, kept deliberately tiny so the ideas stay in the spotlight. Every operation is shown five ways — in the **mongosh** shell and in the **Node.js**, **Python**, **Go**, and **Rust** drivers — so the lessons transfer to whatever stack you actually work in.

MongoDB is a **document database**: instead of storing your data as rows in rigid tables, it stores **documents** — JSON-like objects with fields, nested objects, and arrays — grouped into **collections**. A document is allowed to look however your data naturally looks, so the shape of the data in the database tends to match the shape of the objects in your code, with no translation layer in between.

## What each module covers

- **Intro & Documents** — the module you are in now. What a document database is, how to run MongoDB locally with Docker, the shell and Compass, and what a BSON document really is.
- **CRUD** — the four everyday verbs: creating, reading, updating, and deleting documents.
- **Querying** — filtering with operators, sorting, limiting, projecting fields, and paging through results.
- **Indexes** — making queries fast, understanding what an index costs, and reading a query plan.
- **Aggregation** — the pipeline that groups, reshapes, and summarises data into reports.
- **Data Modeling** — deciding when to embed related data and when to keep it in separate collections.
- **Transactions & Consistency** — multi-document atomicity, read and write concerns, and the guarantees you can rely on.
- **Operations & Scaling** — backups, replica sets for resilience, and sharding for growth.

## Reading AI-generated code

This course shows the Node.js driver next to the shell, and the most common Node mistake in AI-written code is a forgotten `await`:

<SpotTheBug lang="js" code={`// AI comment: "insert the member, then confirm the count"
const members = db.collection("members");
members.insertOne({ name: "Grace" });
const n = await members.countDocuments();
console.log(n === 1 ? "saved" : "missing");`}>

`insertOne` returns a promise; without `await` the code races ahead. We ran the pattern 20 times (deleting the collection first each time): the count was **0 in 15 of the 20 runs**, so the check printed "missing" for a write that succeeds a moment later. A rejection of the un-awaited promise is also lost - a duplicate-key insert failed silently until we attached a `.catch`. The fix is one word:

```js
// app/intro-await.mjs
const members = db.collection("members");
await members.deleteMany({});
await members.insertOne({ name: "Grace" });
const n = await members.countDocuments();
console.log(n === 1 ? "saved" : "missing");
if (n !== 1) throw new Error("expected 1");
```

```text
saved
```

</SpotTheBug>

## Mental Model

The course is one loop: **model** a document, **write** it (CRUD), **read** it (querying), make the read **fast** (indexes), **summarise** it (aggregation), keep it **correct** (transactions) and **alive** (operations). Modules 1 to 3 are the vocabulary of that loop; the rest are the properties you add once the loop works.

## Trade-offs

| Choice | Benefit | Cost |
|---------|---------|------|
| The document model's flexible schema | Start writing code and shipping features fast, without fully designing a schema on day one | No compile-time guarantee that every document in a collection shares the same shape - consistency becomes your team's own responsibility |
| BSON with more types than JSON | Store Date, ObjectId, and Decimal128 exactly, without converting values yourself | Each language driver maps these types onto its own native types differently (the Documents and BSON lesson measured it) |
| Standalone container for learning | Simplest to run, supports a root user | No transactions or change streams; module 7 needs the replica-set variant |

## Common Misconceptions

- **"No schema means no design."** - a flexible schema still needs discipline; the What is MongoDB lesson shows a typo field accepted silently.
- **"Each module is fully independent."** - later modules lean on the vocabulary here (document, field, BSON, `_id`).
- **"MongoDB fits every job."** - the module covers when a relational database is still the better tool.
- **"The Docker container from Setup covers the whole course."** - a standalone one does not: module 7 needs a replica set.
- **"Missing `await` still works if the write is quick."** - 15 of 20 counts were 0 in the run above.

> Real-world example
>
> **eBay** - uses MongoDB as one of its core enterprise data platform standards, powering customer-facing applications on ebay.com, including a product catalog scaled across large replica sets for massive read volume ([mongodb.com/customers/ebay](https://www.mongodb.com/customers/ebay), 2017).
>
> **Forbes** - uses MongoDB Atlas as the backend for the CMS that serves all content on Forbes.com; the flexible data structures let the team add components quickly and cut average build times from 25 to 9 minutes ([mongodb.com/customers/forbes](https://www.mongodb.com/customers/forbes), 2019).

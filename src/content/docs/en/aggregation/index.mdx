A `find` call answers one kind of question: "give me back the documents that match this filter." That is plenty for reading records, but it cannot *summarise* them. It will not tell you the copies sold per title, the orders each customer placed, or the three top-selling books. For questions that fold many documents into a smaller, reshaped answer, MongoDB gives you the **aggregation pipeline**.

Picture a conveyor belt: your documents enter at one end, pass through a line of **stages**, and a transformed stream comes out the other end. Each stage does one well-defined job and passes its output to the next. The order is yours to choose, and it matters - a stage only ever sees what the stage before it produced.

**One dataset for the whole module.** Every lesson here seeds the same `sales` collection in its first block: 200 000 book orders `{ title, genre, quantity, price, buyer }` over 500 titles, 5 genres, prices 5-25 and 1 000 buyers (the unwind lesson uses its own `orders` collection with an `items` array). Output was captured on mongo 8.3.11, mongosh 2.11.1 and Node driver 7.7.0 on one Mac; Python, Go and Rust tabs were each run once in a scratch program. `aplan()` is a helper that condenses `explain("executionStats")` of an aggregation to one line: what the first stage read from the collection, then the stages that were left to run in the pipeline.

```js
// mongosh/agg-seed.js
const genres = ["fiction", "science", "history", "poetry", "comics"];
globalThis.aplan = (pipeline) => {               // one line per aggregate explain: what the first stage read, then the stages left in the pipeline
  const e = db.sales.explain("executionStats").aggregate(pipeline);
  const cursor = e.stages ? e.stages[0].$cursor : e, rest = e.stages ? e.stages.slice(1).map((s) => Object.keys(s)[0]) : [];
  const chain = (p) => { const out = []; for (p = p.queryPlan ?? p; p; p = p.inputStage) out.push(p.stage + (p.indexName ? "(" + p.indexName + ")" : "")); return out.join(" > "); };
  const s = cursor.executionStats;
  return chain(cursor.queryPlanner.winningPlan) + "  keys=" + s.totalKeysExamined + " docs=" + s.totalDocsExamined + (rest.length ? "  | left in pipeline: " + rest.join(" > ") : "");
};
for (let s = 0; s < 200000; s += 50000) {
  db.sales.insertMany(Array.from({ length: 50000 }, (_, k) => {
    const i = s + k;                                          // 500 titles, 5 genres, quantity 1..5, price 5..25, 1000 buyers (pseudo-random but repeatable)
    return { title: "T" + (i % 500), genre: genres[(i % 500) % 5], quantity: 1 + ((Math.imul(i, 2654435761) >>> 0) % 5), price: 5 + ((Math.imul(i, 40503) >>> 0) % 21), buyer: "b" + (i % 1000) };
  }), { ordered: false });
}
db.sales.createIndex({ price: 1 });
console.log("sales:", db.sales.countDocuments(), "orders");
```

```text
sales: 200000 orders
```

## A pipeline is a list of stages

You hand aggregation an **array** of stage objects. Each stage is named with a `$`-prefixed key - `$match`, `$group`, `$sort`, and so on. The canonical shape: filter the stream, fold it into groups, order the result. Here: the three best-selling fiction titles.

export const pipelineFlow = `flowchart LR
  In["sales documents"] --> M["$match: filter the stream"]
  M --> G["$group: fold into groups"]
  G --> S["$sort: order the groups"]
  S --> L["$limit: keep three"]
  L --> Out["result documents"]`

## How this differs from find

A `find` filters and projects, but always returns a subset of your *original* documents. Aggregation can do that too (`$match` and `$project`), and can also invent entirely new documents: counts, averages, joined records, flattened arrays.

- `find` reads documents out; aggregation **reshapes a stream** of them.
- `find` returns documents that already exist; aggregation can **synthesise** new ones.
- A pipeline is **ordered and composable** - stack stages like Lego.

The difference is measurable. Getting copies per fiction title by `find` and summing in the shell moves 40 000 documents to the client; the pipeline moves the 100 answers:

```js
// mongosh/agg-client-vs-server.js
const bytes = (docs) => docs.reduce((n, d) => n + bsonsize(d), 0);
let t = Date.now();
const all = db.sales.find({ genre: "fiction" }).toArray();              // pull every fiction order to the client ...
const totals = {};
for (const d of all) totals[d.title] = (totals[d.title] ?? 0) + d.quantity;   // ... and sum there
const clientMs = Date.now() - t;
t = Date.now();
const rows = db.sales.aggregate([{ $match: { genre: "fiction" } }, { $group: { _id: "$title", copies: { $sum: "$quantity" } } }]).toArray();
const serverMs = Date.now() - t;
console.log({ clientDocsTransferred: all.length, clientMB: +(bytes(all) / 1048576).toFixed(1), clientMs });
console.log({ serverDocsTransferred: rows.length, serverKB: +(bytes(rows) / 1024).toFixed(1), serverMs });
assert.strictEqual(rows.length, Object.keys(totals).length);
assert.ok(rows.every((r) => totals[r._id] === r.copies));
```

```text
{ clientDocsTransferred: 40000, clientMB: 3.7, clientMs: 159 }
{ serverDocsTransferred: 100, serverKB: 3, serverMs: 52 }
```

Same totals (the fence asserts it), about 1 000 times fewer bytes on the wire. On a real network the gap is far wider than these local milliseconds.

## The pipeline uses your indexes

A pipeline that starts with `$match` is planned like a `find` on that filter, so it can use an index. `explain` shows the plan of the first stage (the part that reads the collection) and the stages that remain; here the `$group` itself ran inside the same plan:

```js
// mongosh/agg-explain.js
const p = [{ $match: { price: { $gte: 24 } } }, { $group: { _id: "$genre", n: { $sum: 1 } } }];
console.log("with price_1  :", aplan(p));
db.sales.dropIndex("price_1");
console.log("without index :", aplan(p));
db.sales.createIndex({ price: 1 });
```

```text
with price_1  : GROUP > FETCH > IXSCAN(price_1)  keys=13422 docs=13422
without index : GROUP > COLLSCAN  keys=0 docs=200000
```

## Tips and gotchas

- Each stage sees only the previous stage's output: a field dropped early is gone for later stages.
- Start with `$match` so an index can help (13 422 keys instead of 200 000 documents above).
- A plain `find` is easier to read when you only filter; reach for a pipeline to summarise or build new documents.

<Callout title="Mental model">
An aggregation pipeline is an array of stages. Documents enter, each stage transforms the stream and passes it on, and the last stage's output is your result. Think of it as a conveyor belt, not a single query.
</Callout>

## Reading AI-generated code

Asked for "the top titles by copies sold", an assistant often keeps everything in application code:

<SpotTheBug lang="js" code={`// AI comment: "load the fiction orders, then total copies per title in JavaScript"
const orders = await db.collection("sales").find({ genre: "fiction" }).toArray();
const totals = {};
for (const o of orders) totals[o.title] = (totals[o.title] ?? 0) + o.quantity;
return Object.entries(totals).sort((a, b) => b[1] - a[1]).slice(0, 3);`}>

It is correct, and that is why it slips through review. It drags 40 000 documents (3.7 MB, 159 ms in the run above) through the driver and the application heap to keep three numbers, and the cost grows with the collection instead of with the answer. The pipeline computes the same totals inside the server and returns 100 rows (3 KB, 52 ms) - the fence in the previous section asserts the two agree. Use `$group` + `$sort` + `$limit` and let the database do the folding.

</SpotTheBug>

## Mental Model

Treat `find` as choosing rows and `aggregate` as writing a small data-flow program: each stage is a function from a stream of documents to a stream of documents. The cheap programs shrink the stream early (`$match`), then fold it (`$group`), and only then shape it for the client.

## Trade-offs

| Choice | Benefit | Cost |
|---------|---------|------|
| Aggregation pipeline | Summarises server-side: 100 rows instead of 40 000 documents | Harder to read than a plain query; debug stage by stage |
| find + application code | Simple; any logic | Moves every document first: 3.7 MB, 159 ms vs 3 KB, 52 ms |
| Many-stage pipeline | Compose one step at a time | Order affects both speed and correctness |

## Common Misconceptions

- **"Aggregation can always replace `find`."** - for plain filtering `find` is clearer and equally fast.
- **"Every stage sees the original collection."** - each sees only the previous stage's output.
- **"Aggregation ignores indexes."** - a leading `$match` used `price_1` (13 422 keys); without the index it scanned 200 000 documents.
- **"Summing in the app is fine, it's the same result."** - same result, 1 000 times the bytes.

MongoDB stores related data in separate collections often enough that you will sometimes need to stitch two of them back together. The `$lookup` stage does that join inside an aggregation pipeline: for each incoming document it finds matching documents in another collection and attaches them as an **array** field. The manual describes it as "a left outer join to a collection in the same database" ([$lookup](https://www.mongodb.com/docs/manual/reference/operator/aggregation/lookup/), consulted 2026-09-30): every input document comes through, with an empty array when nothing matches.

Captured on mongo 8.3.11, mongosh 2.11.1 and Node driver 7.7.0 on one Mac; Python, Go and Rust tabs were each run once in a scratch program. The lesson seeds the module's `sales` shape (20 000 orders here, to keep a per-document join quick) plus a `books` collection keyed by title (500 books; titles T500-T519 are sold but have no book), a `booksByTitle` copy with a plain `title` field, and `lplan()`, a helper that reports how the join was executed.

```js
// mongosh/lk-seed.js
const genres = ["fiction", "science", "history", "poetry", "comics"];
globalThis.lplan = (pipeline, coll = "sales") => {        // how the $lookup was executed
  const e = db.getCollection(coll).explain("executionStats").aggregate(pipeline);
  const q = e.queryPlanner?.winningPlan?.queryPlan;
  if (q) { for (let p = q; p; p = p.inputStage) if (p.stage === "EQ_LOOKUP") return "EQ_LOOKUP " + p.strategy + (p.indexName ? " on " + p.indexName : "") + " | executionTimeMillis " + e.executionStats.executionTimeMillis; }
  const l = (e.stages ?? []).find((s) => s.$lookup);
  return l ? "$lookup (no strategy reported) | keys " + l.totalKeysExamined + ", docs " + l.totalDocsExamined + ", indexes " + JSON.stringify(l.indexesUsed) : "no lookup stage";
};
db.sales.insertMany(Array.from({ length: 20000 }, (_, i) => ({ title: "T" + (i % 520), genre: genres[(i % 520) % 5], quantity: 1 + (i % 5), price: 5 + (i % 21), buyer: "b" + (i % 1000) })));
db.books.insertMany(Array.from({ length: 500 }, (_, i) => ({ _id: "T" + i, author: "A" + (i % 50), year: 1900 + (i % 120) })));   // T500..T519 have NO book
db.booksByTitle.insertMany(Array.from({ length: 500 }, (_, i) => ({ title: "T" + i, author: "A" + (i % 50), year: 1900 + (i % 120) })));
console.log("sales:", db.sales.countDocuments(), "| books:", db.books.countDocuments(), "(20 titles sold have no book)");
```

## The equality form: localField and foreignField

The simplest `$lookup` matches one local field against one foreign field: `from` (the collection), `localField`, `foreignField`, and `as` (the array field to add). The result is **always an array**, even when at most one document matches, because a join can in general match many. If `localField` is itself an array, each element is matched against the foreign field with no `$unwind` needed ([$lookup](https://www.mongodb.com/docs/manual/reference/operator/aggregation/lookup/), consulted 2026-09-30):

```js
// mongosh/lk-array-local.js
db.carts.insertOne({ _id: "c1", titles: ["T1", "T2", "T900"] });
const c = db.carts.aggregate([{ $lookup: { from: "books", localField: "titles", foreignField: "_id", as: "books" } }]).toArray()[0];
console.log("localField is an array ->", c.books.map((b) => b._id), "(T900 has no book; no $unwind needed)");
assert.strictEqual(c.books.length, 2);
```

```text
localField is an array -> [ 'T2', 'T1' ] (T900 has no book; no $unwind needed)
```

## Left outer, and how to make it inner

```js
// mongosh/lk-outer.js
const total = db.sales.countDocuments();
const joined = db.sales.aggregate([{ $lookup: { from: "books", localField: "title", foreignField: "_id", as: "book" } }, { $match: { book: { $size: 0 } } }, { $count: "noBook" }]).toArray()[0].noBook;
const inner = db.sales.aggregate([{ $lookup: { from: "books", localField: "title", foreignField: "_id", as: "book" } }, { $unwind: "$book" }, { $count: "n" }]).toArray()[0].n;
console.log({ orders: total, ordersWithNoBook: joined, afterUnwind: inner });
assert.strictEqual(total, joined + inner);
```

```text
{ orders: 20000, ordersWithNoBook: 760, afterUnwind: 19240 }
```

760 of the 20 000 orders reference a title with no book: they came through with `book: []`. A following `$unwind: "$book"` drops them (an inner join); `preserveNullAndEmptyArrays: true` keeps them.

## The pipeline form

When you need more than one equality - filtering or projecting the foreign side - use the **pipeline form**: declare `let` variables from the local document and run a sub-pipeline against the foreign collection, comparing with `$expr`. A single `$` in the sub-pipeline is a field of the *foreign* document; `$$t` is the `let` variable from the *local* one. Attaching only books published after 1950:

```js
// mongosh/lk-pipeline-form.js
const rows = db.sales.aggregate([
  { $match: { title: { $in: ["T7", "T60"] } } },
  { $group: { _id: "$title" } },
  { $sort: { _id: 1 } },
  { $lookup: { from: "books", let: { t: "$_id" },
      pipeline: [{ $match: { $expr: { $eq: ["$_id", "$$t"] } } }, { $match: { year: { $gt: 1950 } } }, { $project: { _id: 0, author: 1, year: 1 } }],
      as: "book" } },
]).toArray();
console.log(JSON.stringify(rows));
assert.ok(rows.every((r) => r.book.length === 0 || r.book[0].year > 1950));
```

```text
[{"_id":"T60","book":[{"author":"A10","year":1960}]},{"_id":"T7","book":[]}]
```

## Which join did the server run?

The review of the old lesson said `$lookup` has no strategy and "queries the foreign collection once per input document". Only one of those is true. `explain` reports the strategy chosen for the equality form: **IndexedLoopJoin** (an index lookup per input document), **HashJoin** (build a hash table of the foreign side once) or **NestedLoopJoin** (scan the foreign collection per input document). Same question, different foreign fields:

```js
// mongosh/lk-strategy.js
const eq = (from, foreignField) => [{ $lookup: { from, localField: "title", foreignField, as: "book" } }];
console.log("foreignField _id (always indexed)   :", lplan(eq("books", "_id")));
console.log("foreignField title, NO index        :", lplan(eq("booksByTitle", "title")));
db.booksByTitle.createIndex({ title: 1 });
console.log("foreignField title, index title_1   :", lplan(eq("booksByTitle", "title")));
const pipe = [{ $lookup: { from: "books", let: { t: "$title" }, pipeline: [{ $match: { $expr: { $eq: ["$_id", "$$t"] } } }], as: "book" } }];
console.log("pipeline form ($expr on _id)        :", lplan(pipe));
```

```text
foreignField _id (always indexed)   : EQ_LOOKUP IndexedLoopJoin on _id_ | executionTimeMillis 104
foreignField title, NO index        : EQ_LOOKUP HashJoin | executionTimeMillis 23
foreignField title, index title_1   : EQ_LOOKUP IndexedLoopJoin on title_1 | executionTimeMillis 107
pipeline form ($expr on _id)        : $lookup (no strategy reported) | keys 19240, docs 19240, indexes ["_id_"]
```

- **IndexedLoopJoin** - the foreign field has an index (`_id_` is always there).
- **HashJoin** - no index but a small foreign collection: one pass builds the hash table. Here it was faster (23 ms) than the indexed loop (107 ms).
- **Pipeline form** - no strategy is reported; the `$lookup` stage instead lists `totalKeysExamined: 19240`, `totalDocsExamined: 19240` and `indexesUsed: ["_id_"]` - one indexed lookup per input document.

### $lookup + $unwind is one stage

```js
// mongosh/lk-unwind.js
const p = [{ $lookup: { from: "books", localField: "title", foreignField: "_id", as: "book" } }, { $unwind: "$book" }];
const e = db.sales.explain().aggregate(p);
const l = e.stages.find((x) => x.$lookup).$lookup;
console.log("explain stages:", e.stages.map((x) => Object.keys(x)[0]).join(" > "), "(no separate $unwind stage)");
console.log("$lookup.unwinding:", JSON.stringify(l.unwinding), "| strategy fields:", Object.keys(l).filter((k) => /strategy|index|unwind/i.test(k)).join(", "));
console.log("rows with $unwind (inner join):", db.sales.aggregate([...p, { $count: "n" }]).toArray()[0].n);
console.log("rows with preserveNullAndEmptyArrays (left join):", db.sales.aggregate([p[0], { $unwind: { path: "$book", preserveNullAndEmptyArrays: true } }, { $count: "n" }]).toArray()[0].n);
```

```text
explain stages: $cursor > $lookup (no separate $unwind stage)
$lookup.unwinding: {"preserveNullAndEmptyArrays":false} | strategy fields: unwinding
rows with $unwind (inner join): 19240
rows with preserveNullAndEmptyArrays (left join): 20000
```

The optimizer coalesces `$lookup` + `$unwind` into a single stage (`unwinding` on the `$lookup`), so the matched documents are produced one at a time instead of first building the array.

Sharded collections: the `from` collection can be sharded starting in MongoDB 5.1 ([$lookup](https://www.mongodb.com/docs/manual/reference/operator/aggregation/lookup/), consulted 2026-09-30). This course runs unsharded, so that path is not exercised here.

## Tips and gotchas

- **Index the `foreignField`** (or whatever the sub-pipeline matches on): NestedLoopJoin over 50 000 books took 1 162 ms and IndexedLoopJoin 10 ms for the same join.
- It is a left outer join: filter empties with `$match` or make it inner with `$unwind`.
- `as` is always an array; pair with `$unwind` when you expect one match.
- Joining the same two collections on every read suggests the data wants to be embedded - see the data-modeling module.

<Callout title="Lookup attaches an array">
`$lookup` is a left outer join that hangs matched foreign documents on a new array field. The equality form joins one field to one field and reports a join strategy; the pipeline form filters and reshapes the foreign side. Index the foreign field: without an index a big foreign collection becomes a nested loop.
</Callout>

Nothing in `$lookup` makes the lookup O(1): it depends entirely on an index on `foreignField`. With no index on a 50 000-book catalogue, explain reports **NestedLoopJoin** and the join of just 100 orders took 1 006 ms; after `createIndex({ title: 1 })` the same pipeline reported IndexedLoopJoin and took 13 ms. ## Mental Model

`$lookup` is a loop that runs a query for you: for each input document, find matches on the other side. The only decision is how that inner query is served - an index probe, a hash table built once, or a scan - and `explain` names the choice. Index or small side = cheap; large unindexed side = a scan per row.

## Trade-offs

| Choice | Benefit | Cost |
|---------|---------|------|
| `$lookup` (reference) | No duplicated data; one place to update | Every read pays the join (an index probe per input row) |
| Embedding | One read, no join | Duplication; updates chase every copy |
| Pipeline form | Filter and reshape the foreign side | More complex; no join strategy reported |
| Equality form | Short; a strategy you can read in explain | One equality only |

## Common Misconceptions

- **"`$lookup` has no join strategy."** - explain showed IndexedLoopJoin, HashJoin and NestedLoopJoin for the equality form.
- **"It always queries the foreign collection once per input document."** - only in the loop cases; HashJoin built the table once and was 4-5x faster on a 500-book side.
- **"Unmatched documents are filtered out."** - 760 orders came through with `book: []`.
- **"A one-element `as` array is an object."** - it is an array; use `$unwind`.
- **"An index on the local side speeds the join."** - the probe hits the foreign side.

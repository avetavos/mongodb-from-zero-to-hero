A plain ascending index covers most needs, but MongoDB ships specialised index types for cases it cannot handle gracefully: fields that hold arrays, full-text search, documents that should expire on their own, indexes over only a slice of a collection, uniqueness, schemaless attributes, hashed lookups and locations. Each is a small variation on `createIndex`, and each has a trap that the plain documentation examples do not show. This lesson proves every one of them.

Captured on mongo 8.3.11, mongosh 2.11.1 and Node driver 7.7.0 on one Mac. The lesson seeds 100 000 `members` (10 cities, three borrowed titles each, 2% owing fines, half with a `cardNumber`, some with free-form `attrs`, each at a coordinate near Berlin) and reuses the one-line `plan()` helper. Python, Go and Rust tabs were each run once in a scratch program against the same server.

```js
// mongosh/types-seed.js
const cities = ["Berlin", "Paris", "Lima", "Oslo", "Cairo", "Tokyo", "Rome", "Lagos", "Dhaka", "Quito"];
globalThis.plan = (cur) => {                       // stage chain (also through TEXT/GEO stages), then keys and docs read
  const e = cur.explain("executionStats"), s = e.executionStats, stages = [];
  for (let p = e.queryPlanner.winningPlan; p; p = p.inputStage) stages.push(p.stage + (p.indexName ? "(" + p.indexName + ")" : ""));
  return stages.join(" > ") + "  returned=" + s.nReturned + " keys=" + s.totalKeysExamined + " docs=" + s.totalDocsExamined;
};
const colors = ["red", "green", "blue"];
for (let s = 0; s < 100000; s += 50000) {
  db.members.insertMany(Array.from({ length: 50000 }, (_, k) => {
    const i = s + k;
    const d = { name: "m" + i, city: cities[i % 10],
                borrowed: ["book" + (i % 500), "book" + ((i * 7) % 500), "book" + ((i * 13) % 500)],
                fines: i % 50 === 0 ? 1 + (i % 7) : 0,                       // only 2% of members owe anything
                location: { type: "Point", coordinates: [13 + (i % 100) / 100, 52 + (Math.floor(i / 100) % 100) / 100] } };
    if (i % 2 === 0) d.cardNumber = "C" + i;                                    // half the members have no card
    if (i % 3 === 0) d.attrs = { color: colors[i % 3 === 0 ? (i / 3) % 3 : 0] };   // schemaless attributes
    if (i % 5 === 0) d.attrs = Object.assign(d.attrs ?? {}, { size: "L" });
    return d;
  }), { ordered: false });
}
console.log("members:", db.members.countDocuments(), "| with fines:", db.members.countDocuments({ fines: { $gt: 0 } }), "| with cardNumber:", db.members.countDocuments({ cardNumber: { $exists: true } }));
```

## Multikey: indexing arrays

When you index a field that holds arrays, MongoDB makes it a **multikey** index automatically: one entry per array element, so a query for one title seeks straight to its owners. Nothing to configure - the values decide.


## Text: searching words

A **text index** tokenizes and stems string fields so `$text` can match words. The lesson used to say results are ranked by relevance; they are not, unless you ask. The server keeps the score and you must project and sort by `{ $meta: "textScore" }`:

<Tabs syncKey="lang">

    ```js
    console.log("no sort (index order)   :", plain);
    const ranked = db.tickets.find({ $text: { $search: "overdue reminder" } }, { score: { $meta: "textScore" } }).sort({ score: { $meta: "textScore" } }).toArray();
    console.log("sorted by textScore     :", ranked.map((d) => d.n + ":" + d.score.toFixed(2)).join("  "));
    console.log("plan                    :", plan(db.tickets.find({ $text: { $search: "overdue reminder" } })));
    ```

## TTL: documents that expire

A **TTL** index deletes documents once a date field is older than `expireAfterSeconds`. The field must be a BSON date (or an array containing dates): the manual states that you "specify an index field that is either a date type or an array that contains date type values", and that the background task "runs every 60 seconds" ([TTL indexes](https://www.mongodb.com/docs/manual/core/index-ttl/), consulted 2026-09-30). Creating it is one call; the first tab below also proves the type trap:

<Tabs syncKey="lang">
  <TabItem label="mongosh">

    ```js
    db.sessions2.insertMany([{ _id: "bug", createdAt: new Date().toISOString() }, { _id: "fix", createdAt: new Date() }]);
    console.log(db.sessions2.aggregate([{ $project: { _id: 1, type: { $type: "$createdAt" } } }]).toArray());
    assert.strictEqual(db.sessions2.findOne({ _id: "bug" }) !== null && db.sessions2.aggregate([{ $match: { _id: "bug" } }, { $project: { t: { $type: "$createdAt" } } }]).toArray()[0].t, "string");
    ```

To see the real timing, this run uses `expireAfterSeconds: 1` and polls. It is marked `@skip-verify` because it waits for the 60-second monitor and the course checker has a 90-second budget per lesson:

```js
// mongosh/types-ttl.js @skip-verify waits up to ~60 s for the TTL monitor (default sweep interval)
db.sessions.createIndex({ createdAt: 1 }, { expireAfterSeconds: 1 });
const t0 = Date.now();
db.sessions.insertMany([
  { _id: "date", createdAt: new Date() },
  { _id: "array", createdAt: [new Date(), new Date(Date.now() + 3600e3)] },
  { _id: "string", createdAt: new Date().toISOString() },                 // the trap: a string, not a Date
]);
let gone = null;
while (Date.now() - t0 < 125000) {
  if (gone === null && db.sessions.countDocuments({ _id: { $in: ["date", "array"] } }) === 0) gone = Math.round((Date.now() - t0) / 1000);
  sleep(1000);
}
console.log("Date and array-of-Date documents gone after", gone, "s (expireAfterSeconds was 1)");
console.log("after 125 s still stored:", db.sessions.find().toArray().map((d) => d._id));
```

```text
Date and array-of-Date documents gone after 14 s (expireAfterSeconds was 1)
after 125 s still stored: [ 'string' ]
```

The Date and array-of-Date documents disappeared within the monitor's 60-second cycle (14 s in this run - the phase depends on when the cycle last fired), never instantly. The ISO-string document was still there after 125 seconds, and always will be: TTL silently ignores non-date values.

## Partial: indexing a subset

A **partial** index covers only documents matching a filter, so it stays small when you query one slice. Only 2% of members owe fines, so the index below holds 2 000 entries instead of 100 000:

<Tabs syncKey="lang">
  <TabItem label="mongosh">
    ```js
    // mongosh/types-partial.js
    console.log(db.members.createIndex({ fines: 1 }, { partialFilterExpression: { fines: { $gt: 0 } }, name: "fines_owing" }));
    const kb = (n) => Math.round(n / 1024);
    db.members.createIndex({ fines: 1 }, { name: "fines_all" });
    const sz = db.members.stats().indexSizes;
    console.log("index sizes KB:", { fines_owing: kb(sz.fines_owing), fines_all: kb(sz.fines_all) });
    db.members.dropIndex("fines_all");
    console.log("fines > 2   :", plan(db.members.find({ fines: { $gt: 2 } })));
    console.log("fines = 0   :", plan(db.members.find({ fines: 0 })));
    console.log("fines >= 0  :", plan(db.members.find({ fines: { $gte: 0 } })));
    ```
  </TabItem>
  <TabItem label="Node.js">
    ```js
    // app/types-partial.mjs
    ```

## Unique, and why sparse is the wrong tool

A **unique** index rejects duplicates. The catch is optional fields: a missing field is indexed as `null`, and two `null`s are duplicates. The old lesson ran `unique`, then `unique + sparse` on the same key, which fails (same index name). The whole sequence, with real errors:

```js
// mongosh/types-unique.js
try { db.members.createIndex({ cardNumber: 1 }, { unique: true }); }              // half the members have no cardNumber
catch (e) { console.log("1. unique alone     :", e.codeName, "-", e.message.slice(e.message.indexOf("E11000"))); }
console.log("2. unique + sparse  :", db.members.createIndex({ cardNumber: 1 }, { unique: true, sparse: true }));
try { db.members.createIndex({ cardNumber: 1 }, { unique: true, partialFilterExpression: { cardNumber: { $exists: true } } }); }
catch (e) { console.log("3. switch to partial (same name):", e.codeName); }
db.members.dropIndex("cardNumber_1");
console.log("4. partial + unique :", db.members.createIndex({ cardNumber: 1 }, { unique: true, partialFilterExpression: { cardNumber: { $exists: true } }, name: "card_unique" }));
db.members.insertMany([{ name: "no card 1" }, { name: "no card 2" }]);
try { db.members.insertOne({ name: "dup", cardNumber: "C2" }); } catch (e) { console.log("   duplicate card     : code", e.code, JSON.stringify(e.keyValue)); }
console.log("   members without a card inserted:", db.members.countDocuments({ name: /^no card / }));
```

```text
1. unique alone     : DuplicateKey - E11000 duplicate key error collection: b2_e5a3dc.members index: cardNumber_1 dup key: { cardNumber: null }
2. unique + sparse  : cardNumber_1
3. switch to partial (same name): IndexKeySpecsConflict
4. partial + unique : card_unique
   duplicate card     : code 11000 {"cardNumber":"C2"}
   members without a card inserted: 2
```

Step 1 fails on the 50 000 members without a card (`dup key: { cardNumber: null }`). Step 2 works, but it is the wrong tool: a **sparse** index skips documents that lack the field, and a sparse index that the planner is forced to use for a sort returns incomplete results:

```js
// mongosh/types-sparse.js
db.cards.insertMany([{ n: 1, card: "b" }, { n: 2 }, { n: 3, card: "a" }]);
db.cards.createIndex({ card: 1 }, { sparse: true, name: "card_sparse" });
console.log("plain sort           :", db.cards.find().sort({ card: 1 }).toArray().map((d) => d.n));
console.log("sort with sparse hint:", db.cards.find().sort({ card: 1 }).hint("card_sparse").toArray().map((d) => d.n), "<- document 2 is missing");
assert.strictEqual(db.cards.find().sort({ card: 1 }).hint("card_sparse").toArray().length, 2);
```

```text
plain sort           : [ 2, 3, 1 ]
sort with sparse hint: [ 3, 1 ] <- document 2 is missing
```

Document 2 has no `card`, so the hinted plan drops it (2 of 3 documents); without the hint the planner refuses the sparse index and returns all three. The manual says the same: "MongoDB does not select the sparse index to fulfill the query in order to return complete results", and "Partial indexes can function as sparse indexes, but also support filter expressions ... Use a partial index for greater control" ([sparse indexes](https://www.mongodb.com/docs/manual/core/index-sparse/), consulted 2026-09-30). Step 4 above is the recommended shape: `unique` plus `partialFilterExpression: { cardNumber: { $exists: true } }` allows any number of card-less members and rejects a duplicate card. Switching an existing index to different options needs a drop first (step 3 returned `IndexKeySpecsConflict`).

## Three more you will meet

**Wildcard** - one index over a subtree whose keys you do not know in advance (`attrs.$**`). It is convenient for schemaless attributes but indexes every path, so it is larger and slower than a targeted index; note the conjunction below still used the one wildcard path and filtered the rest (11 112 keys for 2 223 results):

```js
// mongosh/types-wildcard.js
console.log(db.members.createIndex({ "attrs.$**": 1 }));
console.log("attrs.color = red :", plan(db.members.find({ "attrs.color": "red" })));
console.log("attrs.size  = L   :", plan(db.members.find({ "attrs.size": "L" })));
console.log("size = L AND color:", plan(db.members.find({ "attrs.size": "L", "attrs.color": "red" })));
```

```text
attrs.$**_1
attrs.color = red : FETCH > IXSCAN(attrs.$**_1)  returned=11112 keys=11112 docs=11112
attrs.size  = L   : FETCH > IXSCAN(attrs.$**_1)  returned=20000 keys=20000 docs=20000
size = L AND color: FETCH > IXSCAN(attrs.$**_1)  returned=2223 keys=11112 docs=11112
```

**Hashed** - stores a hash of the value: perfect for equality and for hash-based sharding, useless for ranges and sorts:

```js
// mongosh/types-hashed.js
console.log(db.members.createIndex({ name: "hashed" }));
console.log("name = m4242 :", plan(db.members.find({ name: "m4242" })));
console.log("name range   :", plan(db.members.find({ name: { $gte: "m4242", $lt: "m4243" } })));
console.log("sort by name :", plan(db.members.find().sort({ name: 1 }).limit(3)));
```


## Tips and gotchas

- A compound index can hold at most one array field (`cannot index parallel arrays`, code 171), and the error can appear later at insert time.
- `$text` does not rank unless you project and sort `textScore`; only one text index per collection.
- TTL deletes only BSON dates, within about 60 seconds, not instantly; a string date is never deleted.
- Prefer partial over sparse; a partial index serves only queries guaranteed to fall inside its filter.
- A unique index treats a missing field as `null`; without a partial filter only one document may lack it.

<Callout title="Pick the index that fits the shape of the data">
Most queries want a plain index, but arrays want multikey, words want text (and a score sort), expiring data wants TTL on a real date, a queried subset wants partial, optional unique values want partial + unique, unknown keys want wildcard, and locations want 2dsphere.
</Callout>

## Mental Model

Every special index type is the same B-tree with a different rule for **which entries go in** (multikey: each array element; partial/sparse: only some documents; wildcard: every path; hashed: the hash; TTL: a date the server watches) and **which questions it can answer** (text: word match plus score; 2dsphere: distance; hashed: equality only). If a query needs an entry that was never written, the index cannot help.

## Trade-offs

| Choice | Benefit | Cost |
|---------|---------|------|
| Multikey | Seek by any array element | ~3 entries per document here; one array field per compound index |
| Text | Word search with a score | One per collection; unranked unless you sort by textScore |
| TTL | Self-cleaning data, no cron | Up to ~60 s late; only real dates |
| Partial | 28 KB instead of 360 KB | Only queries inside the filter can use it |
| Unique (+ partial) | Database-level uniqueness with optional fields | Duplicate writes are rejected: handle E11000 |
| Wildcard | No need to know the keys | Indexes every path; weaker than a targeted index |
| Hashed | Even distribution, cheap equality | No ranges, no sort |

## Common Misconceptions

- **"`$text` results come back ranked."** - unsorted order was 5, 1, 4, 2; sorted by score 5, 4, 1, 2.
- **"TTL works on any timestamp-looking field."** - the ISO string survived 125 s; only dates are deleted.
- **"unique + sparse is how you make an optional field unique."** - use a partial filter; sparse loses documents on sorts.
- **"A partial index speeds up every query on the field."** - `fines = 0` and `fines >= 0` were COLLSCAN.
- **"A hashed index also helps ranges and sorts."** - both were COLLSCAN over 100 000 documents.
- **"TTL deletes at the exact second."** - within the 60-second monitor cycle, never instantly.

> Real-world example
>
> The MongoDB manual itself steers you away from sparse: "Partial indexes can function as sparse indexes, but also support filter expressions for conditions beyond whether a field exists" ([sparse indexes](https://www.mongodb.com/docs/manual/core/index-sparse/), consulted 2026-09-30), and warns that expired documents "may exist for some time beyond the 60 second period between runs of the background task" on a busy server ([TTL indexes](https://www.mongodb.com/docs/manual/core/index-ttl/), consulted 2026-09-30).

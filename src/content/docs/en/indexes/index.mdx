A query that returns the right answer can still be a slow query. When you ask MongoDB to find every member who joined in 2023, and there is nothing helping it, the server has only one option: open the collection at the first document and read forward, checking each one, until it has looked at every single document. That brute-force read is called a **collection scan**, and MongoDB labels it `COLLSCAN` in its diagnostics. On a handful of library members it is invisible. On a million documents it is the difference between a reply in a millisecond and a reply that crawls.

An **index** is the fix. It is a separate, ordered data structure that the server maintains alongside your collection, holding the values of one or more fields in sorted order, each paired with a pointer back to the full document. Because the values are sorted, the server can jump straight to the ones it wants instead of reading everything - the same reason you flip to the back of a textbook rather than reading every page to find a term. This module is about building the right index for the right query and proving the win with `explain`.

Every number below was captured on mongo 8.3.11, mongosh 2.11.1 and Node driver 7.7.0 on one Mac (single node, no load), so treat the milliseconds as orders of magnitude and the key/document counts as exact. Python, Go and Rust tabs were each run once in a scratch program against the same server.

## A scan versus a seek

Picture the two strategies side by side. Without an index, the query walks the entire collection. With an index, it descends a sorted tree and lands directly on the matching range:

export const scanVsIndexDiagram = `flowchart TB
  subgraph NoIndex["Without an index - COLLSCAN"]
    Q1["Query: joined equals 2023"] --> S0["Read doc 1"]
    S0 --> S1["Read doc 2"]
    S1 --> S2["Read doc 3"]
    S2 --> S3["...read every document"]
    S3 --> R1["Return the matches"]
  end
  subgraph WithIndex["With an index - IXSCAN"]
    Q2["Query: joined equals 2023"] --> B0["Index root"]
    B0 --> B1["Sorted branch"]
    B1 --> B2["Leaf: joined equals 2023"]
    B2 --> R2["Follow pointers to matching docs"]
  end`

## Measured on 1 000 000 documents

Every lesson seeds its own data. This one builds a million `members` (name, joined year, fines, city, one borrowed book) and defines `plan()`, a helper that condenses `explain("executionStats")` into one line: the stage chain, then `returned` (results), `keys` (index entries read) and `docs` (documents read).

```js
// mongosh/idx-seed.js
const cities = ["Berlin", "Paris", "Lima", "Oslo", "Cairo", "Tokyo", "Rome", "Lagos", "Dhaka", "Quito"];
const mk = (i) => ({ name: "m" + i, joined: NumberInt(2000 + (i % 26)), fines: i % 7, city: cities[i % 10], borrowed: ["b" + (i % 500)] });
globalThis.mk = mk;
globalThis.plan = (cur) => {                       // one line per explain: stages, then the work counters
  const e = cur.explain("executionStats"), s = e.executionStats, stages = [];
  for (let p = e.queryPlanner.winningPlan; p; p = p.inputStage) stages.push(p.stage + (p.indexName ? "(" + p.indexName + ")" : ""));
  return stages.join(" > ") + "  returned=" + s.nReturned + " keys=" + s.totalKeysExamined + " docs=" + s.totalDocsExamined + " " + s.executionTimeMillis + "ms";
};
const t = Date.now();
for (let s = 0; s < 1000000; s += 50000) {
  db.members.insertMany(Array.from({ length: 50000 }, (_, k) => mk(s + k)), { ordered: false });
}
console.log("members:", db.members.countDocuments(), "docs, seeded in", Date.now() - t, "ms");
assert.strictEqual(db.members.countDocuments(), 1000000);
```

```text
members: 1000000 docs, seeded in 6079 ms
```

```js
assert.strictEqual(db.members.find({ name: "m777777" }).explain("executionStats").executionStats.totalDocsExamined, 1000000);

```

### An index is not always a win: selectivity

The index helps because it lets the server skip documents. When the filter keeps most of the collection, there is little to skip. `joined` has only 26 distinct values, so `joined: 2023` keeps 3.8% of the data, but a range that keeps every document is a different story. `hint()` forces a plan so we can compare:

```js
// mongosh/idx-selectivity.js
db.members.createIndex({ joined: 1 });
console.log("joined = 2023 (3.8% of docs), index :", plan(db.members.find({ joined: 2023 })));
console.log("joined = 2023, forced COLLSCAN       :", plan(db.members.find({ joined: 2023 }).hint({ $natural: 1 })));
console.log("all members, index scan forced       :", plan(db.members.find({ joined: { $gte: 2000 } }).hint({ joined: 1 })));
console.log("all members, forced COLLSCAN         :", plan(db.members.find({ joined: { $gte: 2000 } }).hint({ $natural: 1 })));
```

```text
joined = 2023 (3.8% of docs), index : FETCH > IXSCAN(joined_1)  returned=38461 keys=38461 docs=38461 35ms
joined = 2023, forced COLLSCAN       : COLLSCAN  returned=38461 keys=0 docs=1000000 291ms
all members, index scan forced       : FETCH > IXSCAN(joined_1)  returned=1000000 keys=1000000 docs=1000000 993ms
all members, forced COLLSCAN         : COLLSCAN  returned=1000000 keys=0 docs=1000000 293ms
```

The two forced plans for "everyone" read the same number of documents, but the index route also read 1 000 000 keys first (about 3x slower here). Low-selectivity filters gain little; the planner weighs this for you, which is why `explain` (not intuition) decides.

## What an index costs

**Disk and memory.** Each index is a separate structure. On this collection the data is about 100 MB, and the indexes take:

```js
// mongosh/idx-size.js
const s = db.members.stats(), mb = (n) => +(n / 1048576).toFixed(1);
console.log({ dataMB: mb(s.size), indexMB: Object.fromEntries(Object.entries(s.indexSizes).map(([k, v]) => [k, mb(v)])) });
assert.ok(s.indexSizes.name_1 > 0);
```

```text
{ dataMB: 100.6, indexMB: { _id_: 26.9, name_1: 11.9, joined_1: 5.3 } }
```

**Write time.** Every insert, update of an indexed field, or delete must also change every index. Same 200 000 documents, once into a collection with only `_id_`, once into one with five extra indexes:

```js
// mongosh/idx-write-cost.js
function bulkLoad(coll, n) {
  const t = Date.now();
  for (let s = 0; s < n; s += 10000) coll.insertMany(Array.from({ length: 10000 }, (_, k) => mk(s + k)), { ordered: false });
  return Date.now() - t;
}
const bare = bulkLoad(db.w0, 200000);
["name", "joined", "fines", "city", "borrowed"].forEach((f) => db.w5.createIndex({ [f]: 1 }));
const heavy = bulkLoad(db.w5, 200000);
console.log("200 000 inserts, _id index only    :", bare, "ms");
console.log("200 000 inserts, _id + 5 indexes   :", heavy, "ms");
assert.ok(heavy > bare);
```

```text
200 000 inserts, _id index only    : 1244 ms
200 000 inserts, _id + 5 indexes   : 2240 ms
```

MongoDB caps a collection at 64 indexes and a compound index at 32 fields ([MongoDB limits](https://www.mongodb.com/docs/manual/reference/limits/), consulted 2026-09-30), but the practical ceiling is your write budget long before that.

### Finding indexes nobody uses

`$indexStats` counts how often each index served a query since the server started. An index at `ops: 0` is a candidate to remove. Before dropping it, `hideIndex()` keeps the index maintained but invisible to the planner, so you can watch for regressions and `unhideIndex()` instantly if something slows down - no rebuild:

```js
// mongosh/idx-unused.js
db.members.find({ name: "m1" }).toArray();
db.members.find({ joined: 2023 }).limit(1).toArray();
const usage = db.members.aggregate([{ $indexStats: {} }, { $project: { _id: 0, name: 1, ops: "$accesses.ops" } }, { $sort: { name: 1 } }]).toArray();
console.log(usage);
db.members.hideIndex("joined_1");
console.log("joined_1 hidden:", plan(db.members.find({ joined: 2023 })));
db.members.unhideIndex("joined_1");
console.log("joined_1 visible again:", plan(db.members.find({ joined: 2023 })));
```

```text
[
  { name: '_id_', ops: Long('0') },
  { name: 'joined_1', ops: Long('1') },
  { name: 'name_1', ops: Long('2') }
]
joined_1 hidden: COLLSCAN  returned=38461 keys=0 docs=1000000 305ms
joined_1 visible again: FETCH > IXSCAN(joined_1)  returned=38461 keys=38461 docs=38461 29ms
```

## What this module covers

The lessons build from one field to the full toolbox:

1. **Why indexes matter** - scans versus seeks, and the cost of having none or too many.
2. **Single and compound indexes** - the prefix rule that decides which queries a compound index can serve.
3. **The ESR rule** - Equality, Sort, Range ordering, measured.
4. **Explain and query plans** - reading `explain`, rejected plans, the plan cache and covered queries.
5. **Index types** - multikey, text, TTL, partial, unique, sparse, wildcard, hashed and geospatial.

## Tips and gotchas

- Every collection starts with one unique index on `_id`. You cannot drop it.
- `createIndex` returns the index name as a plain string (`"name_1"`), and creating an index that already exists is a no-op - but the same key with different options is an error (see below).
- Indexes cost disk, memory and write time (about 11.9 MB and a slower insert for one string field here). Index what queries use, and use `$indexStats` to find the rest.
- Low-selectivity fields (26 years, 7 fine values) rarely justify a standalone index; put them behind a selective field in a compound index.

An index trades extra write cost and storage for the ability to find documents by seeking through sorted values instead of scanning every document. The rest of this module is just choosing which fields to sort.
</Callout>

## Reading AI-generated code

An assistant asked to "make the member lookup fast" will often write this, with the reassuring comment:

<SpotTheBug lang="js" code={`// AI comment: "make sure the index exists, then query"
app.get("/members/:email", async (req, res) => {
  const members = db.collection("members");
  await members.createIndex({ email: 1 }, { unique: true });   // safe: createIndex is idempotent
  res.json(await members.findOne({ email: req.params.email }));
});`}>

The comment is half right: `createIndex` is idempotent, so the repeated call does not rebuild anything. But it is not free, and it is not safe. Run 500 times against an existing index it cost a round trip each time (numbers below), and the moment the option set changes - here a later deploy adds `unique: true` to the same key - **every request** throws instead of just the first, because the index `email_1` already exists with different options. Index management belongs in a startup/migration step, run once, with an explicit `name`:

```js
// mongosh/idx-handler-bug.js
db.people.insertMany(Array.from({ length: 200 }, (_, i) => ({ email: "p" + i + "@x.test" })));
db.people.createIndex({ email: 1 });                       // deploy 1: plain index
let t = Date.now();
for (let i = 0; i < 500; i++) db.people.createIndex({ email: 1 });   // "make sure the index exists" on every request
console.log("500 repeated createIndex calls:", Date.now() - t, "ms, indexes:", db.people.getIndexes().length);
try { db.people.createIndex({ email: 1 }, { unique: true }); }      // deploy 2: same key, new option
catch (e) { console.log(e.codeName + ":", e.message); }
assert.strictEqual(db.people.getIndexes().length, 2);
db.people.dropIndex("email_1");
console.log("fixed startup script:", db.people.createIndex({ email: 1 }, { unique: true, name: "email_unique" }));
```

```text
500 repeated createIndex calls: 158 ms, indexes: 2
IndexKeySpecsConflict: An existing index has the same name as the requested index. When index names are not specified, they are auto generated and can cause conflicts. Please refer to our documentation. Requested index: { v: 2, unique: true, key: { email: 1 }, name: "email_1" }, existing index: { v: 2, key: { email: 1 }, name: "email_1" }
fixed startup script: email_unique
```

The fix only ran cleanly after dropping the old non-unique index first: changing an index means an explicit drop-and-create (or `collMod` for a few properties), never a silent re-create.

</SpotTheBug>

## Mental Model

An index is a second, sorted copy of some fields with pointers back. A read that can use it pays for the matching entries only; every write pays for the data and for every index that mentions a changed field. The decision is always **reads saved versus writes and memory spent**, and `explain` is the ledger.

## Trade-offs

| Choice | Benefit | Cost |
|---------|---------|------|
| Index the fields your queries use often | COLLSCAN of 1 000 000 documents becomes 1 key and 1 document | Extra disk (11.9 MB for `name_1`) and slower writes |
| Create no indexes | Fastest inserts, nothing to maintain | Every query is a COLLSCAN that grows with the data |
| Index a low-selectivity field alone | Helps a rare value | Little gain when the filter keeps most documents; still pays write cost |
| Hide before dropping | Reversible test of "is this index needed" | Still pays write cost while hidden |

## Common Misconceptions

- **"An index always makes a query faster."** - a filter that keeps every document read 1 000 000 keys and 1 000 000 documents through the index, no better than a scan.
- **"Indexes are free reads-only helpers."** - five extra indexes made the same 200 000 inserts slower (numbers above).
- **"Calling `createIndex` on every startup or request is harmless."** - it is a no-op only while the options are identical; changed options raise `IndexKeySpecsConflict`.
- **"An unused index is harmless."** - it is still updated on every write and held in cache; `$indexStats` shows which ones are idle.

The previous lesson left a question hanging: when you build a compound index for a query, what order should the fields go in? The answer is a short, memorable rule called **ESR** - **Equality, Sort, Range**. List the fields your query matches exactly first, then the field you sort on, then any field you query as a range. Follow that order and one index can satisfy the filter, the sort and the range in a single pass, with no in-memory sort.

Numbers below come from mongo 8.3.11 and mongosh 2.11.1 on one Mac (Node driver 7.7.0 for the Node tab). Data: 200 000 members, 10 cities (20 000 in Berlin), `fines` 0-6, `joined` 26 years, `score` 0-999. The lesson seeds itself and reuses the one-line `plan()` helper (stages, results, index keys, documents read).

```js
// mongosh/esr-seed.js
const cities = ["Berlin", "Paris", "Lima", "Oslo", "Cairo", "Tokyo", "Rome", "Lagos", "Dhaka", "Quito"];
globalThis.plan = (cur) => {
  const e = cur.explain("executionStats"), s = e.executionStats, stages = [];
  for (let p = e.queryPlanner.winningPlan; p; p = p.inputStage) stages.push(p.stage + (p.indexName ? "(" + p.indexName + ")" : ""));
  return stages.join(" > ") + "  returned=" + s.nReturned + " keys=" + s.totalKeysExamined + " docs=" + s.totalDocsExamined;
};
for (let s = 0; s < 200000; s += 50000) {
  db.members.insertMany(Array.from({ length: 50000 }, (_, k) => {
    const i = s + k;
    return { name: "m" + i, joined: NumberInt(2000 + (Math.floor(i / 10) % 26)), fines: i % 7,
             score: Math.floor(i / 10) % 1000, city: cities[i % 10] };
  }), { ordered: false });
}
const q = { city: "Berlin", fines: { $gt: 2 } };
console.log("members:", db.members.countDocuments(), "| Berlin:", db.members.countDocuments({ city: "Berlin" }), "| Berlin with fines > 2:", db.members.countDocuments(q));
```

```text
members: 200000 | Berlin: 20000 | Berlin with fines > 2: 11428
```

## The query we are optimizing

Every Berlin member with more than two fines, sorted by join year. Three fields, three roles:

- `city` - an **equality**: exactly one value.
- `joined` - the **sort** field.
- `fines` - a **range**: `$gt: 2`, a span of values.

## Applying ESR

ESR gives `{ city: 1, joined: 1, fines: 1 }`. To compare, we also build the tempting wrong order that puts the range before the sort, `{ city: 1, fines: 1, joined: 1 }` (Equality, Range, Sort), and give both explicit names:

```js
// mongosh/esr-create.js
console.log(db.members.createIndex({ city: 1, joined: 1, fines: 1 }, { name: "ESR" }));   // Equality, Sort, Range
console.log(db.members.createIndex({ city: 1, fines: 1, joined: 1 }, { name: "ERS" }));   // Equality, Range, Sort
```

```text
ESR
ERS
```

The Node.js tab builds the ESR index on its own 5 000-document collection and checks the plan has no `SORT` stage:

```js
// app/esr-index.mjs
const c = db.collection("members");
await c.insertMany(Array.from({ length: 5000 }, (_, i) => ({ city: ["Berlin", "Oslo"][i % 2], joined: 2000 + (i % 26), fines: i % 7 })));
await c.createIndex({ city: 1, joined: 1, fines: 1 }, { name: "ESR" });
const e = await c.find({ city: "Berlin", fines: { $gt: 2 } }).sort({ joined: 1 }).explain("queryPlanner");
const stages = []; for (let p = e.queryPlanner.winningPlan; p; p = p.inputStage) stages.push(p.stage);
console.log(stages.join(" > "));
if (stages.includes("SORT")) throw new Error("ESR order should not need a SORT");
```

```text
FETCH > IXSCAN
```

## Measuring the three orders

```js
// mongosh/esr-measure.js
const q = { city: "Berlin", fines: { $gt: 2 } };
console.log("ESR  {city, joined, fines}:", plan(db.members.find(q).sort({ joined: 1 }).hint("ESR")));
console.log("ERS  {city, fines, joined}:", plan(db.members.find(q).sort({ joined: 1 }).hint("ERS")));
console.log("planner, no hint          :", plan(db.members.find(q).sort({ joined: 1 })));
const ex = db.members.find(q).sort({ joined: 1 }).explain();
console.log("rejected plans            :", ex.queryPlanner.rejectedPlans.map((p) => { let s = p; while (s.inputStage) s = s.inputStage; return s.indexName; }));
const ids = (n) => db.members.find(q, { _id: 1, joined: 1 }).sort({ joined: 1 }).hint(n).toArray().map((d) => d.joined).join();
assert.strictEqual(ids("ESR"), ids("ERS"));                                    // same join-year order from both indexes
assert.ok(!plan(db.members.find(q).sort({ joined: 1 }).hint("ESR")).includes("SORT"));
assert.ok(plan(db.members.find(q).sort({ joined: 1 }).hint("ERS")).includes("SORT"));
```

```text
ESR  {city, joined, fines}: FETCH > IXSCAN(ESR)  returned=11428 keys=11455 docs=11428
ERS  {city, fines, joined}: FETCH > SORT > IXSCAN(ERS)  returned=11428 keys=11428 docs=11428
planner, no hint          : FETCH > IXSCAN(ESR)  returned=11428 keys=11455 docs=11428
rejected plans            : [ 'ERS' ]
```

The ESR index returned the 11 428 results in join order straight from the index: 11 455 keys examined (27 more than results - the server skipped ahead between `joined` values) and **no `SORT` stage**. The E-R-S index found the same 11 428 keys but they come out grouped by `fines`, not by `joined`, so the plan inserts `FETCH > SORT > IXSCAN`: all 11 428 entries are sorted in memory before any document is fetched. Left alone, the planner chose ESR and listed ERS under `rejectedPlans`. Same answer, different work - and the SORT is the part that grows with the result size and hits the memory ceiling.

`hint()` (used above) forces a named index so you can compare orders side by side; do not leave it in production code, because it stops the planner adapting when data changes.

### With a limit, the gap widens

```js
// mongosh/esr-limit.js
const q = { city: "Berlin", fines: { $gt: 2 } };
console.log("ESR  first 20:", plan(db.members.find(q).sort({ joined: 1 }).limit(20).hint("ESR")));
console.log("ERS  first 20:", plan(db.members.find(q).sort({ joined: 1 }).limit(20).hint("ERS")));
```

```text
ESR  first 20: LIMIT > FETCH > IXSCAN(ESR)  returned=20 keys=21 docs=20
ERS  first 20: FETCH > SORT > IXSCAN(ERS)  returned=20 keys=11428 docs=20
```

An ordered index lets the server stop after the first 20 entries (21 keys, 20 documents). The wrong order must still read and sort all 11 428 keys to know which 20 come first.

**In Compass:** build the candidate index in the **Indexes** tab, then run the query in the **Explain Plan** tab. When ESR is satisfied the sort is handled by the index; when it is not, the plan shows an explicit sort stage.

## When the rule loses

ESR minimizes sorting, not keys read. If the range is *very* selective and the sort field has many distinct values, walking every key in sort order to test the range can cost more than sorting the few survivors. Berlin members with `score >= 995` are 100 of 20 000, sorted by `name` (unique):

```js
// mongosh/esr-exception.js
db.members.createIndex({ city: 1, name: 1, score: 1 }, { name: "ESR_name" });     // Equality, Sort, Range
db.members.createIndex({ city: 1, score: 1, name: 1 }, { name: "ERS_name" });     // Equality, Range, Sort
const q = { city: "Berlin", score: { $gte: 995 } };                                   // a very selective range: 100 of 20 000
console.log("ESR  all 100 :", plan(db.members.find(q).sort({ name: 1 }).hint("ESR_name")));
console.log("ERS  all 100 :", plan(db.members.find(q).sort({ name: 1 }).hint("ERS_name")));
console.log("ESR  first 20:", plan(db.members.find(q).sort({ name: 1 }).limit(20).hint("ESR_name")));
console.log("ERS  first 20:", plan(db.members.find(q).sort({ name: 1 }).limit(20).hint("ERS_name")));
console.log("Same query, sort on joined (26 distinct values):");
db.members.createIndex({ city: 1, joined: 1, score: 1 }, { name: "ESR_joined" });
console.log("ESR joined   :", plan(db.members.find(q).sort({ joined: 1 }).hint("ESR_joined")));
```

```text
ESR  all 100 : FETCH > IXSCAN(ESR_name)  returned=100 keys=20001 docs=100
ERS  all 100 : FETCH > SORT > IXSCAN(ERS_name)  returned=100 keys=100 docs=100
ESR  first 20: LIMIT > FETCH > IXSCAN(ESR_name)  returned=20 keys=4446 docs=20
ERS  first 20: FETCH > SORT > IXSCAN(ERS_name)  returned=20 keys=100 docs=20
Same query, sort on joined (26 distinct values):
ESR joined   : FETCH > IXSCAN(ESR_joined)  returned=100 keys=127 docs=100
```

Here ESR reads every Berlin key (20 001) to find 100 matches, while E-R-S seeks straight to the 100 and sorts them. With a `limit(20)`, ESR stops after 4 446 keys, still about 44x more than E-R-S. The last line shows the flip side: sorting on `joined`, which has only 26 distinct values, ESR reads 127 keys - the server hops between the 26 values - so the exception needs a high-cardinality sort field. That is why the rule is a default to confirm with `explain`, not a law.

## Tips and gotchas

- ESR is a default, not a law: confirm with `explain` on your data, and compare orders with `hint()`.
- Equality fields (several are fine) all go first, the single sort field next, range fields last.
- The payoff is removing the blocking SORT (and its memory ceiling), and stopping early with `limit`.

Order compound index fields by how the query uses them: exact matches first, the sort field next, range comparisons last. That ordering lets one index narrow, order and scan without a separate sort - unless a very selective range on a high-cardinality sort makes the opposite order cheaper. Measure.
</Callout>

Containing the sort field is not the same as being ordered for it. Because `fines` is a range, the keys come out grouped by `fines` and the plan still has a blocking `SORT`. Comparing the AI's index with the ESR one:

## Mental Model

Picture the index as a sorted list of tuples. An equality pins the first coordinate, so you are inside one sorted sub-list. If the next coordinate is the sort field, that sub-list is already in the order you want. If the next coordinate is a range, you are reading several sorted runs (one per range value) that must be merged - which is exactly what the SORT stage does.

## Trade-offs

| Choice | Benefit | Cost |
|---------|---------|------|
| ESR order | No SORT stage; stops early with `limit` (21 keys for 20 rows) | May read more keys when the range is very selective (20 001 vs 100) |
| E-R-S order (range before sort) | Fewest keys for a very selective range | Blocking in-memory SORT; cannot stop early (11 428 keys for 20 rows) |
| Order fields ad hoc | Fast to write | Each query shape needs another index |

## Common Misconceptions

- **"If the sort field is in the index, the sort is free."** - only if the fields before it are equalities; after a range the SORT stage came back.
- **"ESR always reads the fewest keys."** - it minimizes sorting; the selective-range case read 20 001 keys versus 100.
- **"A wrong order returns wrong results."** - results were identical; only the work differed.
- **"Leave `hint()` in as a safeguard."** - it freezes the plan and blocks the planner from adapting.

> Real-world example
>
> MongoDB documents this exact ordering as "The ESR (Equality, Sort, Range) Guideline" and states the same exception measured above: "If the range predicate in your query is very selective, then put it before sort fields" ([ESR Guideline](https://www.mongodb.com/docs/manual/tutorial/equality-sort-range-guideline/), consulted 2026-09-30).

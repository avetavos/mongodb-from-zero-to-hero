If you arrive at MongoDB from a relational background, the hardest habit to unlearn is the one that served you best in SQL: splitting your data into many narrow tables joined back together at query time. That discipline is **normalization**; it removes duplication so a fact lives in exactly one place. MongoDB asks you to think the other way around. You start from "what does my application ask for, and how can a single read hand back everything one screen needs."

The unit of storage is the **document** - a nested, JSON-like structure with arrays and sub-objects. Because a document can hold related data inside itself, the question behind every modeling decision is: **"do I nest this related data inside the document, or keep it separate and store a reference?"** That choice - embedding versus referencing - is what this module turns on.

**Datasets in this module.** Each lesson seeds its own data with the same shape: `products` (`_id: "BK-n"`, `title`, `price`) and orders in two versions - `ordersEmb` (items carry a copy of the title and price) and `ordersRef` (items carry only `productId`). This lesson uses 500 products and 10 000 orders of 2-5 items. Captured on mongo 8.3.11, mongosh 2.11.1 and Node driver 7.7.0 on one Mac; Python, Go and Rust tabs were each run once in a scratch program.

```js
// mongosh/dm-seed.js
const rnd = (() => { let x = 7; return () => (x = (Math.imul(x, 1103515245) + 12345) >>> 0) / 4294967296; })();   // repeatable pseudo-random numbers
db.products.insertMany(Array.from({ length: 500 }, (_, i) => ({ _id: "BK-" + i, title: "Book " + i, price: 10 + (i % 40) })));
const specs = Array.from({ length: 10000 }, (_, i) => ({
  _id: "order_" + i, customerId: "cust_" + (i % 500), status: i % 3 ? "shipped" : "new",
  lines: Array.from({ length: 2 + Math.floor(rnd() * 4) }, () => { const p = Math.floor(rnd() * 500); return { p, qty: 1 + Math.floor(rnd() * 3) }; }),
}));
db.ordersEmb.insertMany(specs.map(({ lines, ...o }) => ({ ...o, items: lines.map((l) => ({ sku: "BK-" + l.p, title: "Book " + l.p, qty: l.qty, price: 10 + (l.p % 40) })) })));   // embedded copies
db.ordersRef.insertMany(specs.map(({ lines, ...o }) => ({ ...o, items: lines.map((l) => ({ productId: "BK-" + l.p, qty: l.qty })) })));                                 // references only
console.log("products:", db.products.countDocuments(), "| orders:", db.ordersEmb.countDocuments(), "embedded /", db.ordersRef.countDocuments(), "referenced");
```

## Relational habits versus document thinking

In a relational schema you design around the data's shape and let queries pay the cost of reassembling it. In a document schema you design around the queries and decide duplication up front:

export const mindsetDiagram = `flowchart TB
  subgraph Relational["Relational - model for storage"]
    R0["Start: list the entities"] --> R1["Split into normalized tables"]
    R1 --> R2["No duplication - one fact, one place"]
    R2 --> R3["Reassemble with JOINs at read time"]
  end
  subgraph Document["Document - model for access"]
    D0["Start: list the queries"] --> D1["Group data that is read together"]
    D1 --> D2["Embed or reference based on access"]
    D2 --> D3["One read returns a whole screen"]
  end`

<Mermaid code={mindsetDiagram} title="Relational design optimizes storage and pays at read time; document design optimizes the read and decides duplication up front" />

Neither is universally correct. The relational instinct is excellent when data is highly interrelated and updated from many directions; the document instinct shines when an application repeatedly fetches the same shaped bundle - a user and settings, an order and its line items, an article and its tags.

Embedding costs about 40% more bytes per order (303 vs 216 on average, 2.89 MB vs 2.06 MB for the collection) because each item repeats a title and price - copies that can drift from `products`. What it buys is a read that needs one query. Timing 2 000 order-detail reads on the local server:

```js
// mongosh/dm-reads.js
const ids = Array.from({ length: 2000 }, (_, i) => "order_" + ((i * 37) % 10000));
const time = (f) => { const t = Date.now(); f(); return Date.now() - t; };
const emb = time(() => ids.forEach((id) => db.ordersEmb.findOne({ _id: id })));
const ref = time(() => ids.forEach((id) => { const o = db.ordersRef.findOne({ _id: id }); db.products.find({ _id: { $in: o.items.map((i) => i.productId) } }).toArray(); }));
const lookup = time(() => ids.forEach((id) => db.ordersRef.aggregate([{ $match: { _id: id } }, { $unwind: "$items" }, { $lookup: { from: "products", localField: "items.productId", foreignField: "_id", as: "p" } }]).toArray()));
console.log("2 000 order-detail reads (each needs titles and prices):");
console.log({ embedded_1_query: emb + " ms", referenced_2_queries: ref + " ms", referenced_1_lookup_aggregate: lookup + " ms" });
```

One query took 591 ms for the 2 000 reads; two queries per order 1 104 ms; a single `$lookup` aggregate per order 662 ms. There is no network in this test, so on a real network - where each round trip costs milliseconds - the gap grows with the number of round trips, not with the CPU.

## Tips and gotchas

- MongoDB is **schema-flexible**, not schema-less: documents can differ, but a deliberate, consistent shape keeps a collection fast and maintainable.
- "Model for your queries" means knowing your main access patterns *before* you design; a schema perfect for one read may be wrong for another.
- Duplication is allowed and sometimes desirable: the cost of a copy is keeping it in sync, the benefit is a faster, simpler read.
- A per-item loop over a referenced collection is the classic N+1: 4 queries for a 3-item order.

<Callout title="Model for access, not for storage">
The relational reflex asks "where does this data belong so I never repeat it." The document reflex asks "what does my application read together, so it can read it in one shot." Start every schema from the queries and the embed-or-reference decision follows.
</Callout>

## Reading AI-generated code

Asked to "render an order with product titles", an assistant normalizes like SQL and resolves each item on its own:

<SpotTheBug lang="js" code={`// AI comment: "products live in their own collection - single source of truth"
const order = await db.collection("ordersRef").findOne({ _id });
for (const item of order.items) {
  item.product = await db.collection("products").findOne({ _id: item.productId });
}
return order;`}>

The design is fine; the loop is the bug. It is the N+1 pattern: one query for the order plus one per item. The profiler in the Node.js tab counted **4** queries for a 3-item order, against **1** for the embedded shape and **2** for a single `$in` lookup of all product ids - and the difference multiplies by every page view. Batch the ids into one `find({ _id: { $in: [...] } })` (the two-query version shown in the Python, Go and Rust tabs), use a `$lookup` aggregate, or embed the fields the page always shows.

</SpotTheBug>

## Mental Model

Every relationship is a bet on which side of the read you want to pay for. Embedding pays at write time and in bytes (303 vs 216 per order, copies to keep in sync) to make the common read one query. Referencing pays at read time (2 queries, or a `$lookup`) to keep each fact in one place. Decide per relationship, from the queries.

## Trade-offs

| Choice | Benefit | Cost |
|---------|---------|------|
| Embedding | One query (591 ms for 2 000 reads); atomic writes | Bigger documents (303 vs 216 bytes); copies can drift; growth risk |
| Referencing | Small, stable documents; one copy of each fact | 2 queries or a `$lookup` per read (1 104 / 662 ms) |
| Bucket pattern | Fewer documents for high-volume series | Bucket size chosen in advance; grouping logic |

## Common Misconceptions

- **"MongoDB has no schema."** - every document has a shape; the database only enforces it if you add validation.
- **"There is one correct schema per entity."** - the same order was 303 or 216 bytes depending on the access pattern.
- **"A schema cannot change later."** - it can; you write the migration and plan the rollout (see schema validation).
- **"Referencing is the clean way, embedding is a shortcut."** - the referenced order needed 2-4 queries for the same page.

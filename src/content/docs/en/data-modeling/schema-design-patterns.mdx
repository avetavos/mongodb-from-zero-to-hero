Once you can choose between embedding and referencing you keep meeting the same problems: a document carrying far more than one screen needs, a value expensive to recompute on every read, an array that wants to grow forever, a reference that forces a lookup just to show one field. The MongoDB community named the recurring solutions **schema design patterns** ([Building with Patterns](https://www.mongodb.com/blog/post/building-with-patterns-a-summary), consulted 2026-09-30; the Bucket pattern has [its own post](https://www.mongodb.com/blog/post/building-with-patterns-the-bucket-pattern)). They are not features you switch on - they are shapes you give your documents. This lesson runs four of them and measures what each buys and costs.

Captured on mongo 8.3.11, mongosh 2.11.1 and Node driver 7.7.0 on one Mac; Python, Go and Rust tabs were each run once in a scratch program. The seed builds one popular product with 10 000 reviews stored two ways (one fat document, and a subset document plus a `reviews` collection).


## The Subset pattern

**Problem:** a document embeds a large array but most reads need the first few elements; loading all of it wastes memory and bandwidth (the pattern "solves the problem of having the working set exceed the capacity of RAM due to large documents", per the pattern summary). **Solution:** keep the few elements you display - the *subset* - in the main document and the full list in its own collection. Adding a review touches both, and `$push` with `$each`, `$sort` and `$slice` keeps the inline array at five:

## The Computed pattern

**Problem:** a value is derived from many source documents and read far more often than the sources change. **Solution:** compute it at write time and store it. The key detail is atomicity: the item and the total change in **one** `updateOne`, so they cannot disagree:

```js
// mongosh/pat-computed.js
db.orders.insertOne({ _id: "order_1", items: [], itemCount: 0, total: 0 });
const add = (id, sku, qty, price) => db.orders.updateOne({ _id: id }, { $push: { items: { sku, qty, price } }, $inc: { itemCount: qty, total: qty * price } });   // one atomic write keeps the sum right
add("order_1", "BK-1", 1, 42); add("order_1", "BK-2", 2, 18.5); add("order_1", "BK-3", 1, 55);
const o = db.orders.findOne({ _id: "order_1" });
const recomputed = db.orders.aggregate([{ $match: { _id: "order_1" } }, { $project: { t: { $sum: { $map: { input: "$items", in: { $multiply: ["$$this.qty", "$$this.price"] } } } } } }]).toArray()[0].t;
console.log({ stored_total: o.total, itemCount: o.itemCount, recomputed_from_items: recomputed });
assert.strictEqual(o.total, recomputed);
// the stale-field risk: change a price and forget the total
db.orders.updateOne({ _id: "order_1", "items.sku": "BK-2" }, { $set: { "items.$.price": 20 } });
const stale = db.orders.findOne({ _id: "order_1" });
console.log("after changing one price without touching total ->", { stored_total: stale.total, real_total: stale.items.reduce((n, i) => n + i.qty * i.price, 0) });
const drifted = db.orders.countDocuments({ $expr: { $ne: ["$total", { $sum: { $map: { input: "$items", in: { $multiply: ["$$this.qty", "$$this.price"] } } } }] } });
console.log("orders whose stored total no longer matches their items:", drifted);
```

```text
{ stored_total: 134, itemCount: 4, recomputed_from_items: 134 }
after changing one price without touching total -> { stored_total: 134, real_total: 137 }
orders whose stored total no longer matches their items: 1
```

The trade-off is exactly what the last lines show: any write path that changes an item without the total leaves a stale value (134 stored, 137 real) and nothing errors. Add an `$expr` audit query like the one above to a health check.

## The Bucket pattern

**Problem:** a high-volume stream of tiny records (sensor readings, log lines) as one document each means millions of small documents and big indexes. **Solution:** group many records into one document per window - here per sensor per hour, capped at 200 readings so a bucket can never grow without bound (the unbounded-array trap from the last lesson). 20 000 readings, both ways:

```js
// mongosh/pat-bucket.js
const N = 20000, base = 1700000000000, sensors = ["s1", "s2"];
const reading = (i) => ({ sensorId: sensors[i % 2], t: new Date(base + i * 5000), celsius: 20 + ((Math.imul(i, 2654435761) >>> 0) % 100) / 10 });
const plain = db.readingsPlain, buck = db.readingsBucket;
let t = Date.now();
for (let i = 0; i < N; i += 1000) plain.insertMany(Array.from({ length: 1000 }, (_, k) => reading(i + k)));
const plainMs = Date.now() - t;
t = Date.now();
const ops = [];
for (let i = 0; i < N; i++) {                                                    // one bucket per sensor per hour, capped at 200 readings
  const r = reading(i), hour = new Date(Math.floor(r.t.getTime() / 3600000) * 3600000);
  ops.push({ updateOne: { filter: { sensorId: r.sensorId, hour, count: { $lt: 200 } }, update: { $push: { readings: { t: r.t, celsius: r.celsius } }, $inc: { count: 1 }, $setOnInsert: { sensorId: r.sensorId, hour } }, upsert: true } });
  if (ops.length === 1000) { buck.bulkWrite(ops, { ordered: true }); ops.length = 0; }
}
if (ops.length) buck.bulkWrite(ops, { ordered: true });
const buckMs = Date.now() - t;
plain.createIndex({ sensorId: 1, t: 1 }); buck.createIndex({ sensorId: 1, hour: 1 });
const ix = (c) => Math.round(Object.values(c.stats().indexSizes).reduce((a, b) => a + b, 0) / 1024);
console.log({ plain: { documents: plain.countDocuments(), ingestMs: plainMs, indexKB: ix(plain) }, bucketed: { documents: buck.countDocuments(), ingestMs: buckMs, indexKB: ix(buck) } });
const oneHour = buck.findOne({ sensorId: "s1", count: 200 });
console.log("a full bucket:", oneHour.count, "readings in one document; readings in the collection:", buck.aggregate([{ $group: { _id: null, n: { $sum: "$count" } } }]).toArray()[0].n);
assert.strictEqual(buck.aggregate([{ $group: { _id: null, n: { $sum: "$count" } } }]).toArray()[0].n, N);
```

```text
{
  plain: { documents: 20000, ingestMs: 140, indexKB: 760 },
  bucketed: { documents: 112, ingestMs: 1903, indexKB: 28 }
}
a full bucket: 200 readings in one document; readings in the collection: 20000
```

Bucketing cut the collection to 112 documents and the indexes from 760 KB to 28 KB, but ingest was about 14 times slower (1 903 ms vs 140 ms) because each reading is an upsert that finds its bucket first. That is the honest trade: cheaper storage and reads, more expensive writes.

### The native alternative: time series collections

For time-ordered measurements MongoDB builds and maintains the buckets for you. The manual: "Compared to normal collections, storing time series data in time series collections improves query efficiency and reduces the disk usage" ([time series collections](https://www.mongodb.com/docs/manual/core/timeseries-collections/), consulted 2026-09-30). You declare a `timeField` and an optional `metaField`:

```js
// mongosh/pat-timeseries.js
db.createCollection("readingsTs", { timeseries: { timeField: "t", metaField: "sensorId", granularity: "seconds" } });
const base = 1700000000000;
for (let i = 0; i < 20000; i += 1000) db.readingsTs.insertMany(Array.from({ length: 1000 }, (_, k) => ({ sensorId: ["s1", "s2"][(i + k) % 2], t: new Date(base + (i + k) * 5000), celsius: 20 + ((Math.imul(i + k, 2654435761) >>> 0) % 100) / 10 })));
const s = db.readingsTs.stats();
console.log({ visibleDocuments: db.readingsTs.countDocuments(), buckets: s.timeseries.bucketCount, avgReadingsPerBucket: Math.round(20000 / s.timeseries.bucketCount) });
const kb = (c) => Math.round(db[c].stats().size / 1024);      // data size in BSON bytes (storageSize is not meaningful this early)
console.log("data size KB - one document per reading:", kb("readingsPlain"), "| hand-made buckets:", kb("readingsBucket"), "| time series collection:", kb("readingsTs"));
console.log("query it like any collection:", db.readingsTs.aggregate([{ $match: { sensorId: "s1" } }, { $group: { _id: null, avg: { $avg: "$celsius" } } }, { $project: { _id: 0, avg: { $round: ["$avg", 2] } } }]).toArray());
assert.strictEqual(db.readingsTs.countDocuments(), 20000);
```

```text
{ visibleDocuments: 20000, buckets: 56, avgReadingsPerBucket: 357 }
data size KB - one document per reading: 1301 | hand-made buckets: 731 | time series collection: 75
query it like any collection: [ { avg: 24.9 } ]
```

Same 20 000 readings: 1 301 KB as plain documents, 731 KB as hand-made buckets, 75 KB in the time series collection (the sizes are BSON data sizes, and the time series figure is the compressed columnar bucket data). Reach for the hand-made pattern only when the native collection does not fit (for example when you need to update readings in place).

## The Extended Reference pattern

**Problem:** you reference another document but always need one or two of its fields to render the parent. **Solution:** copy those few fields next to the reference. The pattern is most useful "when your application is experiencing lots of JOIN operations to bring together frequently accessed data" (pattern summary). Copy only fields that rarely change, and plan the refresh:

```js
// mongosh/pat-extended-reference.js
db.customers.insertMany([{ _id: "cust_77", name: "Grace Hopper", city: "Cambridge", notes: "long profile ..." }, { _id: "cust_78", name: "Linus", city: "Helsinki" }]);
db.ordersX.insertMany(Array.from({ length: 5000 }, (_, i) => ({ _id: "o" + i, customer: { id: i % 2 ? "cust_77" : "cust_78", name: i % 2 ? "Grace Hopper" : "Linus", city: i % 2 ? "Cambridge" : "Helsinki" }, total: 10 + (i % 90) })));   // id + the fields the page always shows
console.log("order list row, no lookup needed:", db.ordersX.findOne({ _id: "o1" }));
db.customers.updateOne({ _id: "cust_77" }, { $set: { city: "Arlington" } });                                // the customer moves
console.log("orders now showing the old city:", db.ordersX.countDocuments({ "customer.id": "cust_77", "customer.city": "Cambridge" }));
const t = Date.now();
const r = db.ordersX.updateMany({ "customer.id": "cust_77" }, { $set: { "customer.city": "Arlington" } });
console.log("refresh copies:", r.modifiedCount, "orders updated in", Date.now() - t, "ms; still stale:", db.ordersX.countDocuments({ "customer.id": "cust_77", "customer.city": "Cambridge" }));
assert.strictEqual(r.modifiedCount, 2500);
```

```text
order list row, no lookup needed: {
  _id: 'o1',
  customer: { id: 'cust_77', name: 'Grace Hopper', city: 'Cambridge' },
  total: 11
}
orders now showing the old city: 2500
refresh copies: 2500 orders updated in 21 ms; still stale: 0
```

## Tips and gotchas

- Patterns are trade-offs, not free wins: Subset and Extended Reference add a copy to keep current, Computed adds write-time work and a stale-value risk, Bucket makes writes 14x costlier here.
- Computed and Extended Reference denormalize; own a plan for refreshing them (an audit query, a batch `updateMany`).
- For time-ordered data check the native time series collection before hand-rolling buckets.
- Cap a bucket (here 200 readings) so it cannot become the unbounded array it was meant to avoid.
- Do not apply a pattern speculatively; reach for one when you can name the problem in your workload.

<Callout title="Patterns are named trade-offs">
Each pattern trades something - a copy to maintain, a little write-time work - for a faster or simpler read. Learn the problem each one solves so that when you meet the symptom you already know the cure. Use a pattern because you have its problem, never just because it exists.
</Callout>

## Reading AI-generated code

Asked to "keep the order total up to date", an assistant adds the item and recomputes nothing - it relies on the total being right from before:

<SpotTheBug lang="js" code={`// AI comment: "total is a Computed field, so we only need to update the item"
await db.collection("orders").updateOne(
  { _id: "order_1", "items.sku": "BK-2" },
  { $set: { "items.$.price": 20 } }
);`}>

The Computed pattern only works if **every** write path maintains the computed field. This one changes an item price and leaves `total` alone: the run above ended with a stored total of 134 while the items summed to 137, the `$expr` audit found 1 order out of sync, and no error was raised anywhere. The fix is to change both in one atomic update (`$inc` the difference, or rewrite the total), and to run the audit query regularly:

```js
// mongosh/pat-computed-fix.js
db.orders.updateOne(
  { _id: "order_1", "items.sku": "BK-2" },
  [{ $set: { items: { $map: { input: "$items", in: { $cond: [{ $eq: ["$$this.sku", "BK-2"] }, { $mergeObjects: ["$$this", { price: 20 }] }, "$$this"] } } } } },
   { $set: { total: { $sum: { $map: { input: "$items", in: { $multiply: ["$$this.qty", "$$this.price"] } } } } } }]      // items and total change in ONE update
);
const o = db.orders.findOne({ _id: "order_1" });
const real = o.items.reduce((n, i) => n + i.qty * i.price, 0);
console.log({ stored_total: o.total, real_total: real, ordersOutOfSync: db.orders.countDocuments({ $expr: { $ne: ["$total", { $sum: { $map: { input: "$items", in: { $multiply: ["$$this.qty", "$$this.price"] } } } }] } }) });
assert.strictEqual(o.total, real);
```


## Mental Model

Every pattern moves work from read time to write time (Computed, Bucket, Subset) or moves a join into the document (Extended Reference). The bill arrives as a copy to keep correct or a write path to maintain. Before adopting one, name the read you are speeding up, and the write path that now has one more job.

## Trade-offs

| Pattern | Benefit | Cost |
|---------|---------|------|
| Subset | 2.16 MB read becomes 1 154 bytes | A second write; the inline copy must stay current |
| Computed | No recomputation on read; atomic with the item | Stale if any write path forgets it (134 vs 137) |
| Bucket | 112 documents and 28 KB of indexes instead of 20 000 and 760 KB | 14x slower ingest here; bucket size to choose |
| Time series collection | 75 KB, no bucket code | Only for time-ordered measurements; limited in-place updates |
| Extended Reference | No lookup for the common fields | Refresh on change: 2 500 orders to update |

## Common Misconceptions

- **"A `$slice` projection makes a fat document cheap to read."** - the server still loaded it: 1 675 ms vs 218 ms.
- **"A computed field maintains itself."** - the one forgotten write left it 3 off with no error.
- **"Bucketing is a pure win."** - reads and storage improved; ingest was 14x slower.
- **"Hand-made buckets are the way to store time series."** - the native collection stored the same data in 75 KB.
- **"Copying fields is always wrong in a database."** - Extended Reference does it on purpose, for fields that rarely change.

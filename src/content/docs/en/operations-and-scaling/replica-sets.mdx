A replica set is the answer to one blunt question: what happens when the server holding your data stops responding? With a single `mongod`, the answer is that your application is down until someone fixes the machine. With a replica set, another copy takes over in seconds. A **replica set** is a group of `mongod` instances that all hold the same data — one **primary** that accepts every write, and one or more **secondaries** that keep their own copies in step with it.

Everything marked *3-node* below was run on this Mac on a throwaway replica set of three `mongo:8.3.11` containers (`rs-1`, `rs-2`, `rs-3`, replica set name `rsb3`, mongosh 2.11.1, Node driver 7.7.0 in a fourth container), each capped at 512 MB, all removed afterwards. Fences with a path comment also ran against the course's one-node replica set. Python/Go/Rust tabs mirror the verified shell/Node call and are not executed by the course's automated checker.

## Primary, secondaries, and the oplog

Only the primary takes writes. Each write it applies is also recorded in a capped collection called the **oplog** (`local.oplog.rs`). Every secondary reads the primary's oplog and replays the same operations, so the copies converge. That makes secondaries *eventually* consistent: there is a lag between a write on the primary and the same write everywhere else. A real oplog entry for `insertOne({ name: "Ada" })`:

```text
{
  op: 'i',
  ns: 'lib.members',
  o: { _id: ObjectId('6abccde57c8538514ddd8679'), name: 'Ada' },
  ts: Timestamp({ t: 1790758373, i: 2 }),
  t: Long('1')
}

```

`op: "i"` is an insert, `o` is the document, `ts` orders it, `t` is the election term. And what the whole set looks like (*3-node*):


## Automatic elections — timed

When the primary disappears, the remaining members vote; a candidate that gets a majority becomes primary. How long does that take? The manual says: "The median time before a cluster elects a new primary should not typically exceed 12 seconds, assuming default replica configuration settings. This includes time required to mark the primary as unavailable and call and complete an election." ([Replica set elections](https://www.mongodb.com/docs/manual/core/replica-set-elections/)). While elections run, the set cannot process writes; reads on secondaries can continue.

Measured, twice. A writer inside the set inserted with `w: "majority"` every 100 ms (`retryWrites` is on by default, so an interrupted write is retried once a primary exists), and the writer logged how long each insert took:

```js
// mongosh/rs-writer.js @skip-verify needs the 3-node replica set (run inside a member)
const c = db.getSiblingDB("lib").ticks;
const end = Date.now() + 40000;
let i = 0;
while (Date.now() < end) {
  const t0 = Date.now();
  let r = "ok";
  try { c.insertOne({ i: i++, t: new Date() }, { writeConcern: { w: "majority" } }); } catch (e) { r = "ERR " + e.name + " " + e.code; }
  print(JSON.stringify({ at: t0, ms: Date.now() - t0, r }));
  sleep(100);
}
```

Run 1 — the primary killed with `docker kill` (SIGKILL: a crash, no goodbye). Run 2 — the primary stopped with `docker stop` (SIGTERM: a clean shutdown). The only iterations slower than 300 ms:

```text
{"at":1790758407048,"ms":10773,"r":"ok"}
rs-1:27017 SECONDARY | rs-2:27017 PRIMARY | rs-3:27017 SECONDARY

```

```text
{"at":1790758473930,"ms":324,"r":"ok"}
rs-1:27017 PRIMARY | rs-2:27017 (not reachable/healthy) | rs-3:27017 SECONDARY

```

A crash stalled one write for about 10.8 s — the 10 s election timeout plus the election itself, in line with the manual's "typically ... 12 seconds" — and then that write *succeeded*: the driver waited for the new primary and retried. A clean shutdown lets the primary hand over, and the stall was under half a second. Both leave you with the same lesson: application code must ride out a pause of about ten seconds during a crash, not fail fast. (Atlas documents a failover test button and says an election takes five seconds on average on its clusters — [Test Resilience](https://www.mongodb.com/docs/atlas/tutorial/test-resilience/), consulted 2026-09-30.)

## Why an odd number of voters

A candidate needs votes from more than half the voting members. Below, two of three members were stopped; the survivor could not win an election and stayed a secondary, so it refused writes:

```text
rs-1:27017 SECONDARY | rs-2:27017 (not reachable/healthy) | rs-3:27017 (not reachable/healthy)
MongoServerError | 10107 NotWritablePrimary | not primary

```

After the two members were restarted the set healed by itself:

```text
rs-1:27017 PRIMARY | rs-2:27017 SECONDARY | rs-3:27017 SECONDARY

```

With three voters one failure leaves a majority of two. With two voters one failure leaves one of two — no majority, no primary.

## A secondary can be behind

One secondary (`rs-2`) was frozen with `db.fsyncLock()` — a stand-in for a lagging member — while an order was written to the primary and read straight back three ways (Node, *3-node*):

```js
// app/rs-stale-read.mjs @skip-verify needs the 3-node replica set and a frozen secondary (real output below)
const orders = client.db("shop").collection("orders");
const direct = new MongoClient("mongodb://rs-2:27017/?directConnection=true", { readPreference: "secondary" });
await direct.connect();
await orders.insertOne({ _id: "o-1", total: 42 });
console.log("bug   (read the frozen secondary):", await direct.db("shop").collection("orders").findOne({ _id: "o-1" }));
console.log("fix 1 (read the primary)         :", await orders.findOne({ _id: "o-1" }, { readPreference: "primary" }));
// fix 2: causal consistency - the read waits for the secondary to reach the write
const session = client.startSession({ causalConsistency: true });
await orders.insertOne({ _id: "o-2", total: 7 }, { session, writeConcern: { w: "majority" } });
await orders.findOne({ _id: "o-2" }, { session, readPreference: "secondary", readConcern: { level: "majority" }, maxTimeMS: 2000 });
```

```text
bug   (read the frozen secondary): null
fix 1 (read the primary)         : { _id: 'o-1', total: 42 }
fix 2 (causal session, secondary) : served by a caught-up secondary in 40 ms

```

The write was acknowledged (`w: "majority"` by default — the other secondary and the primary had it) and yet the frozen secondary returned `null`. A causally consistent session gives a read-your-writes guarantee on secondaries: the read is served only by a member that has reached the write — here the healthy `rs-3`, in 40 ms — instead of the frozen `rs-2`.

**In Atlas:** an Atlas cluster is a replica set (in a sharded cluster, each shard is one — [Manage clusters](https://www.mongodb.com/docs/atlas/manage-clusters/)), and *Test Failover* triggers the election for you.

## Tips and gotchas

- Keep an **odd** number of voting members: three tolerate one failure, five tolerate two.
- An **arbiter** votes but holds no data; it cannot become primary and adds no durability. It also changes the default write concern (see the read/write concerns lesson).
- **Secondaries lag.** If your application reads its own writes right after writing, read from the primary or use a causally consistent session (proved above).
- Replication is availability, not backup: a bad `deleteMany` replicates too.
- **A crash is not a clean stop.** Budget about ten seconds of write pause for a hard failure.

<Callout title="Availability through copies and votes">
A replica set keeps copies in sync through the oplog and elects a new primary by majority vote. A crashed primary cost one write about ten seconds; a stopped one under half a second; a lost majority cost every write.
</Callout>

## Reading AI-generated code

An assistant scales reads by sending them to secondaries and writes a confident comment:

<SpotTheBug lang="js" code={`// AI comment: "the insert is acknowledged, so reading it back from a secondary is safe"
await orders.insertOne({ _id: "o-1", total: 42 });
const saved = await ordersOnSecondary.findOne({ _id: "o-1" });   // readPreference: "secondary"

An acknowledged write is on the primary and a majority — not necessarily on the *particular* secondary you read. In the lab a frozen secondary returned `null` for a write that had been acknowledged, and the code above would report a lost order that is not lost. Read your own writes from the primary, or use a causally consistent session (`causalConsistency: true`). The run above shows the bug, the primary read and the causal read side by side.

</SpotTheBug>

## Mental Model

A replica set is **one authoritative log (the oplog) and several copies replaying it**, with a vote to decide who owns the log. Writes go to the log owner; the copies are always slightly behind; the vote needs a strict majority of all voters, alive or not. Failover is not instantaneous because the others must first decide the owner is really gone — that decision is what the ten-second timeout buys.

## Trade-offs

| Choice | Benefit | Cost |
|---------|---------|------|
| Replica set (vs. a single `mongod`) | Automatic failover; measured ~10.8 s pause on a crash, 0.3 s on a clean stop | At least three nodes to run; writes still bottleneck on one primary |
| Reading from secondaries | Spreads read load off the primary | Proven above: an acknowledged write was invisible on a lagging secondary |
| Reading from the primary only | Always the latest write | The primary carries all the load |
| Even number of voters | Fewer machines than the next odd number | A single failure can leave no majority |

## Common Misconceptions

- **"Adding secondaries scales writes."** — every write goes to the one primary; secondaries scale reads only. Scaling writes is sharding.
- **"Failover takes a second or two."** — a crash paused one write for ~10.8 s (a clean stop 0.3 s); the manual says the median should not typically exceed 12 s.
- **"An acknowledged write is visible everywhere."** — visible on the primary and a majority; a specific secondary may be behind (`null` above).
- **"Two nodes are enough for HA."** — with two voters a single failure leaves one of two, and the survivor stays a secondary.
- **"Replicas are backups."** — a dropped collection replicates too.
- **"All members in one availability zone is fine."** — a replica set protects against a node failing, not against the zone failing; spread members across zones.

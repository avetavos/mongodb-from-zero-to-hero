The last two moves in this module are about doing more with fewer round trips. An **upsert** answers a question you hit constantly: "update this document if it exists, otherwise create it." A **bulk write** lets you send a whole list of mixed operations - inserts, updates, deletes - to the server in a single call instead of one network trip per operation. Neither introduces new operators; they compose the methods you already know into something more efficient.

We finish with our `members` collection one more time. Every output below was captured on mongo 8.3.11, mongosh 2.11.1 and Node driver 7.7.0 (the Python, Go and Rust tabs were each run once in a scratch program on the same server).

## Upsert: update or insert

Add the upsert option to an update, and when the filter matches nothing, MongoDB inserts a new document built from the filter plus the update. When the filter *does* match, it behaves like an ordinary update. Here we record a visit for "Katherine" - if she is not yet a member, this creates her:

<Tabs syncKey="lang">
  <TabItem label="mongosh">
    ```js
    // mongosh/upsert.js
    const first = db.members.updateOne(
      { name: "Katherine" },
      { $set: { joined: 2026 }, $inc: { visits: 1 } },
      { upsert: true }
    );
    console.log(first);
    console.log(db.members.findOne({ name: "Katherine" }));
    const second = db.members.updateOne(
      { name: "Katherine" },
      { $set: { joined: 2026 }, $inc: { visits: 1 } },
      { upsert: true }
    );
    console.log(second);
    assert.strictEqual(first.upsertedCount, 1);
    assert.strictEqual(second.matchedCount, 1);
    assert.strictEqual(db.members.findOne({ name: "Katherine" }).visits, 2);
    ```
  </TabItem>
  <TabItem label="Node.js">
    ```js

      { name: "Katherine" },
    ```

Because no Katherine existed, the first call created her. **The acknowledgement differs between the shell and the drivers**, and the old lesson text got it wrong: the shell reports the new `_id` as `insertedId` (there is **no** `upsertedId` field in mongosh) plus `upsertedCount: 1`, while the Node driver reports `upsertedId` and `upsertedCount: 1`. In both, `matchedCount: 0` is your signal that an insert happened rather than an update:

### What goes into the inserted document: `$setOnInsert`

The inserted document is the filter's **equality** conditions plus the update. Conditions that are not equalities are *not* copied, and `$setOnInsert` writes fields only when the upsert inserts (it does nothing on the update path):

```js
// mongosh/upsert-setoninsert.js
const r1 = db.people.updateOne(
  { name: "Ada", joined: { $gt: 2000 } },                       // name is equality, joined is a range
  { $setOnInsert: { fines: 0, createdBy: "upsert" }, $inc: { visits: 1 } },
  { upsert: true }
);
console.log(r1.upsertedCount, db.people.findOne({ name: "Ada" }, { _id: 0 }));
db.people.updateOne({ name: "Ada" }, { $setOnInsert: { fines: 99 }, $inc: { visits: 1 } }, { upsert: true });
console.log(db.people.findOne({ name: "Ada" }, { _id: 0 }));    // fines still 0: $setOnInsert skipped
assert.strictEqual(db.people.findOne({ name: "Ada" }).fines, 0);
assert.strictEqual("joined" in db.people.findOne({ name: "Ada" }), false);
```

```text
1 { name: 'Ada', createdBy: 'upsert', fines: 0, visits: 1 }
{ name: 'Ada', createdBy: 'upsert', fines: 0, visits: 2 }
```

The `name` equality came from the filter; the range on `joined` did not (no `joined` field was created); `fines: 99` on the second call was ignored because the document already existed.

## bulkWrite: many operations, one round trip

`bulkWrite` takes a list of operations and sends them together. Each entry names its operation and carries the same filter and update you would pass individually, so you can mix inserts, updates, and deletes freely. Here we onboard one new member, charge a fine, and remove a lapsed member - all in a single call:

<Tabs syncKey="lang">
  <TabItem label="mongosh">
    ```js
    // mongosh/bulk-write.js
    const res = db.members.bulkWrite([
      { insertOne: { document: { name: "Tim", joined: 2026, fines: 0 } } },
      { updateOne: { filter: { name: "Grace" }, update: { $inc: { fines: 1 } } } },
      { deleteOne: { filter: { name: "Linus" } } }
    ]);
    console.log(res);
    assert.strictEqual(res.insertedCount, 1);
    assert.strictEqual(res.deletedCount, 1);
    ```
  </TabItem>
  <TabItem label="Node.js">
    ```js
    // app/bulk-write.mjs
    const res = await db.collection("members").bulkWrite([
      { insertOne: { document: { name: "Tim", joined: 2026, fines: 0 } } },
      { updateOne: { filter: { name: "Grace" }, update: { $inc: { fines: 1 } } } },
      { deleteOne: { filter: { name: "Linus" } } },
    ]);
    console.log(res);
    if (res.insertedCount !== 1 || res.modifiedCount !== 1 || res.deletedCount !== 1) throw new Error("unexpected counts");
    ```
  </TabItem>
  <TabItem label="Python">

    ```python
    res = db.members.bulk_write([
        InsertOne({"name": "Tim", "joined": 2026, "fines": 0}),
        UpdateOne({"name": "Grace"}, {"$inc": {"fines": 1}}),
        DeleteOne({"name": "Linus"}),
    ])
    print(res.inserted_count, res.modified_count, res.deleted_count)
    ```
  </TabItem>

The whole point is the round trip: instead of three separate conversations with the server, the driver batches the list and sends it once. Other operation kinds work the same way (`updateMany`, `replaceOne`, `deleteMany`, and `upsert: true` on an update entry); in the mongosh run, a bulk with an upserting `updateOne`, an `updateMany` and a `replaceOne` returned `matchedCount: 4, modifiedCount: 4, upsertedCount: 1, upsertedIds: { '0': ObjectId('...') }`.

**A Rust note.** The Rust driver's `bulk_write` lives on the **client** (it spans namespaces) and needs a **MongoDB 8.0+ server**; the model types are builders (`InsertOneModel::builder()...`) wrapped into `WriteModel`. The struct-literal form (`WriteModel::InsertOne { namespace: ..., document: ... }`) that earlier drafts of this lesson showed does not compile on Rust driver 3.9.1 (`variant WriteModel::InsertOne has no field named namespace`) - the code above is what we ran.

### How big can one bulkWrite be?

Older advice says to hand-split big batches. The driver already does that on the wire (it respects the server's `maxWriteBatchSize` and `maxMessageSizeBytes` for you), so a single call can carry a very large list. On this Mac against a single-node replica set:

```js
// app/bulk-large.mjs
const ops = Array.from({ length: 250000 }, (_, i) => ({ insertOne: { document: { n: i } } }));
let t = Date.now();
const r = await db.collection("bulk").bulkWrite(ops, { ordered: false });
console.log("250k-op bulkWrite:", r.insertedCount, "in", Date.now() - t, "ms");
t = Date.now();
const r2 = await db.collection("many").insertMany(Array.from({ length: 100000 }, (_, i) => ({ n: i })));
console.log("100k insertMany  :", r2.insertedCount, "in", Date.now() - t, "ms");
if (r.insertedCount !== 250000) throw new Error("expected all 250000");
```

```text
250k-op bulkWrite: 250000 in 833 ms
100k insertMany  : 100000 in 323 ms
```

Timings are from two runs on one machine (862 ms and 833 ms for the 250 000 operations) - the point is that 250 000 operations went through in a single call without manual batching. What you still have to watch are limits that *are* visible to you, such as the 16 MiB size of any one document.

## Ordered versus unordered

By default `bulkWrite` is **ordered**: it runs the operations in sequence and stops at the first one that errors, leaving the rest unrun. Switch it to **unordered** and the server may run the operations in any order and keeps going past failures, applying every operation that can succeed. Unordered is often faster and is the right choice when the operations do not depend on each other. The original example inserted two different names and so could not fail either way; to see the difference you need something that fails - a unique index and a duplicate:

The real result: with `ordered: true` the second insert (index 1, the duplicate `Tim`) failed with code `11000` and Margaret, after it, never ran - only Barbara was inserted. With `ordered: false` the duplicate was still reported, but Barbara **and** Margaret both went in:

```text
ordered=true: MongoBulkWriteError 11000 inserted 1 failed at [ 1 ] -> [ 'Barbara', 'Tim' ]
ordered=false: MongoBulkWriteError 11000 inserted 2 failed at [ 1 ] -> [ 'Barbara', 'Margaret', 'Tim' ]
```

In both modes the error tells you exactly which operation failed (`writeErrors[i].index`) and how many succeeded (`result.insertedCount`); neither mode rolls back what it applied.

## Tips and gotchas

- An upsert builds its new document from **both** the filter's equality conditions and the update operators - range conditions are not copied (see `$setOnInsert` above). Make the filter specific so the inserted document comes out the way you expect.
- After an upsert, check `matchedCount`: `0` plus an `insertedId` (shell) / `upsertedId` (drivers) means a document was created; `1` means an existing one was updated.
- **An upsert is only race-safe with a unique index** on the filter fields (proven below).
- Ordered `bulkWrite` stops at the first error. If you want every independent operation attempted regardless of failures, set `ordered: false`.
- `bulkWrite` is about efficiency, not transactions. Unless you wrap it in a transaction, the operations are not all-or-nothing - some can succeed while others fail (`inserted 1` above).
- The shell result has `insertedCount` on `bulkWrite` but not on `insertMany`; check which object you have.

<Callout title="Fewer round trips, same building blocks">
Upserts and bulk writes do not add new query language - they pack the inserts, updates, and deletes you already know into a single trip to the server. That is most of what "making CRUD fast" means in practice.
</Callout>

## Reading AI-generated code

An assistant asked for a page-view counter will reach for an upsert and explain that it "guarantees one row per page":

<SpotTheBug lang="js" code={`// AI comment: "upsert is atomic, so there can never be two rows for the same page"
async function recordView(db, page) {
  await db.collection("counters").updateOne(
    { page },
    { $inc: { views: 1 } },
    { upsert: true }
  );
}`}>

The update of one document is atomic, but "find nothing, then insert" is two steps, and without a unique index two concurrent calls can both find nothing and both insert. We fired 100 parallel upserts per page for 20 pages on one client: **17 to 19 of the 20 pages ended up with duplicate rows, and one page collected up to 16 documents** (three runs: 19/20 with at most 7 documents, 17/20 with at most 13, 17/20 with at most 16 - the exact count varies with timing), every upsert reported success, and the totals were still correct (2000 views) - so nothing looked wrong. With a unique index on `page`, the same run produced exactly **one document per page, no rejected upserts, 2000 total views** (the server retries the loser of the race as an update):

```js
// app/upsert-race.mjs
const ROUNDS = 20, PARALLEL = 100;
async function race(useUniqueIndex) {
  const c = db.collection(useUniqueIndex ? "counters_unique" : "counters_plain");
  if (useUniqueIndex) await c.createIndex({ page: 1 }, { unique: true });
  let roundsWithDuplicates = 0, maxDocs = 0, rejected = 0;
  for (let r = 0; r < ROUNDS; r++) {
    const page = `/home-${r}`;
    const results = await Promise.allSettled(Array.from({ length: PARALLEL }, () =>
      c.updateOne({ page }, { $inc: { views: 1 } }, { upsert: true })));
    rejected += results.filter((x) => x.status === "rejected").length;
    const docs = await c.countDocuments({ page });
    if (docs > 1) roundsWithDuplicates++;
    maxDocs = Math.max(maxDocs, docs);
  }
  const total = (await c.aggregate([{ $group: { _id: null, v: { $sum: "$views" } } }]).next()).v;
  return { roundsWithDuplicates: `${roundsWithDuplicates}/${ROUNDS}`, maxDocsForOnePage: maxDocs, rejectedUpserts: rejected, totalViews: total };
}
const plain = await race(false);
const unique = await race(true);
console.log("without unique index:", plain);
console.log("with unique index   :", unique);
if (unique.maxDocsForOnePage !== 1 || unique.totalViews !== ROUNDS * PARALLEL) throw new Error("unique index should give one document per page");
```

```text
without unique index: {
  roundsWithDuplicates: '17/20',
  maxDocsForOnePage: 16,
  rejectedUpserts: 0,
  totalViews: 2000
}
with unique index   : {
  roundsWithDuplicates: '0/20',
  maxDocsForOnePage: 1,
  rejectedUpserts: 0,
  totalViews: 2000
}
```

The fix is one line, done once: `createIndex({ page: 1 }, { unique: true })`.

## Mental Model

An upsert is **"match, else create" evaluated on the server**, but the *uniqueness* of what it creates is only as strong as the constraint behind it. A bulk write is **a list of independent commands in one envelope**: the envelope saves round trips, `ordered` decides whether the list stops at the first failure, and neither gives you all-or-nothing. Together: the unique index protects correctness, the bulk envelope protects latency.

## Trade-offs

| Choice | Benefit | Cost |
|---------|---------|------|
| `bulkWrite` | Combines many operations into one round trip; 250 000 inserts in about 850 ms in one call | One combined result - you must unpack `writeErrors` yourself when some fail; not atomic |
| `bulkWrite` ordered (default) | Predictable: operations run in list order and stop at the first error | One failure leaves every later operation unrun (`Margaret` above) |
| `bulkWrite` unordered | Keeps going past failures; often faster | Order not guaranteed; you must read `writeErrors` |
| upsert (with unique index) | One round trip covers insert-if-missing and update-if-present; race-safe | Needs the unique index (extra write cost and storage) |
| upsert (no unique index) | Nothing extra to maintain | Concurrent calls duplicate documents (17-19 of 20 pages in our runs) |
| Explicit check-then-write (`findOne` first) | Fine-grained control before writing | Two round trips and the same race window between find and write |

## Common Misconceptions

- **"An upsert always prevents duplicates."** - only with a unique index behind the filter; without it we got up to 16 documents for one page.
- **"`upsertedId` is in every result."** - mongosh reports `insertedId` and `upsertedCount`; the drivers report `upsertedId`.
- **"You must split big bulk writes yourself."** - the driver batches on the wire; 250 000 operations ran in one call in about 850 ms. Batch only for memory or your own progress reporting.
- **"Unordered means faster and safe."** - it keeps going past failures, but you still have to read `writeErrors`, and nothing is rolled back.
- **"A range in the upsert filter ends up in the new document."** - only equality conditions are copied.
- **"`bulkWrite` is a transaction."** - it is not; `inserted 1` remained after the failure.

> Real-world example
>
> The `updateOne` reference states the requirement we measured: "To avoid multiple upserts, ensure that the `filter` field(s) are uniquely indexed" ([db.collection.updateOne](https://www.mongodb.com/docs/manual/reference/method/db.collection.updateOne/), consulted 2026-09-30). In our run the unique index produced no rejected upserts - the losing concurrent upsert was retried by the server as an update - so 2000 of 2000 increments landed on 20 documents.

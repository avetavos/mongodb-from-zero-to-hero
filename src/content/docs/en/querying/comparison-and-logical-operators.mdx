An exact-match filter - field equals value - only gets you so far. Real questions are ranges and sets: "who owes more than three fines?", "who joined in 2022 or 2023?", "which records are missing a field entirely?". MongoDB answers these with **query operators**, special keys that begin with a dollar sign and live *inside* the value position of a field. The pattern is always the same: instead of giving a field a plain value, you give it a small document whose key is an operator.

We keep querying our library `members`. Every output below was captured on mongo 8.3.11, mongosh 2.11.1 and Node driver 7.7.0 (Python, Go and Rust tabs were each run once in a scratch program on the same server). This lesson's data is deliberately a little messy - one member with no `fines` field, one with `fines: null`, one whose `joined` is a *string* - because that is where operators surprise people.

## Comparison operators

The comparison family compares a field against a value: `$eq` (equal), `$ne` (not equal), `$gt` (greater than), `$gte` (greater-or-equal), `$lt` (less than), and `$lte` (less-or-equal). Writing a plain value is just shorthand for `$eq`. Here we ask for every member who owes more than two fines:

<Tabs syncKey="lang">
  <TabItem label="mongosh">
    ```js
    // mongosh/cmp-gt.js
    const docs = db.members.find({ fines: { $gt: 2 } }, { _id: 0 }).sort({ name: 1 }).toArray();
    console.log(docs);
    assert.strictEqual(docs.map((d) => d.name).join(), "Grace,Linus");
    ```
  </TabItem>
  <TabItem label="Node.js">
    ```js
    // app/cmp-gt.mjs
    const docs = await db.collection("members")
      .find({ fines: { $gt: 2 } })
      .toArray();
    console.log(docs.map((d) => d.name).sort());
    if (docs.length !== 2) throw new Error("expected 2");
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    docs = list(db.members.find({"fines": {"$gt": 2}}))
    print(docs)
    ```
  </TabItem>
  <TabItem label="Go">

    if err != nil {

Only members above the threshold come back (`missing`, `null` and other-typed values never satisfy `$gt`):

```text
[
  { name: 'Grace', joined: 2021, fines: 3 },
  { name: 'Linus', joined: 2023, fines: 5 }
]
```

You can combine two comparisons on the **same** field by putting both operators in one document - here, members who joined in a window of years. And note what `$gt: 2000` does to the member whose `joined` is the *string* `"2020"`:

```js
// mongosh/cmp-range-and-types.js
console.log("joined 2022..2023   :", names({ joined: { $gte: 2022, $lte: 2023 } }));
console.log("joined > 2000       :", names({ joined: { $gt: 2000 } }));        // Alan's "2020" is a string
console.log("joined type string  :", names({ joined: { $type: "string" } }));
assert.strictEqual(names({ joined: { $gt: 2000 } }).includes("Alan"), false);
assert.strictEqual(names({ joined: { $type: "string" } }), "Alan");
```

```text
joined 2022..2023   : Edsger, Linus, Margaret
joined > 2000       : Ada, Barbara, Edsger, Grace, Linus, Margaret
joined type string  : Alan
```

MongoDB compares a number only with other numbers, so the mistyped `"2020"` is silently absent from every numeric range - it does not error and it does not sort as 2020 (a single type-bracketing rule: a range query only sees values of the same type as its operand).

## Membership: $in and $nin

`$in` matches when a field equals **any** value in a list, and `$nin` matches when it equals **none** of them. This is far cleaner than chaining `$or` of equalities. Here we pull the members who joined in either 2021 or 2023:

<Tabs syncKey="lang">
  <TabItem label="mongosh">

    console.log("joined $in [2021,2023]:", names({ joined: { $in: [2021, 2023] } }));
    console.log("fines $nin [0,5]      :", names({ fines: { $nin: [0, 5] } }));
    assert.strictEqual(names({ joined: { $in: [2021, 2023] } }), "Grace, Linus, Margaret");
    ```
  </TabItem>
  <TabItem label="Node.js">

    ```
  </TabItem>

Both matching years are returned together - and look at `$nin`: it returned four members, including Ada (no `fines` at all), Barbara (`null`) and Alan (1), because "not in [0, 5]" is true for anything that is not literally 0 or 5:

```text
joined $in [2021,2023]: Grace, Linus, Margaret
fines $nin [0,5]      : Ada, Alan, Barbara, Grace
```

## Combining conditions: $and, $or, $not, $nor

Several field/value pairs in one filter already mean AND, so `$and` is only needed when you would otherwise write the same field twice. `$or` is the everyday one - it takes a list of filters and matches if **any** holds. Here we find members who either owe nothing or joined in 2021:

<Tabs syncKey="lang">
  <TabItem label="mongosh">
    ```js
    // mongosh/cmp-or-nor.js
    console.log("$or fines 0 / joined 2021:", names({ $or: [{ fines: 0 }, { joined: 2021 }] }));
    console.log("$nor (same branches)     :", names({ $nor: [{ fines: 0 }, { joined: 2021 }] }));
    console.log("$not { $gt: 2 }          :", names({ fines: { $not: { $gt: 2 } } }));
    assert.strictEqual(names({ $or: [{ fines: 0 }, { joined: 2021 }] }), "Edsger, Grace, Margaret");
    ```
  </TabItem>
  <TabItem label="Node.js">
    ```js
    // app/cmp-or.mjs
    const docs = await db.collection("members").find({
      $or: [{ fines: 0 }, { joined: 2021 }]
    }).toArray();
    console.log(docs.map((d) => d.name).sort());
    if (docs.length !== 3) throw new Error("expected 3");
    ```
  </TabItem>
  <TabItem label="Python">
    ```python
    docs = list(db.members.find({
        "$or": [{"fines": 0}, {"joined": 2021}]
    }))
    ```
  </TabItem>
  <TabItem label="Go">
    ```go
    cur, err := coll.Find(ctx, bson.M{
        "$or": bson.A{
            bson.M{"fines": 0},
            bson.M{"joined": 2021},
        },
    })
    if err != nil {
        return err
    }
    var docs []bson.M
    if err := cur.All(ctx, &docs); err != nil {
        return err
    }
    ```
  </TabItem>
  <TabItem label="Rust">
    ```rust
    let mut cursor = coll
        .find(doc! {
            "$or": [
                doc! { "fines": 0 },
                doc! { "joined": 2021 },
            ]
        })
        .await?;
    ```
  </TabItem>
</Tabs>

Anyone matching either branch appears. `$nor` is the logical opposite of `$or` - and notice that it **includes members who do not have the field at all** (Ada) or have it as `null` (Barbara): "none of these branches hold" is true when there is nothing to compare. `$not` inverts a single operator expression and, likewise, matches missing fields:

```text
$or fines 0 / joined 2021: Edsger, Grace, Margaret
$nor (same branches)     : Ada, Alan, Barbara, Linus
$not { $gt: 2 }          : Ada, Alan, Barbara, Edsger, Margaret
```

`$not` only wraps an *operator expression*. Handing it a bare value is rejected by the server:

```text
> db.members.find({ fines: { $not: 5 } }).toArray()
MongoServerError: $not argument must be a regex or an object
> db.members.find({ fines: { $not: { $eq: 5 } } })     -> Ada, Alan, Barbara, Edsger, Grace, Margaret
```

## Testing for a field: $exists and $type

Documents in one collection need not all share the same fields. `$exists` asks whether a field is present at all, regardless of its value, and `$type` asks what BSON type the value has. Here we find members who have *no* `fines` field recorded yet - and compare with `null`:

<Tabs syncKey="lang">
  <TabItem label="mongosh">
    ```js
    // mongosh/cmp-exists-type.js
    console.log("fines $exists false :", names({ fines: { $exists: false } }));
    console.log("fines null          :", names({ fines: null }));
    console.log("fines $type null    :", names({ fines: { $type: "null" } }));
    console.log("joined $type number :", names({ joined: { $type: "number" } }));
    console.log("joined $type [int,double]:", names({ joined: { $type: ["int", "double"] } }));
    assert.strictEqual(names({ fines: { $exists: false } }), "Ada");
    assert.strictEqual(names({ fines: null }), "Ada, Barbara");
    ```
  </TabItem>
  <TabItem label="Node.js">

Three different questions with three different answers:

```text
fines $exists false : Ada
fines null          : Ada, Barbara
fines $type null    : Barbara
joined $type number : Ada, Barbara, Edsger, Grace, Linus, Margaret
joined $type [int,double]: Ada, Barbara, Edsger, Grace, Linus, Margaret
```

`{ fines: null }` matches **both** the missing field (Ada) and the explicit null (Barbara); `$exists: false` is only the missing one; `$type: "null"` is only the explicit null. `$type` takes either a type alias (`"int"`, `"string"`, `"number"` = any numeric type) or an array of aliases.

**In Compass:** type any of these filters straight into the **Filter** field at the top of the Documents tab, for example `{ fines: { $gt: 2 } }`, and press **Find** (Compass accepts every query operator except `$text` and `$expr`, per its documentation, [mongodb.com/docs/compass/current/query/filter](https://www.mongodb.com/docs/compass/current/query/filter/)).

## What the planner does with each

The old lesson said `$ne` makes the planner "often choose not to use an index at all". We measured on 20 000 documents with a single-field index on `city` and one on `joined`; `explain("executionStats")` reports keys and documents examined:

```js
// mongosh/cmp-explain.js
const cities = ["Berlin", "Cambridge", "Helsinki", "Austin", "Boston"];
db.big.insertMany(Array.from({ length: 20000 }, (_, i) => ({ i, city: cities[i % 5], joined: 2020 + (i % 6), fines: i % 4 })));
db.big.createIndex({ city: 1 });
db.big.createIndex({ joined: 1 });
const stage = (p) => p.inputStage ? p.stage + " > " + stage(p.inputStage) : (p.inputStages ? p.stage + " > [" + p.inputStages.map(stage).join(", ") + "]" : p.stage);
const stats = (label, cursor) => {
  const e = cursor.explain("executionStats"), es = e.executionStats, wp = e.queryPlanner.winningPlan;
  console.log(label.padEnd(26), stage(wp.queryPlan ?? wp), "| returned", es.nReturned, "| keys", es.totalKeysExamined, "| docs", es.totalDocsExamined);
  return es;
};
stats("city = Berlin", db.big.find({ city: "Berlin" }));
const ne = stats("city $ne Berlin", db.big.find({ city: { $ne: "Berlin" } }));
stats("city $nin [Berlin,Boston]", db.big.find({ city: { $nin: ["Berlin", "Boston"] } }));
stats("joined $gte 2025", db.big.find({ joined: { $gte: 2025 } }));
stats("joined $in [2021,2023]", db.big.find({ joined: { $in: [2021, 2023] } }));
stats("$or joined 2021 / 2023", db.big.find({ $or: [{ joined: 2021 }, { joined: 2023 }] }));
const noIdx = stats("$or city / fines (no idx)", db.big.find({ $or: [{ city: "Berlin" }, { fines: 3 }] }));
stats("$or city / joined", db.big.find({ $or: [{ city: "Berlin" }, { joined: 2021 }] }));
assert.strictEqual(ne.totalKeysExamined, 16001);
assert.strictEqual(noIdx.totalDocsExamined, 20000);
```

```text
city = Berlin              FETCH > IXSCAN | returned 4000 | keys 4000 | docs 4000
city $ne Berlin            FETCH > IXSCAN | returned 16000 | keys 16001 | docs 16000
city $nin [Berlin,Boston]  FETCH > IXSCAN | returned 12000 | keys 12002 | docs 12000
joined $gte 2025           FETCH > IXSCAN | returned 3333 | keys 3333 | docs 3333
joined $in [2021,2023]     FETCH > IXSCAN | returned 6667 | keys 6669 | docs 6667
$or joined 2021 / 2023     FETCH > IXSCAN | returned 6667 | keys 6669 | docs 6667
$or city / fines (no idx)  SUBPLAN > COLLSCAN | returned 8000 | keys 0 | docs 20000
$or city / joined          SUBPLAN > FETCH > OR > [IXSCAN, IXSCAN] | returned 6668 | keys 7334 | docs 6668
```

What this shows:

- `$ne` and `$nin` **do use the index** (`IXSCAN`) - the planner walks the ranges on either side of the excluded value. What they cannot do is be *selective*: `$ne "Berlin"` examined 16 001 keys and fetched 16 000 documents out of 20 000. It is an index scan that behaves like a near-full scan, which is the accurate version of the old warning.
- `$in` on one field and an `$or` of equalities on the same field produce **the same plan** (`FETCH > IXSCAN`, 6 669 keys) - the optimizer rewrites one into the other, so choose whichever reads better.
- An `$or` needs an index for **every** branch to use them: with indexes on both `city` and `joined` it ran an `OR` of two `IXSCAN`s; when one branch (`fines: 3`) had no index, the whole query fell back to `COLLSCAN` and examined all 20 000 documents.

## Tips and gotchas

- **A plain value is `$eq`.** Writing `{ fines: 0 }` and `{ fines: { $eq: 0 } }` are identical. Reach for the explicit operators only when you need a comparison other than equality.
- **`$ne`, `$nin`, `$nor` and `$not` also match missing fields.** Proven above: `fines: { $ne: 0 }` matched Ada (no field) and Barbara (`null`). If you mean "has a fines field and it is not 0", combine with `$exists` or use `$gt`.
- **Range operators only see their own type.** `{ joined: { $gt: 2000 } }` skipped the string `"2020"`; a mistyped value hides from numeric ranges silently.
- **Two operators on one field go in one document.** Range queries like `{ $gte: 2022, $lte: 2023 }` are a single value document, not two separate filters - repeating the same field key at the top level drops the first (see the find lesson).
- **Prefer `$in` over a pile of `$or` equalities.** They compile to the same plan here, but `$in` is shorter and reads better.

<Callout title="Operators live in the value, logic lives at the top">
Comparison and element operators ($gt, $in, $exists, $type) sit inside a field's value. Logical operators ($and, $or, $not, $nor) sit at the top level of the filter and take whole sub-filters. Keeping that split straight in your head prevents most malformed queries.
</Callout>

## Mental Model

Every query operator answers "does the value **at this path** satisfy the predicate?" - and a missing path or a value of another type is a legitimate input that the predicate must decide about. **Positive** operators (`$eq`, `$gt`, `$in`, `$exists: true`) fail on missing/mistyped values; **negative** operators (`$ne`, `$nin`, `$not`, `$nor`) *succeed* on them. When results look too broad, look for a negative operator; when they look too narrow, look for a type mismatch.

## Trade-offs

| Choice | Benefit | Cost |
|---------|---------|------|
| Equality filter (`$eq` or a plain value) | Most selective, fully uses an index (4 000 keys for 4 000 hits) | Cannot answer range or set questions |
| Range/set operators (`$gt`, `$gte`, `$lt`, `$lte`, `$in`) | Answers range/set questions, still indexable if the field has a matching index | Lower selectivity than equality, especially for wide ranges - can read more keys and documents than necessary |
| Negative operators (`$ne`, `$nin`, `$nor`, `$not`) | Express "everything except" directly | Match missing/`null`/mistyped values; use the index but examine nearly everything (16 001 keys for `$ne`) |
| Combining with `$and`/`$or`/`$nor` | Answers complex logical questions in one call | `$or` needs an index on every branch or it falls back to a collection scan (20 000 documents examined) |

## Common Misconceptions

- **"`$ne` / `$nin` skip the index."** - they use it, but with near-zero selectivity (16 001 keys examined for 16 000 results).
- **"`$or` across different fields is covered by one index."** - each branch needs its own index; one unindexed branch turned the whole query into a `COLLSCAN`.
- **"`$not: 5` works."** - the server answers `$not argument must be a regex or an object`; wrap an operator: `$not: { $eq: 5 }`.
- **"`{ field: null }` means the field is null."** - it also matches documents where the field is missing.
- **"A number stored as a string still falls in numeric ranges."** - `"2020"` was absent from `$gt: 2000`.
- **"`$nor` finds documents that do not match."** - it matches those where none of the branches hold, which includes documents missing the fields entirely.

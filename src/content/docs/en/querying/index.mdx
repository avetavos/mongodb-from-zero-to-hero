Inserting data is easy. The skill that separates someone who *stores* documents from someone who actually *uses* a database is reading them back with precision. Querying is the art of describing, exactly and no more, the subset of documents you care about — and then shaping what comes back so you receive only the fields you need, in the order you want, in pages small enough to handle. This module is entirely about that second half of the database: reading.

We will keep working with a small, made-up collection of library `members` and the books they borrow, because tiny data keeps the queries in the spotlight. By the end you will be able to filter on comparisons and logical combinations, dig into arrays and embedded sub-documents, and trim, sort, and page through results without dragging the whole collection across the wire.

## A query is a description, not a search loop

When you query MongoDB you never write a loop. You hand the server a **filter document** that *describes* the documents you want, and the server finds them. A filter like the one below reads as "every member who joined in 2023 and currently owes nothing":

```js
db.members.find({ joined: 2023, fines: 0 })
```

The plainest filter pairs a field name with a value, and several pairs in the same filter are an implicit AND. From there, querying grows in four directions, and this module takes them one at a time.

## What this module covers

- **Comparison and logical operators.** Beyond exact matches: greater-than, less-than, membership in a set, the absence of a field, and how to combine conditions with explicit AND/OR/NOT. These are the everyday workhorses.
- **Querying arrays.** A field can hold a list. You will learn to match a single element, to require several conditions on *the same* element with `$elemMatch`, to require that several values all be present with `$all`, and to filter by array length.
- **Querying nested documents.** Documents nest. Dot notation lets you reach a field buried inside an embedded object, and there is an important difference between matching a whole sub-document exactly and matching just one of its fields.
- **Projection, sorting, and pagination.** Once you have the right documents, you decide which fields to return, what order they arrive in, and how to slice a large result into manageable pages — and why one popular paging trick gets slow at scale.

Every lesson shows the same query five ways — in `mongosh`, then the Node.js, Python, Go, and Rust drivers — alongside the JSON documents it would return, so you can read the shape of the answer, not just the call.

<Callout title="Reading is the half of the database you will use most">
Most application code reads far more than it writes. Time spent learning to write precise filters and lean projections pays back on every page load — a good query returns exactly the documents and fields you need, and nothing you have to throw away on the client.
</Callout>

## Trade-offs

| Choice | Benefit | Cost |
|---------|---------|------|
| Filter only, no projection specified | Fast to write, query works right away | Returns unused fields every time, wasting bandwidth and client-side memory |
| Filter + a projection listing explicit fields | Reduces data sent over the network, forces the team to see the exact fields the app relies on | Must be kept in sync as the schema evolves |
| An exact-match filter | Always fast and indexable | Cannot answer range/set/complex expression questions |
| A complex filter with several operators and `$and`/`$or` | Answers much more detailed questions | Harder to read, and risks pushing the query planner toward the wrong index |

## Common mistakes

- **Using `$where` to write a condition standard operators cannot express** — `$where` runs JavaScript per document, so it is very slow, cannot use an index at all, and opens a security risk if it takes user input. Always look for a standard operator or aggregation first.
- **Writing an unanchored regex like `/foo/` instead of `/^foo/`** — a regex without `^` forces MongoDB to scan every document in the collection, unable to use an index even if that field has one. If you mean "starts with," always anchor at the start.
- **Assuming skipping the projection has no cost** — every field you do not exclude travels over the network, and the application must serialize all of it. For documents with large fields (a long description, or a big array), a forgotten projection is a common cause of latency.

> 💡 Real-world example
>
> **An e-commerce product filter page** — a sidebar filtering by category, price range, brand, and rating maps directly onto comparison/logical operators (`$gte`, `$lte`, `$in`), and uses a projection to return only the fields a product card needs (name, price, main image), not the whole document.
>
> **An internal admin search panel** — a tool for searching users or orders internally often accidentally lets users type their own regex straight into the query with no anchor, making the search page get slower and slower as the data grows.
